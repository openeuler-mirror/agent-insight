# Troubleshooting · Evaluation

按高频度排序的常见问题与排查清单。

---

## 1. 评测任务跑不动 / 一直 pending

**症状**：触发 `POST /api/eval/rejudge` 或 UI 上点 Run 后，`Evaluation.status` 永远 pending / running。

**排查步骤**

```bash
# 1. 看模型配置是否激活
curl "http://localhost:3000/api/eval/settings?user=demo@163.com" \
  -H "x-witty-api-key: $API_KEY"
# 期望：{ apiKey, baseUrl, model, provider } 都有值

# 2. 测连接
curl -X POST http://localhost:3000/api/eval/settings/test \
  -H "x-witty-api-key: $API_KEY" \
  -d '{}'
# 期望：{ success: true }

# 3. 看 server.log 评估相关错误
tail -200 server.log | grep -i "evaluation\|judge\|error"

# 4. 看 Evaluation 表当前状态
# (开发环境直接看 SQLite)
sqlite3 data/sqlite.db "SELECT id, type, status, errorMessage FROM Evaluation WHERE status != 'done' LIMIT 10"
```

**常见原因**

- ❌ LLM 配置错（API Key 过期 / 配额耗尽 / baseUrl 写错）
- ❌ 模型 context 太短（trace 太长喂不进去）
- ❌ 评估 prompt 出错（罕见，看 server.log）
- ❌ 平台进程卡死（重启 `bash scripts/restart_dev.sh`）

## 2. 评估器分数偏低 / 不准

**症状**：感觉 LLM-as-Judge 评得太严 / 太松，与人工标注差距大。

**排查**

1. **`standardAnswer` 是否合理？** —— 太死板的"完美答案"会让 LLM 评 fail
2. **评估 LLM 是否够强？** —— DeepSeek-7B 评 Claude Sonnet 4 的输出会不准
3. **`judgment_reason` 怎么说？** —— 读几条 reason 看 LLM 的扣分理由对不对
4. **temperature 是否太高？** —— 评估器建议 ≤ 0.3，太高方差大

**修复**

```bash
# 看几条 Evaluation 的 judgment_reason
curl /api/observe/data?user=demo&limit=10 | jq '.[] | {answerScore, failures}'

# 换强模型
curl -X POST /api/eval/settings -d '{
  "settings": { "model": "claude-sonnet-4", "temperature": 0.2 },
  "user": "demo@163.com"
}'

# 重新评一条对比
curl -X POST /api/eval/rejudge -d '{"task_id": "..."}'
```

详见 [LLM-as-a-Judge](./evaluation-methods/llm-as-a-judge) 与 [Human Annotation](./evaluation-methods/human-annotation)。

## 3. 数据集导入失败

**症状**：`POST /api/eval/config/create` 上传 PDF 后 `parse_status` 一直 pending 或返回 500。

**排查**

```bash
# 1. 检查 parse_doc.py 依赖
uv pip install -r skills/skill-generator/scripts/requirements.txt

# 2. 试本地解析
uv run python skills/skill-generator/scripts/parse_doc.py /tmp/test.pdf -o /tmp/out.md

# 3. 看平台 parse 日志
tail -100 server.log | grep -i "parse\|document"
```

**常见原因**

- ❌ `parse_doc.py` 依赖缺失（python uv / pypdf2 / pdfplumber）
- ❌ PDF 加密 / 扫描件无文本（OCR 在 v2 规划）
- ❌ 文件太大（默认上限 50MB）
- ❌ LLM 抽取超时

详见 [Dataset Import](./features/dataset-import)。

## 4. 同一 Trace 评了多次结果不一致

**症状**：`POST /api/eval/rejudge` 跑两次，第一次 0.8 第二次 0.5。

**原因**

LLM 调用本身有随机性。temperature > 0 时同 prompt 多次跑结果会不一样。

**修复**

1. 评估 LLM 配 `temperature: 0`（评估器追求确定性）
2. 接受方差 —— 重要决策跑 3 次取平均
3. 用规则评估器（[Custom Evaluators](./evaluation-methods/custom-evaluators)）做兜底

## 5. SkillIssue 不出来 / 出错的项

**症状**：评测跑完 `Execution.answerScore` 有值，但 `SkillIssue` 表空 / 不全。

**排查**

```bash
# 看评估器输出有没有 is_skill_attributable=true 的项
curl /api/observe/executions/{id}/skill-issues
```

**常见原因**

- ❌ 评估器全判 `is_skill_attributable=false` —— 那些问题都改 Skill 解决不了（如模型本身能力）
- ❌ severity 全 low —— 平台默认过滤 low severity（[derive-skill-opt-points.ts](https://github.com/your-org/agent-insight/blob/main/src/lib/engine/evaluation/derive-skill-opt-points.ts) 关键过滤逻辑）
- ❌ 已 resolved —— `resolvedAt` 非空的 issue 默认隐藏（加 `?includeResolved=1`）

详见 [Intelligent Diagnosis](../observability/features/intelligent-diagnosis) §关键过滤逻辑。

## 6. 评测大批量耗时 / token 爆炸

**症状**：批量评 1000 个 Trace 一晚上跑不完 / token 账单飙升。

**修复**

| 方法 | 节省幅度 |
|---|---|
| 降并发，但分批跑 | 时间一样，避免限流 |
| 改用便宜评估模型（Claude Haiku） | 80-90% token |
| 用 [Custom Evaluator](./evaluation-methods/custom-evaluators) 做粗筛 | 大头 case 不用 LLM 评 |
| [Sampling](../observability/features/sampling) 只评 10% | 90% token |
| 用 [Online Evaluation 的 debouncer](./features/online-evaluation) | 重复 case 合并 |

## 7. 评测集 case 不被识别

**症状**：评测任务跑了，但 `Evaluation` 表的 `rootCauseMatches` / `keyActionCoverage` 全空。

**原因**

数据集 case 里的 `keyActions[]` / `rootCauses[]` 字段没填或格式错。

**修复**

```bash
# 看 case 字段
curl "http://localhost:3000/api/agent-datasets/{id}?user=demo@163.com" \
  | jq '.cases[0]'

# 期望看到 keyActions: ["..."] 和 rootCauses: [{label: "...", weight: 0.5}]
```

UI 上"数据项录入"页编辑，或走 PATCH API 补全。

## 8. 触发评价集（recall）跑不出来

**症状**：`POST /api/skill-eval/trigger/{name}/run` 一直 running。

**注意**：触发评价集与 `AgentEvalDataset` 是不同实体，走的是 [Skills 模块的 recall 分析](../skills/analysis/overview)。

**排查**

1. 看是否安装了 opencode（评测依赖 opencode-live 模式跑）
2. `.opencode/skills/<name>/SKILL.md` 是否物化（平台启动评测时写入）
3. 看 LLM modelConfigId 是否传对

详见 [PROJECT.md §6.7](https://github.com/your-org/agent-insight/blob/main/docs/PROJECT.md)。

## 9. UI 上分数对不上 API 返回的

**症状**：UI 上看 Trace `answerScore: 0.8`，但 API 拉的 `Evaluation` 表里有 `score: 0.6` 的记录。

**原因**

UI 显示**最新**的 Evaluation（按 `ranAt` 倒序）。重评后会有多条 Evaluation，UI 只显示最新一条。

**确认**

```bash
# 拉所有评估事件（按时间倒序）
curl /api/observe/executions/{id}/evaluations | jq 'sort_by(-.ranAt)'
```

详见 [Core Concepts § Evaluation 1:N](./core-concepts) 。
