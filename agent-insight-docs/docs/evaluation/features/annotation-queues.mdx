# Annotation Queues

## 是什么

把 LLM-as-Judge 不确定 / 失败 / 高价值的 Trace 推入"标注队列"，由人工 review + 标记真实分数 / 失败归因 / SkillIssue 是否合理。标注结果回写到 `Evaluation` + `SkillIssue.source='feedback'`，作为评估器的"ground truth"。

## 它解决什么问题

LLM-as-Judge 不是 100% 准。需要人工兜底的场景：

| 场景 | 人工标注的价值 |
|---|---|
| LLM 评估器给低置信度结果 | 人来定夺 |
| 失败 case 的 root cause 难判断 | 人解读 |
| 新评估器上线前验证 | 标 100 条对比 LLM vs 人 |
| 团队对齐 quality criteria | 共同标注 + 讨论 |

## 怎么用

### 通过 UI（v2 规划）

进入 **评测中心 → 标注队列**：

提供：

| 区域 | 内容 |
|---|---|
| 待标注列表 | 按优先级 / 时间排序的待标 Trace |
| 标注表单 | 评分（0-1） + 类别（pass/fail/uncertain）+ 备注 |
| 进度 | 这个队列总共多少，已标了多少 |
| 数据集导出 | 标完一批可以一键导出为评测集 |

### 通过 REST API（v2 规划）

```bash
# 创建标注队列
curl -X POST http://localhost:3000/api/annotation/queues \
  -H "x-witty-api-key: $API_KEY" \
  -d '{
    "name": "low-confidence-2026-05",
    "filter": {
      "evaluatorConfidence": "< 0.6",
      "timeRange": "7d"
    },
    "assignedTo": ["alice@example.com", "bob@example.com"],
    "instructions": "..."
  }'

# 拉一条待标
curl http://localhost:3000/api/annotation/queues/{id}/next \
  -H "x-witty-api-key: $API_KEY"

# 提交标注
curl -X POST http://localhost:3000/api/annotation/items/{id}/submit \
  -H "x-witty-api-key: $API_KEY" \
  -d '{
    "annotatorId": "alice@example.com",
    "score": 0.4,
    "category": "fail",
    "issueIds": ["iss_xxx", "iss_yyy"],
    "note": "Agent 没识别出退款意图..."
  }'
```

## 入队策略

谁该进队列？平台支持几种过滤条件：

| 条件 | 适合 |
|---|---|
| **LLM 评估器 confidence 低** | 评估器自己也拿不准 |
| **score 在边界** | 0.45-0.55 这种 ambiguous case |
| **新评估器跑出来的全部** | 评估器上线前验证 |
| **失败 + high severity SkillIssue** | 重要失败 |
| **随机抽 N%** | 持续质量校准 |

可以组合（且 / 或）。

## 标注结果的去向

标完的结果会：

1. 写到 `Evaluation.l2ScoresJson.human_score`
2. 如果是 SkillIssue 反馈，新增 `SkillIssue(source='feedback')`
3. 累积一定量后可以训练 / fine-tune 评估器（v2 规划）
4. 导出成 `AgentEvalDataset` 当评测集（"金标准集"）

## 关键参数

| 参数 | 类型 | 说明 |
|---|---|---|
| `name` | string | 队列名 |
| `filter` | object | 入队过滤条件 |
| `assignedTo[]` | string[] | 标注人员（user ID） |
| `instructions` | string | 标注规范 |
| `requireMultiAnnotator` | bool | 是否需要 2+ 人同标后取多数 |
| `quotaPerAnnotator` | int | 每个标注人最多分配多少 case |

## 多人协作机制

`requireMultiAnnotator=true` 时，每条 case 至少 2 人标，取多数：

```
case_xxx 标注结果：
  - alice: pass (0.8)
  - bob:   pass (0.85)
  - carol: fail (0.4)
→ 多数：pass，平均 0.825，分歧度 0.32
```

分歧度高的 case 自动标记为"需仲裁"，进入 senior 标注队列。

## 最佳实践

- **标注规范文档化** —— 写清楚"什么算 pass / 什么算 fail"，避免标注人各打各的
- **先标 50 条对齐** —— 团队成员先各自标 50 条，看分歧度，统一标准再放量
- **标注疲劳是真的** —— 一个人一天标 100 条是上限，超过质量降
- **重要队列设 multi-annotator** —— 关键评测集（用于 fine-tune）必须多人交叉
- **导出成金标准集** —— 标完一批立即固化为评测集，将来评估器都对它跑

## 常见问题

<details>
<summary>当前版本支持吗？</summary>

当前版本：UI 没有专门的"标注队列"页面，但 `Execution.user_feedback` 字段（PATCH /api/observe/data）支持单条 Trace 的人工反馈。完整标注队列工作流在 v2 规划。
</details>

<details>
<summary>标注人需要单独账号吗？</summary>

平台账号即可。当前版本无 RBAC，所有 user 都能看到自己 user 下的 Trace。多人标注需要给标注人对应 user 的 API Key。详见 [Administration · RBAC](../../administration/rbac)。
</details>

<details>
<summary>标注会影响 Agent 运行吗？</summary>

不会。标注是事后行为，跟在线评测 / Agent 运行完全异步。
</details>
