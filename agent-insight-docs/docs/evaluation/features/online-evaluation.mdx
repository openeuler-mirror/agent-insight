# Online Evaluation

## 是什么

Trace 上报到平台后**自动**触发评估器跑一遍，把 `answerScore` / `isAnswerCorrect` / `failures[]` 实时写回 `Execution`。区别于 [Offline Evaluation](./offline-evaluation)（手动批量），在线评测是被动触发、持续运行的。

底层流程：

```
SDK 上报 Trace → /api/ingest/upload → 写 Session + Execution
                                          │
                                          ▼ 异步触发（autoEval=true 时）
                              evaluation engine 跑
                                          │
                                          ▼
                          写 Evaluation + SkillIssue
                                          │
                                          ▼
                          回写 Execution.answerScore / failures
```

去重逻辑：[`upload-analysis-debouncer.ts`](https://github.com/your-org/agent-insight/blob/main/src/lib/ingest/upload-analysis-debouncer.ts) 把"同一 Skill 30 秒内多次上报"合并成一次评估，省 token。

## 它解决什么问题

| 没在线评测 | 有 |
|---|---|
| 评分滞后（要等批量跑） | 实时打分 |
| 异常发现晚 | 异常 Trace 几秒内出 failures |
| 监控只看 latency / token | 直接看业务质量 |
| 灰度发布看不到回退 | 实时看新版本 answerScore 退化 |

## 怎么用

### 启用在线评测

在线评测**默认开启**。如果你的 Trace 没自动评分，检查：

1. 用户是否配了评估器 LLM（`/api/eval/settings`）
2. Skill 是否有挂数据集（`Skill.targetDataset`）
3. 是否被 throttle 限流（高 QPS 用户会节流）

### 通过 UI 监控

进入 **链路观测**：

- 列表行右侧的 `answerScore` / `failures` 角标实时更新
- 点击行进 Drawer 看完整 `Evaluation` 详情

### 通过 REST API

平台内部异步跑，不暴露 trigger 接口。但可以查询：

```bash
# 查某 Trace 的所有评估事件
curl http://localhost:3000/api/observe/data?taskId=task_xxx \
  -H "x-witty-api-key: $API_KEY"
# 响应每行含派生字段 is_evaluating (true 表示正在评)
```

### 关闭在线评测（Trace 级）

某些场景不需要实时评（如纯监控、内部测试）：

```python
from agent_insight import AgentInsight, observe

AgentInsight.init(api_key="ai_xxx")

@observe(skip_eval=True)
def my_agent(query): ...
```

或者上报时显式带：

```bash
curl -X POST /api/ingest/upload \
  -d '{"task_id":"...","skip_eval":true, ...}'
```

## 在线 vs 离线选哪个

| 场景 | 选哪个 |
|---|---|
| 生产持续质量监控 | 在线 |
| 灰度发布看回退 | 在线 |
| 上线前回归 | 离线 |
| 月度 / 季度报告 | 离线 |
| 多评估器对比 | 离线（在线一般只跑一种） |
| 节省 token | 离线（人工控制频次） |

两者**可以并存** —— 在线评估器跑主流程，离线评估器加项的特殊维度。

## 关键参数

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| 用户级 evaluator 配置 | object | — | 在 `/api/eval/settings` 配 |
| `skip_eval` (per-trace) | bool | false | 单条 Trace 跳过评估 |
| `debounce_window_s` | int | 30 | 去重时间窗（同 Skill 内） |
| `eval_priority` | enum | `normal` | `high`（关键流程）/ `normal` / `low` |

## 节流与去重

`upload-analysis-debouncer.ts` 的去重逻辑：

```
同 Skill, 30 秒内多次上报 → 只触发一次评估
不同 Skill / 间隔超 30 秒 → 各自评估
```

避免高 QPS 场景评估器把 LLM quota 烧光。如果你希望"每条都评"，关闭去重：

```bash
EVAL_DEBOUNCE_ENABLED=false  # .env
```

但生产强烈不建议（成本会飙）。

## 最佳实践

- **生产场景 always-on** —— 关掉等于自废武功
- **关键场景设 `eval_priority=high`** —— 跳过 debounce + 优先调度
- **采样后再评** —— 跟 [Sampling](../../observability/features/sampling) 配合，1% 采样 + 全评 比 100% 采样 + 跳评 划算
- **配回落机制** —— LLM 评估器挂了，至少有规则评估器兜底
- **看评估器自身的 quota** —— 评估 LLM 与 Agent LLM 通常共享一个 API Key，并发要算清

## 常见问题

<details>
<summary>在线评测会拖慢 Agent 响应吗？</summary>

不会。评估器异步跑，不阻塞 `/api/ingest/upload` 响应。SDK 上报立刻返回。
</details>

<details>
<summary>评测要多久？</summary>

LLM-as-Judge：3-10 秒/条。Trajectory：5-30 秒/条（含子评估器）。Custom（纯函数）：< 100ms/条。
</details>

<details>
<summary>评估失败会重试吗？</summary>

会。`Evaluation.status='failed'` 时会按指数退避重试 3 次。3 次都失败的写入 dead-letter 表。
</details>

<details>
<summary>能为不同 Skill 配不同评估器吗？</summary>

可以。`Skill.targetDataset` 字段挂在 Skill 上，平台调度时按 Skill 选评估器。详见 [Datasets](./datasets) 的 `targetSkill`。
</details>
