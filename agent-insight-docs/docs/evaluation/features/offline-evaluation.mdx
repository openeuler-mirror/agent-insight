# Offline Evaluation

## 是什么

对**已经产生**的一批 Trace 跑评估器。区别于 [Online Evaluation](./online-evaluation)（生产流量实时评估），离线评测是回顾性的 / 批量的 / 不影响生产流量的。

典型用法：

- 上线前回归（新版本对老用例跑一遍看分数）
- 周报 / 月报指标
- A/B 测试（[GrayscaleTask](../../skills/data-model) 底层就是离线评测）
- 应用模型升级后对历史数据重评

## 它解决什么问题

| 没离线评测 | 有 |
|---|---|
| 不知道新版本对老用例怎么样 | 一键跑出来 |
| 月报数据靠人捞 | 离线任务自动出指标 |
| 旧 Trace 没分数（评估器没跑过） | 重评全捞回来 |
| 不敢上线（怕回退） | 离线对比兜底 |

## 怎么用

### 通过 UI

进入 **评测任务**（`/eval`）→ 新建评测：

<!-- TODO 截图：新拍。评测任务工作台（AgentEvalCenter），覆盖选数据集 / 评估器 / Trace 范围 / 开始 Run。 -->

填：

- **评估对象**：哪批 Trace（按时间 / 按 Skill / 按 user 筛选）
- **评测集**：哪个 [AgentEvalDataset](./datasets)
- **评估器**：[LLM-as-Judge](../evaluation-methods/llm-as-a-judge) / [Trajectory](../core-concepts) / [Custom](../evaluation-methods/custom-evaluators)

点 **Run**，任务异步跑。每条 Trace 完成后 `Evaluation` 表多一行，UI 实时刷新。

### 通过 REST API

```bash
# 单条 Trace 重评（最简单）
curl -X POST http://localhost:3000/api/eval/rejudge \
  -H "x-witty-api-key: $API_KEY" \
  -d '{"task_id": "task_xxx", "currentUser": "demo@163.com"}'
# → { success: true, record }

# 批量评测（v2 规划）—— 当前用循环
for task_id in $(curl "/api/observe/data?user=demo@163.com&skill=pdf-extractor" | jq -r '.[].task_id'); do
  curl -X POST /api/eval/rejudge -d "{\"task_id\":\"$task_id\",\"currentUser\":\"demo@163.com\"}"
done
```

### Trajectory 评测专用入口

`POST /api/eval/trajectory/run` 跑轨迹评估（结果路径 + 完整 trace 路径）：

```bash
curl -X POST http://localhost:3000/api/eval/trajectory/run \
  -H "x-witty-api-key: $API_KEY" \
  -d '{
    "user": "demo@163.com",
    "executionIds": ["exec_xxx_1", "exec_xxx_2"],
    "datasetId": "ds_xxx"
  }'
```

跑完会自动触发 [`derive-skill-opt-points.ts`](https://github.com/your-org/agent-insight/blob/main/src/lib/engine/evaluation/derive-skill-opt-points.ts)，把扣分项落到 `SkillIssue` 表。详见 [Intelligent Diagnosis](../../observability/features/intelligent-diagnosis)。

## 关键参数

| 参数 | 类型 | 说明 |
|---|---|---|
| `task_id` / `executionIds[]` | string / string[] | 要评的 Trace |
| `datasetId` | string | 用哪个数据集打分 |
| `evaluatorId` | string | 评估器 ID |
| `currentUser` | string | 当前操作用户 |
| `concurrency` | int | 并发上限（默认 3） |

## 离线 vs 在线对比

| 维度 | 离线（本页） | 在线（[Online Evaluation](./online-evaluation)） |
|---|---|---|
| 触发 | 手动 / 定时 | 每条 Trace 自动 |
| 范围 | 历史 batch | 实时单条 |
| 性能影响 | 不影响生产 | 异步但有 token 成本 |
| 适合 | 回归 / 报告 / 上线前 | 持续监控 / 实时告警 |

## 最佳实践

- **新版本上线前必跑回归**：拿过去 7 天的 Trace 重评新旧两个版本
- **评测集要稳定**：跨实验对比需要相同数据集，频繁改数据集 = 分数没可比性
- **并发不要拉太高**：LLM 评估器吃 token，并发太大撞 rate limit
- **大批量跑前估成本**：1000 trace × LLM-as-Judge ≈ 1000 次评测 LLM 调用
- **结果带 generator 字段**：评估器版本变了，老结果不删但加新 generator 区分

## 常见问题

<details>
<summary>同一 Trace 评了 5 次，UI 显示哪一次？</summary>

UI 默认显示最新的 `Evaluation`（按 `ranAt` 倒序）。每次重评不删历史，只新增。详见 [Evaluation Data Model](../core-concepts)（重评懒删除原则）。
</details>

<details>
<summary>评估失败的 Trace 怎么处理？</summary>

`Evaluation.status = 'failed'` + `errorMessage` 字段。可以通过 API 重跑：

```bash
curl -X POST /api/eval/rejudge -d '{"task_id": "task_xxx"}'
```

如果反复失败，看 server.log，通常是 LLM quota / 模型不支持长 context。
</details>

<details>
<summary>能跨 user 跑离线评测吗？</summary>

不能。`currentUser` 字段决定数据访问范围。多 user 评测要分别跑（或用 admin 账号）。
</details>
