# Regression Detection

## 是什么

把新 Experiment / 新 Skill 版本 / 新模型上线的评分**自动与历史 baseline 对比**，发现退化（regression）立即告警。区别于 [Quality Monitoring](../../observability/features/quality-monitoring)（监控绝对指标），Regression 监控的是**相对历史**的变化。

## 它解决什么问题

| 没退化检测 | 有 |
|---|---|
| 上线慢慢发现"好像变差了" | 上线立刻告警 |
| 改 Skill 不知道是否回退老用例 | 新版本对老用例跑一遍立刻知道 |
| 模型升级后没人验证 | 自动跑回归 |
| 评估指标变了但不知道哪里来的 | 平台标 baseline 与 diff |

## 怎么用

### 通过 UI（v2 规划）

进入 **评测中心 → 回归检测**：

<!-- TODO 截图：新拍。回归检测界面：左侧 baseline 选择，右侧本次 Experiment 对比，差异 case 红框标出。 -->

提供：

| 区域 | 内容 |
|---|---|
| Baseline 选择 | 选哪个历史 Experiment / 版本作为对照 |
| 当前 vs Baseline | 整体分 diff + case-by-case diff |
| 退化告警 | 退化超阈值的 case 高亮 + 建议修复 |
| 自动追溯 | 给出"上次类似分数是什么时候" |

### 通过 REST API（v2 规划）

```bash
# 配置 baseline
curl -X POST http://localhost:3000/api/eval/baselines \
  -H "x-witty-api-key: $API_KEY" \
  -d '{
    "user": "demo@163.com",
    "name": "pdf-extractor production",
    "experimentId": "exp_baseline",
    "metric": "mean_score",
    "threshold": -0.05
  }'

# 跑 Experiment 时自动比 baseline
curl -X POST http://localhost:3000/api/eval/experiments \
  -d '{
    "datasetId": "ds_xxx",
    "evaluatorId": "evaluator_llm_judge",
    "compareToBaseline": "baseline_xxx"
  }'
# 响应额外字段：regression: { detected: true|false, casesDegraded: [...] }
```

### 当前版本可用方案

v2 真正上线前，可以组合：

1. 用 [Score Comparison](./score-comparison) 手动对比新旧 Experiment
2. 用 [A/B Testing](../../skills/analysis/ab-testing) 的三步法 DECISION（短板原则会自动 reject 退化版本）
3. 用 [Quality Monitoring](../../observability/features/quality-monitoring) 配阈值告警

A/B Testing 的 **rejectCategory** 字段就是一种 regression detection：B 版本能力分 < A 减 X 就 reject。详见 [Step 3 · DECISION](../../skills/analysis/step3-decision)。

## 退化判定

```
baseline_score = mean(historical Experiment scores)
current_score = current Experiment score

regression = current_score - baseline_score
            < -threshold  (默认 -0.05)
```

精细化：

| 类型 | 判定 | 例子 |
|---|---|---|
| **整体退化** | mean_score 降 ≥ threshold | 0.85 → 0.78 |
| **case 退化** | 某条 case 分数降 ≥ case_threshold | 0.9 → 0.5 |
| **新失败模式** | 出现 baseline 里没有的 SkillIssue dedupKey | 新涌现的 issue |
| **稳定性退化** | variance 上升 ≥ 0.1 | 输出抖动变大 |

## 关键参数

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `baselineExperimentId` | string | — | baseline Experiment |
| `metric` | string | `mean_score` | 监控指标 |
| `threshold` | float | -0.05 | 退化阈值 |
| `caseLevelThreshold` | float | -0.2 | 单 case 退化阈值 |
| `notify[]` | string[] | — | 告警渠道 URI |

## 触发时机

退化检测可以在三个时机触发：

1. **手动**：用户跑 Experiment 时选 `compareToBaseline`
2. **CI/CD**：通过 [Webhooks](../../api-and-data-platform/webhooks) 在 PR 合并时触发
3. **定时**：每日 / 每周自动对生产数据跑回归

## 最佳实践

- **baseline 别用刚上线的版本** —— 用"已经稳定一段时间" 的版本，避免噪声
- **多 baseline** —— 不同业务场景挂不同 baseline
- **threshold 别设太敏感** —— -0.01 会触发太多 false alarm，-0.05 比较合理
- **case-level threshold 单独配** —— 整体 mean 看不到，但单 case 退 50% 是大问题
- **退化后必有 owner** —— 告警送到 owner，不要"团队群"（没人负责）

## 常见问题

<details>
<summary>当前怎么做手动退化检测？</summary>

```bash
# 跑老版本（baseline）
EXP_OLD=$(curl -X POST /api/eval/experiments -d '{"datasetId":"ds_xxx","evaluatorId":"e_xxx","versionId":"v1"}')

# 跑新版本
EXP_NEW=$(curl -X POST /api/eval/experiments -d '{"datasetId":"ds_xxx","evaluatorId":"e_xxx","versionId":"v2"}')

# 对比
curl -X POST /api/eval/experiments/compare \
  -d "{\"experimentIds\":[\"$EXP_OLD\",\"$EXP_NEW\"]}"
```

详见 [Score Comparison](./score-comparison)。
</details>

<details>
<summary>能自动回滚吗？</summary>

v2 规划支持：退化超阈值 → 自动触发 [Canary Release](../../skills/management/canary-release) 回滚。当前版本：检测到 + 告警，但回滚要人工。
</details>

<details>
<summary>baseline 怎么更新？</summary>

定期（如每月）选最佳 Experiment 升为新 baseline。或者用"rolling baseline"（最近 N 个 Experiment 的均值）做对比，避免人工维护。
</details>
