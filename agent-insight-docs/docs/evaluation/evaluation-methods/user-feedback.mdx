# User Feedback

## 是什么

让 Agent 的**终端用户**（不是平台账号）给 Trace 打分。最常见的形式：

- 👍 / 👎 二元反馈
- 1-5 星评分
- 自由文本评论

落到 `Execution.user_feedback` 字段（PATCH `/api/observe/data` 接口）。

> 区别于 [Human Annotation](./human-annotation) —— 那是平台内部标注人员审阅，user_feedback 是终端用户的真实声音。

## 它解决什么问题

LLM-as-Judge 是"模拟人评"，终端用户反馈是"真实人评"，价值不可替代：

| 维度 | LLM-as-Judge | User Feedback |
|---|---|---|
| 谁评？ | 一个 LLM | 真实用户 |
| 维度 | standardAnswer 对齐 | 实际感受好不好 |
| 频率 | 每条 Trace | 部分用户主动给 |
| 偏差 | LLM 自身偏好 | 用户主观偏好（更真实） |
| 价值 | 持续监控 | 终极 ground truth |

## 怎么用

### 在 Agent 输出后让用户反馈

在你的 Agent 应用里加反馈按钮，调平台 PATCH API：

```typescript
// 用户点 👍 / 👎 后
async function submitFeedback(taskId: string, feedback: 'positive' | 'negative', note?: string) {
  await fetch("http://localhost:3000/api/observe/data", {
    method: "PATCH",
    headers: {
      "Content-Type": "application/json",
      "x-witty-api-key": process.env.AGENT_INSIGHT_API_KEY,
    },
    body: JSON.stringify({
      task_id: taskId,
      user_feedback: feedback === 'positive' ? "👍" : `👎 ${note ?? ''}`,
    }),
  });
}
```

```python
import requests

requests.patch(
    "http://localhost:3000/api/observe/data",
    headers={"x-witty-api-key": "ai_xxx"},
    json={"task_id": "task_xxx", "user_feedback": "👎 答非所问"},
)
```


## user_feedback 字段格式

`Execution.user_feedback` 是字符串字段，平台不强制格式，但推荐用结构化前缀方便后续筛选：

| 反馈类型 | 推荐格式 |
|---|---|
| 二元 | `"👍"` / `"👎"` |
| 1-5 星 | `"⭐⭐⭐⭐"` / `"4/5"` |
| 类别 + 文字 | `"unhelpful: 答非所问"` |
| 纯文本 | `"不错但太长了"` |

平台对前缀做轻量解析（v2 规划），UI 能按反馈类型聚合统计。

## 关键参数

| 参数 | 类型 | 说明 |
|---|---|---|
| `task_id` | string | 哪条 Trace |
| `user_feedback` | string | 反馈文本 |
| `feedback_meta` | object | 反馈元数据（v2，含来源 / 时间戳 / 用户 segment） |

## 与其他评分关系

```
                ┌──────────────────────┐
                │   LLM-as-Judge       │  score: 0.8
                │   (自动评)            │  reason: "覆盖了主要点"
                └──────────────────────┘
                           ┊
                ┌──────────────────────┐
                │  Human Annotation    │  human_score: 0.6
                │  (内部审阅)           │  category: fail
                └──────────────────────┘
                           ┊
                ┌──────────────────────┐
                │  User Feedback       │  👎 "答非所问"
                │  (终端用户)           │
                └──────────────────────┘
```

三层评分**互相校验**：

- LLM 评 0.8、用户 👎 → LLM 评估器需要调整
- LLM 评 0.8、用户 👍 → 评估器准
- LLM 评 0.4、用户 👍 → standardAnswer 可能太严，用户实际接受

## 最佳实践

- **让反馈尽量轻量** —— 👍/👎 比 5 星比文本反馈用户参与率高
- **不要逼用户反馈** —— Modal 弹窗强制反馈 = 用户流失
- **反馈率 5-15% 算正常** —— 别期望 100% 用户都反馈
- **负面反馈优先 review** —— 👎 的 Trace 进 [Annotation Queue](../features/annotation-queues)
- **用 user segment 分群** —— 企业用户 vs 免费用户的反馈倾向不同
- **不要把反馈当唯一评分** —— 主观偏差大，要与 LLM-as-Judge / annotation 互补

## 常见问题

<details>
<summary>反馈数据怎么聚合看？</summary>

当前版本：UI 按 `user_feedback` 字段过滤列表。聚合分析（如 👍/👎 比例时序）走 [Metrics](../../metrics/overview)（v2 落地）。

或者拉数据自己分析：

```bash
curl /api/observe/data?user=demo \
  | jq 'group_by(.user_feedback) | map({fb: .[0].user_feedback, n: length})'
```
</details>

<details>
<summary>反馈和 PII 怎么处理？</summary>

用户在自由文本反馈里可能写邮箱 / 电话。PII 脱敏在客户端做（详见 [PII Masking](../../observability/features/pii-masking)），或者平台收到后服务端兜底脱敏。
</details>

<details>
<summary>反馈能驱动 Skill 优化吗？</summary>

可以。把"频繁 👎 的 case"加到 [Annotation Queue](../features/annotation-queues)，标注后产出 `SkillIssue(source='feedback')`，进入 [Skills 优化](../../skills/optimization/overview) 的 `feedback` 模式（[`docs/optimization-tech.md`](https://github.com/your-org/agent-insight/blob/main/docs/optimization-tech.md) §3.3）。
</details>
