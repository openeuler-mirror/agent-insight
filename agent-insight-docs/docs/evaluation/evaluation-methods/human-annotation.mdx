# Human Annotation

## 是什么

让人来给 Trace 打分 / 归因 / 标 SkillIssue 是否合理。在评测体系里扮演两个角色：

1. **Ground truth** —— 标 100-1000 条作为黄金标准，让 LLM-as-Judge 学
2. **兜底** —— LLM 不确定 / 失败 / 高价值的 case 进入 [Annotation Queues](../features/annotation-queues) 由人决断

写回字段：`Execution.user_feedback` + `Evaluation.l2ScoresJson.human_score`。

## 它解决什么问题

| 没人工标注 | 有 |
|---|---|
| 评估器自说自话 | 有人类基准对比 |
| 不知道评估器准不准 | 拿标注集算 inter-rater reliability |
| 重要场景出错没人审 | 关键场景必标 |
| LLM 不擅长的场景没法 | 主观偏好 / 文化敏感 / 法律意见 |

进入 **链路观测 → 选 Trace → Drawer 底部 user_feedback**：

或者进入 [Annotation Queues](../features/annotation-queues)（v2 规划）批量审阅。

### 通过 REST API

```bash
# 给单条 Trace 加人工反馈
curl -X PATCH http://localhost:3000/api/observe/data \
  -H "x-witty-api-key: $API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "task_id": "task_xxx",
    "user_feedback": "Agent 漏了退款步骤，应判 fail"
  }'

# 详细标注（v2 规划）
curl -X POST http://localhost:3000/api/annotation/items/{id}/submit \
  -H "x-witty-api-key: $API_KEY" \
  -d '{
    "annotatorId": "alice@example.com",
    "score": 0.4,
    "category": "fail",
    "rootCauseMatches": [{"label": "未识别退款意图", "matched": true}],
    "note": "Agent 直接给了帮助文档链接，没调 API"
  }'
```

## 标注表单字段

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `score` | float 0-1 | ✅ | 人工评分 |
| `category` | `pass` / `fail` / `uncertain` | ✅ | 分类 |
| `rootCauseMatches[]` | object[] | ❌ | 命中哪些 root cause |
| `keyActionCoverage[]` | object[] | ❌ | 哪些 key action 覆盖了 |
| `note` | string | ❌ | 自由文本说明 |
| `confidence` | float 0-1 | ❌ | 标注人自己的把握 |

## 与 LLM-as-Judge 配合

```
                ┌──────────────────────┐
                │   LLM-as-Judge       │  默认对所有 Trace 跑
                │   产出 score + reason │
                └──────────┬───────────┘
                           │
                           │ 置信度低 / 失败 / 关键场景
                           ▼
                ┌──────────────────────┐
                │  Annotation Queue    │  推入待标列表
                └──────────┬───────────┘
                           │
                           │ 标注人 review
                           ▼
                ┌──────────────────────┐
                │  Human Annotation    │  写回 human_score
                │  作为 ground truth   │
                └──────────────────────┘
                           │
                           │ 累积 100+ 条后
                           ▼
                ┌──────────────────────┐
                │  Inter-rater         │  评估 LLM-as-Judge
                │  reliability         │  准不准
                └──────────────────────┘
```

## 多人标注与一致性

`requireMultiAnnotator=true` 时，每条 case 由 2-3 人独立标，平台自动汇总：

```
case_xxx:
  - alice: pass (0.8)
  - bob:   pass (0.85)
  - carol: fail (0.4)

→ majority: pass
→ mean_score: 0.683
→ disagreement: 0.4 (高于阈值 0.3)
→ flag for senior review
```

分歧度高（> 0.3）的 case 自动 escalate 给 senior 标注。详见 [Annotation Queues](../features/annotation-queues)。

## 常用一致性指标

| 指标 | 说明 | 取值范围 |
|---|---|---|
| **Cohen's kappa** | 两人间一致性（控制偶然） | -1 to 1，> 0.6 = 实质一致 |
| **Fleiss' kappa** | 多人间一致性 | -1 to 1 |
| **Pearson 相关** | 连续分数相关性 | -1 to 1 |
| **Krippendorff's alpha** | 任意分类一致性 | -1 to 1 |

平台支持自动计算（v2 规划）；当前手动跑 sklearn / nltk。

## 最佳实践

- **写清楚标注规范** —— 提供 "什么算 pass / fail / uncertain" 的判定 rubric
- **先标 50 条对齐** —— 团队成员各自标，看分歧，统一标准再放量
- **疲劳是真的** —— 一个人一天 ≤ 100 条
- **多人交叉** —— 重要数据集必须 2+ 人独立标
- **标注人是专家** —— 不要随便找人，业务专家标 vs 路人标差距巨大
- **定期校准** —— 每月跑一次 inter-rater，分歧高的项重新对齐

## 常见问题

<details>
<summary>当前版本支持多人协作吗？</summary>

当前版本：`PATCH /api/observe/data` 接口的 `user_feedback` 字段是单值，每个 Trace 只能存一份反馈。完整多人标注队列在 v2 规划。当前可用替代：用多个 user 账号，每人对自己看到的 Trace 加 user_feedback。
</details>

<details>
<summary>标注结果会影响在线评测吗？</summary>

不会自动影响。当前版本 `user_feedback` 只是字符串字段，没被评估器读取。v2 规划支持：标注作为 ground truth fine-tune LLM-as-Judge 或动态调整评估器参数。
</details>

<details>
<summary>能给标注人不同权限吗？</summary>

当前版本无 RBAC。所有 user 都能编辑自己 user 下的 Trace。需要"标注人只能标不能看到敏感字段"的话，需要先做 PII 脱敏。详见 [PII Masking](../../observability/features/pii-masking)。
</details>
