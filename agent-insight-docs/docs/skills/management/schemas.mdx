# Schema 定义

## 是什么

Schema 是 Skill 的"接口定义"，告诉 Agent 框架（OpenCode / Claude Code）：

- 这个 Skill 叫什么（`name`）
- 什么时候用它（`description`）
- 它能用哪些工具（`allowed-tools`）
- 它依赖哪些参考文档 / 脚本

落到代码里就是 `SKILL.md` 文件顶部的 **YAML frontmatter**。Agent Insight 在 Skill 创建 / 静态合规扫描时会校验这套 Schema，缺字段或类型错都会报 SkillIssue。

## 它解决什么问题

让 Skill 从"自由发挥的文本"变成"机器可读的接口契约"：

| 没 Schema | 有 Schema |
|---|---|
| Agent 不知道何时触发 Skill | `description` 是唯一召回依据 |
| Skill 可能调任何危险工具 | `allowed-tools` 白名单限定 |
| 升级 Skill 跑挂全公司 | Schema 校验在发布前挡掉 |

## SKILL.md 完整 Schema

```yaml
---
# ───── 必填 ─────
name: pdf-extractor                          # kebab-case，必须等于目录名
description: |                               # OpenCode 选 Skill 的唯一依据
  从 PDF 提取关键信息：作者、标题、摘要、关键章节。
  当用户上传 PDF 并问"文档说了什么"、"帮我总结"时使用。

# ───── 可选 ─────
allowed-tools: ["read", "bash"]              # 工具白名单，空数组 = 全禁
arg-spec:                                    # 入参 schema（JSON Schema 子集）
  type: object
  properties:
    file_path: { type: string }
    max_pages: { type: integer, default: 20 }
  required: ["file_path"]

return-spec:                                 # 出参 schema（可选）
  type: object
  properties:
    summary: { type: string }
    sections: { type: array }

references:                                  # 懒加载参考文档
  - path: references/pdf-format-guide.md
    purpose: PDF 格式速查
  - path: references/troubleshooting.md
    purpose: 异常处理

requires:                                    # 依赖的外部 Skill（可选）
  - chart-renderer >= 2.0

semantic-version: v1.2.3                     # 可选，与 SkillVersion.semanticVersion 同
---

# PDF Extractor

详细的执行指令、关键步骤、示例对话...
```

## 字段语义

| 字段 | 类型 | 必填 | 用途 |
|---|---|---|---|
| `name` | string | ✅ | 唯一标识，前端路由 key |
| `description` | string | ✅ | OpenCode 渐进式加载的"诱饵"，决定召回 |
| `allowed-tools` | string[] | ❌ | 工具白名单，空数组 = 禁用所有工具 |
| `arg-spec` | JSON Schema | ❌ | 入参校验 |
| `return-spec` | JSON Schema | ❌ | 出参校验 |
| `references[]` | object[] | ❌ | 参考文档清单，按需懒加载 |
| `requires[]` | string[] | ❌ | 依赖的其他 Skill |
| `semantic-version` | string | ❌ | 语义化版本 |

## 怎么用

### 平台自动校验

每次创建 Skill 或新增版本，平台都会跑 Schema 校验。校验失败会以 `SkillIssue(source='static', severity='high', ruleId='frontmatter_missing_name' / 'description_too_short' / ...)` 形式上报。

详见 [Skills Analysis · 静态合规](../analysis/overview)。

### 通过 UI 看 Schema 错误

进入 **Skills 分析 → 静态合规 → 重新扫描**，所有 frontmatter 错都会列在结果里：

## 常见 Schema 错（按 ruleId）

| ruleId | severity | 修复方法 |
|---|---|---|
| `frontmatter_missing_name` | high | 顶部加 `name: ...` |
| `frontmatter_missing_description` | high | 顶部加 `description: ...` |
| `description_too_short` | high | description ≥ 3 句话，覆盖触发场景 |
| `name_not_kebab_case` | medium | 改成 `kebab-case` |
| `allowed_tools_not_array` | high | 改成数组 `["read", "bash"]` |
| `unknown_field` | low | 删除或挪到正确位置 |
| `arg_spec_invalid_jsonschema` | medium | 按 JSON Schema 子集修 |

## 最佳实践

- **description 用 `|` 多行 YAML 语法**，写 3-5 行说清触发条件
- **`allowed-tools` 不写就是"全开"** —— 强烈建议显式列出，最小化攻击面
- **`references[]` 不要超过 20 个** —— OpenCode 渐进式加载到 references 阶段，太多了体验慢
- **`requires[]` 要写明版本** —— `chart-renderer >= 2.0`，不写版本 = 兼容性灾难

## 常见问题

<details>
<summary>`allowed-tools` 是白名单还是黑名单？</summary>

白名单。**只有列出来的工具能用**。空数组 `[]` = 禁用所有工具。完全省略 = 默认全开（不推荐）。
</details>

<details>
<summary>`arg-spec` 和 `return-spec` 必须填吗？</summary>

不必。但填了能在 A/B 测试 / 评测时自动校验返回值结构，省一次"明明跑通了但格式不对"的扣分项。
</details>

<details>
<summary>Schema 改了，老版本怎么办？</summary>

老版本不受影响。Schema 只在创建 / 更新新版本时校验。但如果 Schema 由 high 变 low（比如 `allowed-tools` 变必填），老版本可能在新规则下失败 —— 这种情况平台不主动 invalidate，需要用户手动重扫。
</details>
