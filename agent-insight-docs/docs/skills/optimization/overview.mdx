# Skills Optimization

## 是什么

Optimization 是 Skills 闭环的"自进化"环节：基于 [Analysis](../analysis/overview) 子模块产出的 `SkillIssue[]` 优化点，自动改写 `SKILL.md`、产出新版本、再丢回去评测，直到达成目标。

底层依靠两个内置 Skill：

- [`skills/skill-optimizer/`](https://github.com/your-org/agent-insight/blob/main/skills/skill-optimizer/SKILL.md) — 单轮原子优化（static / dynamic / feedback / hybrid）
- [`skills/iterative-optimizer/`](https://github.com/your-org/agent-insight/blob/main/skills/iterative-optimizer/SKILL.md) — 自动多轮迭代（"执行 → 评估 → 优化 → 再执行" 循环）

## 它解决什么问题

让"改 Skill" 从"凭经验改" 升级为"按评测数据驱动 + 自动闭环"：

| 没 Optimization | 有 Optimization |
|---|---|
| 看到 SkillIssue 自己一条条改 | 一键选优化点 → LLM 自动改 SKILL.md |
| 改完手动跑 A/B | 多轮自动循环跑评估 + 改 |
| 全量重写容易把好的代码改坏 | 局部修补，只改命中的部分 |
| 没有版本可追溯 | 每次优化产新 SkillVersion 留痕 |

## 4 种原子优化模式

来自 [`docs/optimization-tech.md`](https://github.com/your-org/agent-insight/blob/main/docs/optimization-tech.md) §3.3：

| 模式 | 输入 | 适合场景 |
|---|---|---|
| **`static`** | 5D 评估 + 静态合规结果 | 冷启动修复，没运行数据时 |
| **`dynamic`** | 报错运行轨迹 | Skill 在生产真实跑挂了 |
| **`feedback`** | 用户的明确反馈 | 用户说"description 还要再细一点" |
| **`hybrid`** | static → dynamic 顺序组合 | 用户想"全都要改" |

支持**顺序编排**：Agent 按 `static → dynamic → feedback` 步骤分步执行，每步执行完请求用户确认（继续 / 修改 / 停止），确保 AI 行为完全在用户掌控中。

## 怎么用

### 通过 UI

进入 **Skills 优化** → 选 Skill → 选优化点 → 选模式 → 开始优化：

<!-- TODO 截图：复用 agent-insight/docs/images/skill-optimization.png — Skills 优化页 -->

平台会：

1. 把选中的 SkillIssue 喂给 LLM
2. LLM 按"局部修补"原则改 `SKILL.md`
3. 展示 Before / After diff 让你 Accept / Revise / Revert
4. Accept 后保存为新 SkillVersion

<!-- TODO 截图：复用 agent-insight/docs/images/skill-optimization-result.png — 优化前后 diff 视图 -->

### 通过 REST API

```bash
# 启动单轮原子优化
curl -X POST http://localhost:3000/api/skills/by-name/{name}/optimize \
  -H "x-witty-api-key: $API_KEY" \
  -d '{
    "user": "demo@163.com",
    "mode": "static",
    "issueIds": ["iss_xxx", "iss_yyy"]
  }'
# 响应 → { newVersion, diff, threadId }
```

### 通过 OpenCode 命令

直接在 OpenCode 终端：

```
帮我优化 /user/work/.opencode/skills/pdf-extractor 这个 skill，目标是准确率达到 0.9 以上，最多跑 5 轮
```

`iterative-optimizer` 这个 Skill 自动识别意图，引导你配置后开始迭代。详见 [Auto Optimize](./auto-optimize)。

## 关键设计

### 局部修补（Local Patching）

**不全量重写**：

```
原 SKILL.md (200 行)
    │
    │ 优化器只锁定有问题的代码块
    ▼
diff:
- 第 47 行: rm -rf /tmp/${var}
+ 第 47 行: [ -n "${var}" ] && rm -rf "/tmp/${var}"
```

避免 LLM 幻觉把无问题的代码改坏。

### Snapshot 版本管理

`static` / `dynamic` 产生**主版本**（v1 → v2 → v3）；`feedback` 模式下每轮反馈修改产生**小版本**（v1.1 → v1.2），Accept 后才晋升主版本。

详见 [`docs/optimization-tech.md`](https://github.com/your-org/agent-insight/blob/main/docs/optimization-tech.md) §3.5。

### 交互式确认闭环

每次优化都强制进入 **Review → Accept/Revise** 多轮交互：

```
LLM 改完
    │
    ▼
Diff Viewer 展示 Before/After
    │
    ▼
用户选: Accept (落盘) / Revise (反馈) / Revert (回滚)
    │
    ▼
Accept → 升 SkillVersion
Revise → 用户给反馈，LLM 再改
Revert → 回滚到指定历史版本
```

人在回路（Human-in-the-loop）的质量把控。

## 最佳实践

- **小步快跑** —— 一次只 fix 1-3 个 SkillIssue，diff 易读
- **优先修 high severity** —— 改一个 high 比改 10 个 low 有用
- **每次优化都跑 A/B** —— 自动迭代 ≠ 自动正确，A/B 验证才能上线
- **回滚预案** —— 优化失败 / 改坏了，一键 Revert 到上一版本
- **保留优化历史** —— `SkillVersion.changeLog` 写清楚改了什么、为什么

## 常见问题

<details>
<summary>自动优化能完全无人值守跑吗？</summary>

能，但**强烈不建议生产用**。`iterative-optimizer` 支持完全自动闭环（执行 → 评估 → 优化 → 再执行），但默认每轮都有人工 confirm 点。完全无人值守只适合 sandbox 跑实验。
</details>

<details>
<summary>优化器会改坏吗？</summary>

会。LLM 即使有"局部修补"约束也可能幻觉。所以平台强制 Diff Viewer + Review。永远不要 Accept 没看过的 diff。
</details>

<details>
<summary>优化效果不好怎么办？</summary>

1. 检查 SkillIssue 是否真的可修（`is_skill_attributable=true` 才适合 Skill 层优化）
2. 换更强的模型（Claude Sonnet 4 > DeepSeek > Qwen）
3. 拆 issue —— 一次只 fix 1 个，diff 简单 LLM 不容易跑偏
4. 实在不行回退到 [Generation](../generation/overview) 重写 Skill
</details>
