# From Description

## 是什么

最主流的 Skill 生成入口：**你用自然语言描述要做什么，平台调 LLM 直接产出符合规范的 `SKILL.md`**。这条路径适合 0 → 1 阶段 —— 你心里有需求但还没动手写。

底层用 [`skills/skill-generator/`](https://github.com/your-org/agent-insight/blob/main/skills/skill-generator/SKILL.md) 这个 Skill 自身作为生成器，调度 LLM 跑出来。

## 它解决什么问题

让"写第一个 Skill"的门槛从"读完 spec"降到"会描述需求"：

| 没 Generator | 有 Generator |
|---|---|
| 翻 [agentskills.io](https://agentskills.io/) 学 schema | 直接描述要做什么 |
| 不知道 description 写多详细 | LLM 按场景生成 3-5 句 |
| 手抖把字段写成 `descrption` | 生成器自带 schema 校验 |
| 不会写 `allowed-tools` | 按需求自动建议工具白名单 |

## 怎么用

### 通过 UI

进入 **Skills 生成 → 从描述生成**，在输入框写需求：

<!-- TODO 截图：复用 agent-insight/docs/images/skill-gen.png — Skills 生成对话框（From Description 模式） -->

写需求的好做法：

```
✅ 创建一个 Skill，当用户请求查看系统信息时，自动执行 shell 脚本
   收集当前系统的关键信息（操作系统、CPU、内存、磁盘、网络等），
   以 Markdown 报告呈现给用户。

❌ 系统信息查询
```

生成完成后会在右侧显示完整的 `SKILL.md` 草稿，你可以：
- 直接保存并发布
- 改完再保存
- 继续追问让 LLM 改

### 通过 REST API

```bash
curl -X POST http://localhost:3000/api/skills/generate \
  -H "x-witty-api-key: $API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "mode": "from-description",
    "description": "创建一个 Skill，当用户请求查看系统信息时...",
    "targetCategory": "ops",
    "user": "demo@163.com"
  }'
# 响应 → { name, content (SKILL.md), suggestedScripts, suggestedReferences }
```

### 通过 SDK（即将支持）

```python
from agent_insight import SkillGenerator

gen = SkillGenerator(api_key="ai_xxx")
draft = gen.from_description(
    description="创建一个 Skill，当用户请求查看系统信息时...",
    target_category="ops",
)
print(draft.content)
draft.save()  # 直接落库为 v1
```

## 描述怎么写最有效

按这个模板（来自 [`skills/skill-generator/references/scenarios/general.md`](https://github.com/your-org/agent-insight/blob/main/skills/skill-generator/references/scenarios/general.md)）：

```
【场景】什么时候用这个 Skill？给 3-5 个典型用户输入
【动作】Agent 拿到这些输入后该做什么？步骤清单
【输出】最终要给用户的格式（Markdown 报告 / JSON / 表格 / ...）
【边界】什么场景不要触发？什么场景应该退给主 Agent？
```

例子：

```
【场景】用户说"系统状态"、"检查系统"、"硬件信息"、"性能怎么样"、"显示一下机器情况"
【动作】1) 跑 lscpu/free/df/ip 等 5 个命令；2) 解析结果；3) 排版成 Markdown
【输出】Markdown 报告，含 5 个 H2 段落（CPU/内存/磁盘/网络/总结）
【边界】"修复"、"安装"、"配置变更"类请求不触发，让主 Agent 处理
```

## 关键参数

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `description` | string | ✅ | 自然语言需求，建议 50-300 字 |
| `targetCategory` | string | ❌ | `ops` / `rag` / `coding` / `data` 等场景 tag，影响生成器走哪个场景模块 |
| `referenceDocuments` | string[] | ❌ | PDF / MD / URL，作为额外参考 |
| `modelConfigId` | string | ❌ | 指定生成器用哪个 LLM；不传用 active |

## 最佳实践

- **描述写细但不过细** —— 50-300 字是 sweet spot
- **场景描述给 3-5 个例句** —— LLM 才能生成有覆盖度的 description
- **写明边界条件** —— "不该触发"比"该触发"更重要
- **生成完先 review 再保存** —— LLM 可能会幻觉出多余的 frontmatter 字段
- **第一个版本小一点** —— 复杂 Skill 拆成多个小 Skill 比一个大 Skill 好维护

## 常见问题

<details>
<summary>生成的 description 太啰嗦怎么办？</summary>

继续追问 LLM："description 改成 3 句话以内"。或者直接编辑生成结果，frontmatter 是 YAML 不会破坏整体结构。
</details>

<details>
<summary>生成的 allowed-tools 包含了我不想给的工具？</summary>

LLM 会按需求建议工具列表，但**你最终决定**。直接编辑 `allowed-tools` 数组，删掉不想给的（特别注意 `bash` / `webfetch` 这类高权限工具）。
</details>

<details>
<summary>生成失败怎么办？</summary>

通常是 LLM 输出不符合 schema。重新生成 + 在描述里加一句"请严格按照 frontmatter 规范输出"。如果反复失败，换更强的模型（如 Claude Sonnet 4）。
</details>
