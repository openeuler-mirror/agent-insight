# A/B Testing

## 是什么

A/B Testing 是 Agent Insight 的招牌功能：把同一个 Agent 在「Skill 开 / 关」或「Skill v1 / v2」两种条件下跑同一批用例，按 **能力 / 成本 / 稳定性** 三个 0-100 分维度评分，用**短板原则**给出可执行的发布决策。

底层实现：`GrayscaleTask` 表存配置 + 状态，调度器调用 `runGeneralAgent` 按"样本 × A/B × 轮次"矩阵执行，全部跑完再用同一并发上限触发评估器。

## 它解决什么问题

让"Skill 升级该不该上线"从拍脑袋变成可量化、可解释、可回放：

| 问题 | 没 A/B 时 | 有 A/B 时 |
|---|---|---|
| 加了 Skill 真的有用吗？ | 凭感觉 | **能力分** Δscore × 2.5 |
| 加了 Skill 是不是变贵了？ | 月底看账单才知道 | **成本分** 基于 Δtoken |
| 这版 Skill 跑得稳吗？ | 出问题才发现 | **稳定性分** invokeRate × (1 − var/0.25) |
| 综合该不该上？ | "应该可以吧" | **短板原则** min(三个分)，自动出 direct-release / monitor / reject |

## 怎么用

### 通过 UI

完整三步法：

1. **Step 1 · CONFIG** — 选 A/B 版本、数据集、评估器、重复轮次、并发上限
2. **Step 2 · EXECUTION** — 一键开始，实时看矩阵状态
3. **Step 3 · DECISION** — 自动出三分卡 + 综合判定 + 改进建议

详见 [Step 1](./step1-config) / [Step 2](./step2-execution) / [Step 3](./step3-decision)。

## 关键参数

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `versionAId` | string \| `null` | `null` | A 组（对照），`null` 表示不挂 Skill |
| `versionBId` | string | — | B 组（实验），**必填** |
| `selectedDatasetId` + `selectedCaseIds` | string + string[] | — | 数据集 + 选中的具体用例 |
| `repeatRounds` | int | 1（推荐 3） | 每条用例重复轮次，用于算方差 |
| `agentMaxConcurrency` | int | 5 | Agent 调用并发上限 |
| `evaluatorId` | string | — | 评估器（LLM-as-Judge / Trajectory / Custom） |
| `autoEval` | bool | `true` | 执行完是否自动跑评估器 |
| `recordTriggerDetails` | bool | `false` | 是否记录每次 tool call / skill 触发明细（占空间） |

## 评分算法

### 能力分（Capability）

```
avgEvalA = mean(run.score for run in A)
avgEvalB = mean(run.score for run in B)
Δscore = avgEvalB − avgEvalA              # 评测器百分制下的绝对差
capability_score = clamp(50 + Δscore × 2.5, 0, 100)
```

判定带：≥75 好 / 50–75 一般 / <50 拒绝。

### 成本分（Cost）

以 token 增量为主指标，先映射 base_cost，再按能力分耦合调整：

```
Δtoken = (avgTokensB − avgTokensA) / avgTokensA × 100%

base_cost = piecewise(Δtoken):  # 0%→100, 20%→80, 100%→40, 200%→0
   ≤ 0%        → 100
   ≤ 20%       → 100 − Δtoken × 1.0
   ≤ 100%      → 80  − (Δtoken − 20)  × 0.5
   ≤ 200%      → 40  − (Δtoken − 100) × 0.4
   > 200%      → 0

if cap ≥ 75:    cost = base_cost + 15
elif cap < 50:  cost = base_cost − 20
else:           cost = base_cost
```

判定带：≥70 好 / 40–70 警告 / <40 拒绝。

> "贵但有用" 的 Skill 不会被误杀（cap ≥ 75 加 15 分），"白烧钱" 的 Skill 会被加重惩罚（cap < 50 扣 20）。

### 稳定性分（Stability）

```
invokeRate = (# B runs with skillTriggered=true) / (# B runs)
variance   = mean(per-case variance of B runs' isPassed(0/1))
stability_score = invokeRate × 100 × (1 − variance / 0.25)
```

判定带：≥70 好 / 50–70 警告 / <50 拒绝。

### 综合判定（短板原则）

```
total_score = min(capability_score, cost_score, stability_score)

if N < minSampleSize:        decision = 'insufficient'
elif 任一维度 < 拒绝阈值:     decision = 'reject'  (附 rejectCategory)
elif 三个维度都 ≥ 75:         decision = 'direct-release'
else:                        decision = 'monitor-release'
```

为什么是最低分而不是加权平均？因为三个维度是「且」关系 —— 必须**有用、划算、可靠**才能发布。加权平均会让"能力满分 + 成本翻倍"看起来还行，但实际应该打回。

> 完整算法 + 边界条件见 [`docs/skill-ab-scoring.md`](https://github.com/your-org/agent-insight/blob/main/docs/skill-ab-scoring.md)。算法版本 `agent-skill-scoring-v2.1`。

## 最佳实践

- **重复轮次至少 3 轮**：方差计算需要，否则稳定性分不可信
- **数据集大小 ≥ 5 条**：默认 `minSampleSize=1` 是开发友好值，生产建议 ≥ 5
- **A 组用"无 Skill"做对照**：评估 Skill 加进来到底有没有用，比 v1 vs v2 更基础
- **不要同时改多件事**：A/B 的核心假设是单变量，同时改 Skill + 改 prompt + 换模型 = 无法归因
- **报告留痕**：每次 A/B 都生成完整 `GrayscaleTask.caseStatesJson`，可以回放比较

## 常见问题

<details>
<summary>能力分负数（B 比 A 还差）会怎样？</summary>

`capability_score` 会 clamp 到 0，综合判定走 `reject(能力)`，UI 显示"B 版本性能下降，请按 rejectCategory 修正后复测"。
</details>

<details>
<summary>评估器只能输出 0/1 怎么办？</summary>

向下兼容。0/1 评测器进算法时当 0 分和 100 分代入，`avgEvalA/B` 实际等于"通过率 × 100"。`passRateA/B` 仍作为辅助指标在结果里保留。
</details>

<details>
<summary>样本不够会怎么样？</summary>

`N < minSampleSize` 直接走 `insufficient`，不出综合结论，UI 提示"补到 recommendedSampleSize 后复测"（默认 20）。
</details>

<details>
<summary>耗时为啥不参与判定？</summary>

耗时受网络/并发/负载抖动影响大，不稳定。token 才是相对客观的资源消耗指标。耗时与步数（`avgDurationA/B`、`avgStepsA/B`）作为辅助指标在报告里展示，但不进综合分。
</details>
