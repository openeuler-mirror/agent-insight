# Attribution（归因分析）

## 是什么

多 Agent / 多 Skill 协作时，一次 Trace 跑挂了你能知道"挂了"，但不知道"是哪个 Skill / 哪一步 / 哪个工具" 的责任。Attribution 把模糊的"失败"分解到具体责任主体上：

```
失败 Trace task_xxx
   │
   ▼
Attribution 引擎
   │
   ▼
责任分摊：
- skill: pdf-extractor (60%)
  └─ 在步骤 3 没正确调用 parse_doc.py
- skill: chart-renderer (20%)
  └─ 渲染出错但 main agent 没接住
- tool call: bash (10%)
  └─ 异常 exit code 没被识别
- model (10%)
  └─ 输出包含错误的 JSON
```

## 它解决什么问题

多 Agent 系统是 **"集体责任 = 没人负责"** 的重灾区。Attribution 把它变成"清晰的责任划分"，从而让优化对象明确：

| 没 Attribution | 有 Attribution |
|---|---|
| 失败率高，但每个 Skill 个体看着都没问题 | 数字精确归到具体 Skill |
| 优化谁？谁也不敢动 | 60% 归 pdf-extractor → 先优化它 |
| 团队互相甩锅 | 数据说话 |

## 怎么用

### 通过 UI

A/B 任务跑完 / 评测跑完，进入 **Step 3 · DECISION 下方"归因分析"** 区域：

可以切换三种归因维度：

| 维度 | 切片 | 适合 |
|---|---|---|
| **按 Skill** | 一次 Trace 调用了哪些 Skill，每个 Skill 扣分占比 | 优化 Skill 优先级 |
| **按步骤** | Trace 里每一步的扣分贡献 | 找瓶颈步骤 |
| **按工具** | tool call 失败 / 慢 / 不当使用占比 | 工具白名单 / 调用方式优化 |

### 通过 REST API

```bash
# 单条 Trace 的归因结果
curl "http://localhost:3000/api/observe/executions/{executionId}/attribution?user=demo@163.com" \
  -H "x-witty-api-key: $API_KEY"
# 响应 → {
#   bySkill: [
#     { skill: "pdf-extractor", version: 2, scoreContribution: -0.6, issueCount: 4 },
#     ...
#   ],
#   byStep: [
#     { stepIndex: 3, agent: "pdf-extractor", action: "parse_doc", impact: -0.4 },
#     ...
#   ],
#   byTool: [
#     { tool: "bash", failureCount: 2, impact: -0.1 },
#     ...
#   ]
# }

# 批量归因（A/B 任务级）
curl "http://localhost:3000/api/debug/grayscale-tasks/{taskId}/attribution"
# 响应 → 跨整个任务汇总后的归因表
```

## 归因算法

平台从 `Execution.failures` + `Execution.invokedSkills` + `interactions[].tool_calls` + `Evaluation` 子评估器的输出共同推断责任分摊。详见 PROJECT.md §4.1 的"动态评估优化点的来源（4 大类）"。

```
1. 从 Trace 抽出所有 Skill 调用区间 + 每个步骤
2. 每条 SkillIssue 的 evidence 与具体步骤 / Skill / tool 关联
3. 按 evidence 关联度计算权重
4. 累加到所属责任主体
5. 归一化到 100%
```

每个 SkillIssue 已经携带 `is_skill_attributable` 标志（评估器自判），归因引擎会优先用这个字段做粗粒度归类，再做细粒度分摊。

## 关键参数

| 参数 | 含义 |
|---|---|
| `bySkill` / `byStep` / `byTool` | 三种切片 |
| `scoreContribution` | 该主体对最终扣分的贡献（负数） |
| `issueCount` | 关联的 SkillIssue 数 |
| `impact` | 该步骤对最终扣分的影响（绝对值） |

## 多 Skill 协作的特殊处理

当一次 Trace 同时调用多个 Skill 时（如 `pdf-extractor` 调用 `chart-renderer`），平台会折叠子 Skill 区间 ——

详见 PROJECT.md §6.4.3 `analyze-match` 接口说明：

> 主 Skill 视角下的"委派摘要"会展示子 Skill 的归因，但不按主 Skill 标准逐条匹配。子 Skill 内部步骤标为 `delegated`。

这样既能看到子 Skill 也有责任，又不会把子 Skill 的所有内部步骤都算到主 Skill 头上。

## 最佳实践

- **先看 bySkill 维度** —— 数量级最大的责任主体优先优化
- **同时看 byStep** —— 如果同一 Skill 的扣分集中在 1-2 个步骤，可能是步骤设计问题（不是整 Skill 都要重写）
- **byTool 看异常 tool** —— `bash` exit code 没接住、`webfetch` 超时这类是低 hanging fruit
- **不要只看百分比** —— 60% 责任的 Skill 可能只贡献 -2 分，绝对值小不必紧急修
- **跨 Trace 汇总** —— 单条 Trace 归因看不出系统性问题，任务级汇总才能看趋势

## 常见问题

<details>
<summary>如果归因显示"模型问题"占比很高，怎么办？</summary>

这时候改 Skill 用处不大，考虑：
1. 换更强模型（[Model Swap](../optimization/model-swap)）
2. 接受现实（某些任务确实超出模型能力，需要业务降级）
3. 拆 Skill 让简单部分用便宜模型，复杂部分独立调强模型
</details>

<details>
<summary>归因结果会不会有偏差？</summary>

会。归因引擎依赖评估器的 `is_skill_attributable` 标志，评估器误判会传到归因。建议跨多条 Trace 看汇总，单条不可信。
</details>

<details>
<summary>能自定义归因维度吗？</summary>

当前只支持 Skill / 步骤 / 工具 / 模型 4 个维度。自定义（如按 user / 按时间段）在 v2 规划。
</details>
