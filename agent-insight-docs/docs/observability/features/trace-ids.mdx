# Trace IDs & Distributed Tracing

## 是什么

Agent Insight 用 `taskId` 作为平台内的 trace 主键，同时兼容 OpenTelemetry `trace_id` / `span_id` 体系。**它解决"我的 Trace 怎么跨服务串起来"**：

```
浏览器请求  → Web Server (trace_id=A) → LLM Agent (taskId=B) → 子 Agent (taskId=B-sub)
              │                          │                       │
              └─ OTel trace_id=A         └─ Agent Insight taskId=B
                                         │
                                         └─ trace_id=A 透传，关联两套体系
```

## 它解决什么问题

实际系统不只有 Agent Insight。完整观测栈通常：

- 入口层用 Datadog / Grafana / OTel collector
- Agent 层用 Agent Insight
- 数据库层用 SQL slow log

如果各家用各家的 ID，**出问题没法串**。Trace IDs 让 Agent Insight 与外部观测体系对齐：

| 没 trace ID 关联 | 有关联 |
|---|---|
| 用户报"刚才慢" → 翻 5 个系统 | 一个 trace_id 串到底 |
| Agent 出错 → 不知道上游怎么调过来的 | 看上游 span 上下文 |
| 调度系统看不到 Agent 内部 | OTel 数据双写 |

## 怎么用

### Agent Insight 原生：taskId

最简单的用法 —— 客户端生成 UUID 当 taskId：

```python
from agent_insight import AgentInsight
import uuid

task_id = str(uuid.uuid4())
AgentInsight.init(api_key="ai_xxx", task_id=task_id)
```

```typescript
import { AgentInsight } from "@agent-insight/sdk";
import { randomUUID } from "crypto";

const taskId = randomUUID();
AgentInsight.init({ apiKey: "ai_xxx", taskId });
```

### 兼容 OpenTelemetry

把 OTel `traceparent` header 透传给 Agent Insight，平台会把 `trace_id` 字段写进 `Session.metadata.otel_trace_id`，可以反查：

```python
from opentelemetry.trace import get_current_span

span = get_current_span()
ctx = span.get_span_context()

AgentInsight.init(
    api_key="ai_xxx",
    task_id=str(ctx.trace_id),  # 16-byte hex
    metadata={
        "otel_trace_id": format(ctx.trace_id, "032x"),
        "otel_span_id": format(ctx.span_id, "016x"),
        "otel_traceparent": f"00-{ctx.trace_id:032x}-{ctx.span_id:016x}-01",
    },
)
```

或者更简单，直接把现成 OTel 数据通过 OTLP HTTP 推过来：

```bash
# OTLP endpoint 接收 traces
POST http://localhost:3000/api/ingest/otel/v1/traces
Content-Type: application/json
Header: x-witty-api-key: ai_xxx
```

详见 [SDK · OpenTelemetry](../sdk/opentelemetry)。

### 跨服务传递（distributed）

子 Agent / 子服务调用时把 `taskId` 当 parent 透传：

```python
# 父 Agent
parent_task_id = "task_parent_xxx"
AgentInsight.init(api_key="ai_xxx", task_id=parent_task_id)

# 调子 Agent（HTTP / gRPC / queue）
http_post("https://subagent.example.com/run", headers={
    "X-Agent-Insight-Parent-Task-Id": parent_task_id,
})
```

子 Agent 端：

```python
import os
from agent_insight import AgentInsight

parent_id = os.environ.get("HTTP_X_AGENT_INSIGHT_PARENT_TASK_ID")
sub_task_id = f"{parent_id}-sub-{uuid4()}"

AgentInsight.init(
    api_key="ai_xxx",
    task_id=sub_task_id,
    parent_task_id=parent_id,  # 平台自动建立父子关系
)
```

## 关键参数

| 字段 | 类型 | 说明 |
|---|---|---|
| `task_id` | string | 平台主键，跨服务时建议含父子前缀 |
| `parent_task_id` | string | 上游 Trace ID（建立调用树） |
| `metadata.otel_trace_id` | string | OTel `trace_id` (32 hex char) |
| `metadata.otel_span_id` | string | OTel `span_id` (16 hex char) |
| `interaction.subagent_session_id` | string | 子 Agent 的 sessionId（自动从 tool_calls 推断） |

## 命名约定

| 约定 | 例子 |
|---|---|
| 父 taskId：UUID 或业务 ID | `task_user_session_abc123` |
| 子 taskId：父 + 后缀 | `task_user_session_abc123-sub-xyz` |
| 与 OTel：`task_<otel_trace_id>` | `task_4bf92f3577b34da6a3ce929d0e0e4736` |

## 最佳实践

- **客户端就生成稳定 ID** —— 服务端补 ID 容易丢上下文
- **HTTP header 命名带 `X-Agent-Insight-` 前缀** —— 避免和别的系统撞
- **OTel 互通时整套迁移** —— 不要部分服务用 OTel ID、部分用自定义，会断链
- **跨服务一定要透传 user / environment** —— 不只是 trace_id

## 常见问题

<details>
<summary>同一个 trace_id 调多次能合并 Session 吗？</summary>

`taskId` 是 unique 主键，同 `taskId` 第二次上报会**追加到同一 Session 的 interactions[]**，不是新建。这正是多轮对话的归并机制。
</details>

<details>
<summary>OTel span_id 怎么映射到 interaction？</summary>

平台没有 1:1 字段，但 OTel span 会被解析成 `interaction[i]`，每个 interaction 的 `metadata.otel_span_id` 字段保留原 span_id，便于反查。
</details>

<details>
<summary>分布式 Agent 调用层级超过 3 层会乱吗？</summary>

不会。`parent_task_id` 是字符串字段不嵌套，可以多层嵌套（孙子的 parent 是儿子的 taskId）。但建议用前缀命名避免可读性问题。
</details>
