# 延迟分析

## 是什么

把 Trace 的端到端耗时分解到每一步（每次 LLM 调用、每个 tool call、子 Agent handoff），让你定位"为啥这么慢"。平台同时提供 P50 / P95 / P99 统计 + 单 Trace 瀑布图视图。

底层字段：`Execution.latency`（端到端，ms）+ `interaction.timeInfo`（单步 `{start, end, duration_ms}`）。

## 它解决什么问题

LLM Agent 的延迟敏感场景越来越多（C 端对话 / 实时辅助 / 智能客服）。慢一倍 = 用户流失：

| 没延迟分析 | 有延迟分析 |
|---|---|
| 用户说"慢" → 不知道哪步慢 | 瀑布图一眼看到瓶颈步骤 |
| 不知道 P95 是多少 | 实时 P95 KPI |
| 优化没数据支撑 | 优化前后 P95 直接对比 |
| 失败的慢与成功的慢不分 | 按 success/failure 分桶 |

## 怎么用

**链路观测顶部 KPI 卡**：平均耗时 / P95（最慢 5% 的尾延迟）。

**评估器 / 指标页**：跨 Trace 的延迟直方图、按 Skill / 模型 / framework 分桶。

### 通过 SDK

```python
from agent_insight import AgentInsight

stats = AgentInsight.get_task_stats(task_id)
# → { latency: 4500, model, tokens, ... }
```

### 通过 REST API

```bash
# 单 Trace 延迟
curl "http://localhost:3000/api/observe/task-stats?taskId=task_xxx"
# → { latency: 4500 }

# 全局延迟分布（v2 规划，当前手动聚合）
curl "http://localhost:3000/api/observe/data?user=demo@163.com" \
  | jq '[.[] | .latency] | sort'
```

## 关键参数

| 字段 | 含义 |
|---|---|
| `Execution.latency` | 端到端耗时（ms） |
| `interaction.timeInfo.start/end` | 单步起止时间戳 |
| `interaction.timeInfo.duration_ms` | 单步耗时 |
| `interaction.timeInfo.queued_ms` | 排队等待时间（v2 规划） |

## 延迟分解模型

```
Total Latency (Execution.latency)
   │
   ├── LLM 调用 (Anthropic / OpenAI / ...)
   │     ├── network RTT
   │     ├── LLM 队列等待（provider 侧）
   │     ├── 推理时间（含 reasoning tokens）
   │     └── 流式 first-token vs full-response
   │
   ├── Tool call
   │     ├── 工具执行（bash / read / webfetch）
   │     ├── shell 启动开销（bash 特别）
   │     └── 数据读写 IO
   │
   ├── 子 Agent handoff
   │     ├── 网络（跨进程 / 跨主机）
   │     └── 子 Agent 自己的总耗时
   │
   └── 平台开销（采集 / 上报）
         ├── interaction 序列化
         └── 异步上报（不阻塞主链路）
```

## 最佳实践

- **看 P95 而不是平均** —— 平均被 happy path 拉低，P95 反映真实"最坏 5%"
- **拆 LLM vs tool vs network** —— 优化重点不同：LLM 慢换模型 / tool 慢优化 script / network 慢加 cache
- **关注 first-token latency** —— 对话场景"开始流式输出"比"完全输出完"重要得多
- **prompt caching 对 latency 帮助大** —— Anthropic prompt caching 命中可降 80% latency
- **timeInfo.queued_ms 暴露 LLM provider 限流** —— 突然飙升可能是 rate limit

## 常见问题

<details>
<summary>延迟和 token 关系大吗？</summary>

正相关但不严格线性。output tokens 大概对应"每秒 50-100 token"的输出速度（不同模型不同），prompt tokens 大对 prefill 阶段有影响但远不如 output 显著。所以**输出长度是最大的延迟因素**。
</details>

<details>
<summary>为什么 latency 比所有 interaction 耗时加起来还大？</summary>

`Execution.latency` 是端到端（含采集、上报、跨服务网络）；`interaction.timeInfo` 只算 Agent / LLM / tool 本身。差值通常是采集开销 + 网络。
</details>

<details>
<summary>能按 latency 排序找最慢的 Trace 吗？</summary>

UI 当前按时间倒序，按 latency 排序在 v2 规划。当前替代：API 拉数据自己排：

```bash
curl "/api/observe/data?user=demo" | jq 'sort_by(-.latency) | .[:10]'
```
</details>
