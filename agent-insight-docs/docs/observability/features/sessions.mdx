# Sessions

## 是什么

`Session` 是 Agent Insight 的会话载体。一次 OpenCode / Claude Code 启动后的完整对话被建模成一个 `Session`（`taskId` 唯一），里面装着按时间排序的 `interactions[]`。多轮用户输入也归到同一 `Session`，方便看完整上下文。

> 注意：`Session` 与 `Execution` 是 1:1 关系（同 `taskId`），但视角不同 —— Session 是"原始数据"，Execution 是"评测视角的统计快照"。详见 [Data Model](../data-model)。

## 它解决什么问题

Agent 多轮对话场景特别多：

- 用户先问 A，Agent 回答；再追问 B，Agent 接着前文回答
- 长时间多轮 debugging（来回 10+ 轮）
- 工具调用失败后用户给提示让 Agent 重试

如果每一轮都是独立 Trace，**上下文丢了，看不懂为啥这一轮这么答**。Session 把这些串起来，让你看到完整对话脉络。

## 怎么用

### 通过 UI

链路观测列表每行就是一个 Session（按 `taskId` 一行）。点击行打开 Drawer 后能看到所有轮次的 user / assistant / tool calls 按时间排列。

### 通过 SDK

```python
from agent_insight import AgentInsight

# 显式指定 taskId（多轮对话共用同一 taskId）
AgentInsight.init(api_key="ai_xxx", task_id="task_user_session_xxx")

# 多轮调用，平台自动归到同一 Session
agent_response = my_agent(user_query_1)
agent_response_2 = my_agent(user_query_2)
```

```typescript
import { AgentInsight } from "@agent-insight/sdk";

AgentInsight.init({
  apiKey: "ai_xxx",
  taskId: "task_user_session_xxx",
});
```

### 通过 REST API

```bash
# 拉取单个 Session 的所有 interaction
curl "http://localhost:3000/api/observe/session?taskId=task_xxx" \
  -H "x-witty-api-key: $API_KEY"

# 列出某用户的全部 Session
curl "http://localhost:3000/api/observe/data?user=demo@163.com" \
  -H "x-witty-api-key: $API_KEY"
```

## 关键参数

| 字段 | 含义 |
|---|---|
| `taskId` | 全局唯一 ID（OpenCode session id / 自定义 UUID） |
| `label` | 业务标签 |
| `query` | 初始用户输入 |
| `interactions[]` | 按时间序排列的所有 interaction（多轮都在这里） |
| `startTime` | 第一次 interaction 的时间 |
| `model` | 主 Agent 使用的 LLM |

## 多轮的实现

每轮新输入都追加到 `Session.interactions[]`，平台按 `role: 'user'` 的边界识别"轮次"：

```
Session(taskId=task_xxx)
├── interaction[0] role=user, query="先帮我看 cpu"
├── interaction[1] role=assistant, ... tool_calls=[lscpu]
├── interaction[2] role=tool, ... lscpu 输出
├── interaction[3] role=assistant, answer
│
├── interaction[4] role=user, query="那内存呢？"  ← 第二轮开始
├── interaction[5] role=assistant, ... tool_calls=[free]
└── ...
```

## 最佳实践

- **OpenCode 用户：taskId 用 OpenCode session id**：平台采集端自动透传，多轮自动归组
- **自研 Agent：客户端持久化 taskId**：把它存在 session storage 里，每轮 init 时传入
- **不要每轮换 taskId**：会失去上下文关联
- **`label` 字段标注业务场景**：如 `"客服-投诉"`，便于过滤
- **超长 Session 分段**：超过 100 轮会让 UI 加载慢，考虑按业务自然边界拆 session

## 常见问题

<details>
<summary>同一 taskId 重复上报会怎样？</summary>

平台用 `taskId` 唯一约束，重复上报会合并 `interactions[]`。同 `taskId` 不会创建新 Session，只追加。
</details>

<details>
<summary>能搜索 Session 内容吗？</summary>

可以走 `GET /api/observe/data?query=xxx` 按 `query` 字段模糊搜索。全文搜索 `interactions[]` 内部内容在 v2 规划（接 ClickHouse 后）。
</details>

<details>
<summary>多用户共享同一 taskId 会怎样？</summary>

`taskId` 是全局唯一，跨 user 撞了会拒绝写入（409 Conflict）。建议在客户端用 UUIDv4 起名，避免猜测式 ID（如 `session_1`）。
</details>
