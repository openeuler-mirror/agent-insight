# 采样（Sampling）

## 是什么

高 QPS 场景下，把"上报 100% Trace"改为"上报一部分 + 关键的全部"。Agent Insight 支持三种采样策略：

| 策略 | 含义 | 适合 |
|---|---|---|
| **头采样** (Head sampling) | 客户端按概率丢弃 | 削峰 |
| **尾采样** (Tail sampling) | 服务端跑完再决定保留 | 保留所有失败/慢 Trace |
| **关键路径全采** | 关键业务全保留 | 客服 / 金融 / 医疗 |

底层实现：客户端 SDK 的 sampling rate + 服务端 [`src/lib/ingest/upload-throttle.ts`](https://github.com/your-org/agent-insight/blob/main/src/lib/ingest/upload-throttle.ts)。

## 它解决什么问题

高流量场景一天上百万次 Agent 调用，全采的代价：

- 存储成本（Trace JSON 累积）
- LLM 评估器成本（每条都跑 LLM-as-Judge 烧死）
- 平台性能压力

但又不能完全不采（出 bug 时找不到 Trace）。采样是平衡。

## 怎么用

### 客户端头采样

```python
from agent_insight import AgentInsight

AgentInsight.init(
    api_key="ai_xxx",
    sampling_rate=0.1,      # 只上报 10% 的 Trace
    always_sample_on_error=True,  # 但失败的全报
)
```

```typescript
AgentInsight.init({
  apiKey: "ai_xxx",
  samplingRate: 0.1,
  alwaysSampleOnError: true,
});
```

### 服务端尾采样

平台默认对所有上报数据保留。但可以配 [`upload-throttle.ts`](https://github.com/your-org/agent-insight/blob/main/src/lib/ingest/upload-throttle.ts) 让平台只保留：

- 所有 `isAnswerCorrect=false` 的（失败）
- 所有 `latency > 5000ms` 的（慢）
- 随机抽 10% 的成功 Trace

服务端尾采样优势：客户端**全上报**，平台决定保留谁。能保证"所有失败都留着"，不像头采样可能漏。

### 关键路径全采

业务关键场景永远全采：

```python
AgentInsight.init(api_key="ai_xxx", sampling_rate=0.1)

@observe()
def my_agent(query: str, scenario: str) -> str:
    if scenario in ["refund", "complaint", "fraud"]:
        AgentInsight.force_sample()  # 这条强制全采
    return answer
```

## 关键参数

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `sampling_rate` | float (0-1) | 1.0 | 头采样比例 |
| `always_sample_on_error` | bool | true | 失败时强制采（覆盖 sampling_rate） |
| `force_sample()` | runtime | — | 调用后该 Trace 100% 采 |
| `min_latency_ms_to_sample` | int | 0 | 超过此延迟的全采（v2 规划） |

## 不同 QPS 场景的推荐采样率

| QPS | 推荐 sampling_rate | 理由 |
|---|---|---|
| < 1 (调试 / 内部) | 1.0 | 全采 |
| 1-10 (小流量生产) | 1.0 | 全采 |
| 10-100 (中等) | 0.5 | 一半 |
| 100-1000 (大流量) | 0.1 | 10% |
| 1000+ (超大) | 0.05 + 关键路径全采 | 5% |

无论采样率多低，**关键路径必须全采** —— 客服 / 金融 / 医疗这种场景出错谁负责？

## 最佳实践

- **永远 always_sample_on_error=true** —— 失败的 Trace 是最有价值的
- **关键路径 force_sample** —— 业务上一定要能复盘的，sampling 不要碰
- **采样率别拍脑袋** —— 先全采几小时看真实 QPS，再决定
- **观察成本曲线** —— 采样从 1.0 → 0.5 → 0.1 的存储 / LLM 成本变化
- **服务端尾采样 > 客户端头采样** —— 当 SDK 不支持头采时退而求其次

## 常见问题

<details>
<summary>采样后评测怎么办？</summary>

评估器只对**采样后**的 Trace 跑。如果你的评测要求很高的"代表性"，建议：
1. 把 sampling_rate 提高
2. 或者用 force_sample 把评测对象全采
3. 离线评测时另开数据集（用 [Datasets](../../evaluation/features/datasets) 自定义评测集）
</details>

<details>
<summary>A/B 测试场景能采样吗？</summary>

**不能**。A/B 测试需要严格统计，采样会引入偏差。`GrayscaleTask` 跑出来的所有 Trace 全采，不受 sampling 影响。
</details>

<details>
<summary>采样后 SkillIssue 还准吗？</summary>

会少一些样本。`prevalenceCount` 计数会缩小，但 dedupKey 聚合逻辑不变。可以适当降低 prevalence 抬升阈值（默认 3/5/10，可改成 2/3/5）补偿。
</details>
