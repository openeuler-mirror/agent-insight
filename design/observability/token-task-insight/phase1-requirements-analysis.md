# Token 与任务分析：需求分析

状态：按 issue #375 描述整理；不引入数据模型变更。

## 背景

平台已经按 Trace 保存了 root execution 的 token、耗时、工具/LLM 调用次数和 query，但缺少一个面向成本与调度的汇总视图。用户只能在链路列表里逐条查看，无法快速回答：

- Token 花在哪些任务、用户和会话上？
- 用户实际用 Agent 做了哪些类型的工作？
- 哪些任务属于长时任务，哪些可以在夜间低峰执行？

## 目标

1. 按任务、用户、会话拆解 token 与估算成本。
2. 把 Agent 使用行为归为问答、文本处理、文档分析、代码、批处理、多步工具任务等类型。
3. 综合耗时、token、工具调用次数、LLM 调用次数识别长时任务。
4. 识别可延后的长时任务，给出夜间执行建议与可释放的日间耗时。
5. 保留短任务实时执行的默认路径，不改变现有执行链路。

## 非目标

- 不实现任务排队、异步执行或通知能力（本需求只提供分析依据）。
- 不修改 Agent 执行、调度或模型路由逻辑。
- 不新增 Prisma 表：全部指标从既有 `Execution` 字段派生。
- 不做基于 LLM 的语义分类；首版使用可解释、可测试的规则分类。

## 口径与约束

- 只统计 `isSubagent=false` 的 root trace，避免子 agent 行重复计数；root 行 token 已包含子 agent。
- 耗时使用 `Execution.latency`（毫秒，全链路统一口径）。
- Token 优先取 `inputTokens + outputTokens`；两者都为 0 时回退 `tokens`。
- 成本按模型单价估算，未配置单价的模型按 0 计并显式提示。
- 时段统计固定使用 `Asia/Shanghai`，避免服务端时区漂移。
- 单次最多分析最近 10,000 条 root trace；超出时明确标注截断。

## 验收要点

- 六类任务都有可复现的规则样例。
- 长时判定能分别命中耗时、token、工具调用、LLM 调用四个维度。
- 显式实时要求（如“立即”“今天必须”）的长任务不计入可延后。
- 汇总结果包含任务类型、长短时、用户、时段和可延后任务明细。
- 空数据、截断、模型单价缺失都有诚实提示。
