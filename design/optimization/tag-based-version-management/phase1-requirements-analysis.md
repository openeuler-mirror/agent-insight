# 标签化版本管理与版本分析 — 需求分析

> 文档类型：Phase1 需求分析 ｜ 关联项目：agent-insight
> 输入来源：`docs1/biaoqian.html`
> 创建时间：2026-07-06
> 状态：设计讨论稿，已根据需求对齐意见更新

## 导读

这个需求的核心不是“给 Trace 多加几个彩色标签”，而是用一套标签体系把三件事串起来：

- **版本管理**：在配置区维护可复用的“版本标签”和“业务标签”。
- **链路追踪**：在 Trace 列表给 Trace 打用户标签；业务标签用于筛选 Trace；系统标签只读展示。
- **版本分析**：只消费“版本标签”，把不同迭代版本下的 Trace 聚合成对比和详情视图。

边界也很明确：这是已有 Trace 明细的指标汇总，不做模型分析，不新增 LLM 判断链路；准确率沿用已落库的 `Execution.answerScore`。当前系统没有独立的 `successRate` 存储字段，若后续页面保留“成功率”，只能从 Trace 运行状态派生，且需要和“准确率”明确区分。

## §1 背景与问题

当前观测数据已经有 `Execution` 级指标，例如 `tokens`、`cost`、`latency`、`answerScore`、`framework`、`agentName` 等，但缺少一套面向“实验版本”和“业务筛选”的结构化标签能力。

这带来三个问题：

| 问题 | 影响 |
|-|-|
| 版本语义缺少独立建模 | 想比较 `baseline`、`v1.3`、`v1.4` 这类运行版本时，只能依赖人工记忆或临时筛选，无法稳定复用 |
| 业务属性与版本属性混在一起 | “回归测试 / P0 / 线上复现”适合做 Trace 筛选，但不应该参与版本分析 |
| 系统派生信息与人工标签缺少边界 | Multi-Agent、Skills、SUB、框架名等系统事实应只读展示，不应被用户编辑 |

因此，本需求引入三类标签，并围绕它们补齐管理、打标、筛选和版本聚合分析。

## §2 目标

| 编号 | 目标 |
|-|-|
| G-001 | 建立统一标签体系：系统标签、版本标签、业务标签三类语义清晰分离 |
| G-002 | 支持用户在 Trace 列表对 Trace 增删版本标签和业务标签 |
| G-003 | 支持链路追踪按版本标签和业务标签混合多选筛选，并支持列显隐配置 |
| G-004 | 支持版本分析页按版本标签聚合 Trace，展示跨版本对比与单版本详情 |
| G-005 | 指标全部来自已有 Trace 明细与评测结果，不调用 LLM 生成结论 |
| G-006 | 设计应兼容现有 `Execution` 数据与 Trace 页面，不破坏现有 `label` 字段语义 |

## §3 标签体系

| 标签类型 | 来源 | 是否可编辑 | 用途 | 管理/使用位置 |
|-|-|-|-|-|
| 系统标签 | 由 Trace 数据自动派生，例如 Multi-Agent、Skills、SUB、框架名 | 否 | 帮用户快速识别 Trace 结构和来源 | 链路追踪列表，可配置列显隐，默认隐藏 |
| 版本标签 | 用户创建，例如 `baseline`、`v1.4`、`exp-cot` | 是 | 标记一次迭代、实验或发布版本，作为版本分析聚合维度 | 版本管理创建；链路追踪打标；版本分析消费 |
| 业务标签 | 用户创建，例如“回归测试”“P0 核心”“线上复现” | 是 | 标记业务属性，用于筛选 Trace | 版本管理创建；链路追踪筛选和打标 |

系统标签不进入用户标签表，不参与版本分析。版本标签和业务标签统称“用户标签”。

## §4 需求范围

### 4.1 功能性需求

| 编号 | 需求 | 优先级 |
|-|-|-|
| FR-001 | 新增“版本管理”页面，支持版本标签和业务标签的新增、编辑、删除、列表展示 | P0 |
| FR-002 | 标签字段包含类型、名称、描述、颜色、创建人、创建时间 | P0 |
| FR-003 | 链路追踪列表展示用户标签列，包含版本标签和业务标签 | P0 |
| FR-004 | 链路追踪支持给 Trace 添加和移除用户标签 | P0 |
| FR-005 | 链路追踪支持版本标签和业务标签混合多选筛选；多个标签使用 AND 语义，并按类型和名称前缀聚类展示 | P0 |
| FR-006 | 链路追踪支持系统标签列，系统标签只读且默认隐藏 | P1 |
| FR-007 | 链路追踪支持列显隐配置，用户标签列默认展示 | P1 |
| FR-008 | 新增“版本分析”页，支持版本对比：横轴为版本标签，按标签名字符串排序 | P0 |
| FR-009 | 版本对比支持全部问题聚合和单问题下钻 | P1 |
| FR-010 | 版本分析支持版本详情：选择一个版本标签，查看该版本下 Trace 趋势、覆盖问题与 Trace 明细 | P0 |
| FR-011 | 版本分析支持 Agent、时间窗口等基础上下文筛选 | P1 |
| FR-012 | 版本分析支持导出当前聚合数据 | P2 |

### 4.2 非功能性需求

| 编号 | 需求 | 优先级 |
|-|-|-|
| NFR-001 | 不新增 LLM 调用；版本分析只做信息汇总和指标聚合 | P0 |
| NFR-002 | 用户隔离：标签定义和 Trace 绑定必须按当前用户隔离 | P0 |
| NFR-003 | 性能：用户标签筛选和版本聚合应可被数据库索引支持，避免全量 JSON 扫描 | P0 |
| NFR-004 | 兼容性：现有 `Execution.label` 字段不迁移、不复用为新标签体系的唯一来源 | P0 |
| NFR-005 | 可解释性：准确率、Token、时延、成本、成功率的口径必须在页面或文档中固定 | P1 |
| NFR-006 | 空样本或低样本版本必须显式降级展示，不能给出误导性对比 | P1 |

## §5 明确不做

| 范围外事项 | 原因 |
|-|-|
| 不做模型分析或自动结论生成 | 高保真明确为信息汇总，不含模型分析 |
| 不把业务标签纳入版本分析 | 业务标签用于 Trace 筛选，版本分析只看版本标签 |
| 不让用户编辑系统标签 | 系统标签是由 Trace 数据派生的事实 |
| 不自动回填历史 Trace 的版本标签 | 历史打标策略需要额外规则，本需求先提供人工打标能力 |
| 不替代 Skill 自身版本体系 | 这里的版本标签是 Trace cohort 版本，不是 `SkillVersion` |
| MVP 不在版本分析内支持业务标签过滤 | 版本分析先只按版本标签聚合；“只看某业务标签内的版本对比”记录为未来潜在优化点 |
| 不实现 CI 质量门禁或发布阻断 | 可作为后续演进，当前只做分析视图 |

## §6 指标口径

| 指标 | 口径 |
|-|-|
| Trace 数 | 命中版本标签且满足筛选条件的 root Trace 数；默认不把 sub-agent Execution 当作独立样本 |
| 准确率 | `Execution.answerScore` 的均值；空值不参与均值，并展示覆盖率 |
| 成功率 | 当前没有独立存储字段；MVP 不把它作为质量指标主口径。若页面保留该列，应按 Trace 运行状态派生“运行成功率”，例如成功终态 Trace 数 / 终态 Trace 数，并展示运行中/未知样本数量 |
| Token | 优先使用 `Execution.tokens`；缺失时可用 `inputTokens + outputTokens` 兜底 |
| p95 时延 | `Execution.latency` 的 p95，单位按当前 DB 口径统一为秒展示 |
| 成本 | 优先使用 `Execution.cost`；如后续统一单价重算，则由聚合服务统一封装 |

## §7 验收准则

| 编号 | 通过标准 |
|-|-|
| AC-001 | 用户可以创建、编辑、删除版本标签和业务标签，列表按类型分区展示 |
| AC-002 | Trace 列表可以给一条 Trace 添加/移除版本标签和业务标签，刷新后绑定仍存在 |
| AC-003 | 版本标签与业务标签可以混合多选；筛选时只返回同时绑定全部所选标签的 Trace |
| AC-004 | 系统标签在 Trace 列表只读展示，默认隐藏，用户不能编辑 |
| AC-005 | 版本分析只统计版本标签，业务标签不会进入版本横轴 |
| AC-006 | 版本对比横轴按版本标签名称字符串排序，不按创建时间排序 |
| AC-007 | 版本详情中的 Trace 明细可跳转回对应 Trace 详情 |
| AC-008 | 无 `answerScore` 的 Trace 不污染准确率均值，并展示样本/覆盖提示 |
| AC-009 | 删除标签后，相关 Trace 绑定一起清理或失效，不出现孤儿标签展示 |
| AC-010 | `npm run test` 与类型检查通过；UI 验证需在用户确认后启动 dev server |

## §8 已对齐决策与后续优化

| 编号 | 结论 | 说明 |
|-|-|-|
| C-001 | 一条 Trace 允许多个用户标签，也允许多个版本标签 | 数据层保持多对多；版本分析时同一 Trace 会进入其绑定的每个版本标签聚合 |
| C-002 | 标签删除采用硬删除 | 删除 `Tag` 时级联删除 `ExecutionTag` 绑定；Trace 本体不删除 |
| C-003 | Trace ↔ Tag 绑定使用关系表作为主存储 | API 返回可计算出高保真里的 `testTags` 形状；不把 JSON 作为筛选和聚合主路径 |
| C-004 | 单问题下钻按归一化后的 `Execution.query` 分组 | 后续如接入评测数据集，可升级为 dataset item id / evaluation case id |
| C-005 | 版本分析只统计 root Execution | `isSubagent=false` 为默认且固定的 MVP 口径 |
| C-006 | 路由使用 observe 语义下的 version-analysis 命名 | 避免与 Skill 自身版本体系混淆 |
| F-001 | 版本分析内按业务标签二次过滤暂不做 | 记录为未来潜在优化点，例如“只看 P0/回归测试 Trace 内的版本对比” |
| F-002 | 成功率指标暂不作为已存在数据源处理 | 当前无 `successRate` 字段；如后续保留，需先确认 trace 状态失败口径是否可靠 |
