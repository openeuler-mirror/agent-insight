# 数据库与项目分离部署 · 设计

## 服务与网络

| 服务 | 网络入口（示例容器端口） | 自己持有的数据 |
|---|---|---|
| 项目 | Web 3000。容器内 Web 通过回环 4319 调用 Python Storage Core | Web 运行根、控制器密钥、初始化记录及制品 |
| PostgreSQL | PostgreSQL 协议 5432 | PostgreSQL 卷 |
| openGauss | 数据库协议 5432，按所选镜像配置 | openGauss 卷 |
| SQLite 服务 | 拟定服务端口 8080，提供认证和事务会话 | SQLite 数据库、日志及备份所需文件 |
| ClickHouse | HTTP 8123；外部 HTTPS 按实际端口 | ClickHouse 卷 |

四个数据库模板与一个项目模板见[操作指南](guide.md)。同一部署实例使用固定的 Compose 项目名，分次启动仍能使用同一默认网络、固定服务名和命名卷。用户已有外部数据库时，项目文件可独立使用，不引用数据库服务的 `depends_on`。不同机器使用可路由地址、发布端口与 TLS；本机样例只将端口发布到回环地址。

## 启动契约

1. 拟议入口 `deploy-docker.sh up [--transaction postgresql|opengauss|sqlite]`。首次省略类型取 PostgreSQL。将实例名、后端、目标端口和版本记录在独立部署目录，原子生成权限 0600 的凭据及项目配置。重复执行复用记录；已有其他后端的实例绝不因省略参数而切到 PostgreSQL。显式切换已有实例的后端需要另建实例或走迁移。
2. 入口组合 ClickHouse、所选事务库和项目三份模板，先启动两库，限时等待可认证的数据库查询成功，然后启动项目。容器应用同样完成独立预检，可以直接对接外部库。首次初始化仅在受控的空目标上运行现有版本化建表。普通重启验证身份、版本和结构。双库状态不匹配、旧库或遗失配置但已有卷时停止，输出恢复指引。
3. 项目镜像包含 Node、Python、数据库驱动及 Web 控制网关。前台监督进程持有实例锁，先启动 Core，待其报告两库就绪再启动 Web/WSS 网关。任一子进程意外退出时终止另一进程并以失败状态结束；接到停止信号时先排空 Web、再停止 Core、回收子进程。项目健康探针同时检查 Web 与 Core。配置错误要返回非零退出码，启动入口输出首个可操作原因；避免无限重试掩盖错误。
4. 应用单独启动和源码安装都要求显式提供一种事务库以及 ClickHouse。首次连接失败按目标库区分 DNS/端口、凭据、TLS、权限与版本，输出配置路径和字段名，屏蔽密码、令牌和完整 DSN。源代码路径不依赖 Docker CLI、socket 或系统服务探测。Web 不执行数据库结构同步。

## 文件与连接配置

两种应用入口共用现有 JSON 的 `control`、`clickhouse`、`runtime` 和同一校验器。数据库容器的初始化环境由编排入口按同一份凭据派生。外接时由管理员提供已有账号、库、schema 权限和可达地址。容器只读挂载配置及必要的 CA；路径字段以读取它的进程为准。源代码安装先读配置再装依赖、构建 Web。详细字段和可复制案例见[指南](guide.md)。

| control.backend | 必需连接信息 | 制品位置 |
|---|---|---|
| postgresql / opengauss | `dsn`（含库名）、独立 `schema` | 应用的 `control.artifacts` |
| sqlite 服务（提案） | `endpoint`、`token`；独占一个服务实例 | 应用的 `control.artifacts` |
| sqlite 文件（存量） | `database` | 沿用原文件相邻制品目录 |

SQLite 服务配置与文件配置互斥。`clickhouse.endpoint/database/user/password` 对三种后端均必填。数据库本体、登录角色由所选数据库安装文件或外部管理员准备，应用凭授予的权限初始化业务 schema 与表。生产发布应固定已验证的镜像版本或摘要；openGauss 需验证实际镜像的数据目录、账号创建、DDL 权限、驱动认证及目标 CPU 架构。

## SQLite 服务设计与取舍

建议把持有 SQLite 连接的事务执行部分放进服务容器，优先复用现有业务事务逻辑，Core 通过协议适配调用。SQLite 服务应能在没有 Web 和 ClickHouse 时独立启动。服务端独占数据库文件，由其执行读快照、写事务、回滚与在线备份；Core 保留访问 ClickHouse、协调业务流程及制品管理的职责。先用一条含多次读写与 Outbox 的真实业务事务验证接口粒度，再确定协议和镜像。若事务跨请求，必须把句柄绑定到身份和连接、限制并发和超时，并在断连后回滚。提交响应丢失时用业务幂等键查证，不能盲目重放写入。仅在隔离的同机网络使用明文样例；跨机部署需要验证证书的 TLS 和服务鉴权。

这样可以满足三个容器及独立端口的约束，代价是新增协议、网络故障处理及事务回归工作。直接共享 SQLite 卷会绕开端口边界。把整个 Core 搬进 SQLite 容器又会使它的启动依赖 ClickHouse。两种做法均不满足独立部署条件。

## 升级与恢复

在更换应用或数据库版本前排空写入，成套备份事务库、ClickHouse、制品、私有配置和初始化记录。SQLite 服务端执行一致性备份，保留对应应用镜像摘要。恢复到独立实例验证登录、Trace 和制品读取后再切换。旧 SQLite 文件首次转为网络服务时先对副本演练、核对事务记录与制品，原库作为回退依据。安装入口仅处理新库初始化或同目标有记录的首次安装重试，存量升级沿用[升级与回滚指南](../../../docs/zh/how-to/platform/upgrade-and-rollback.md)。
