# 分析与事务存储完整重构 — 需求分析

日期：2026-11-11。本文是待评审设计，不表示已经实现、迁移或达到容量目标。

## 1. 需求与决策边界

本次是领域模型、物理表、访问层和数据生命周期的完整重构，不要求复用现有表结构。ClickHouse 是分析存储；事务后端由部署者在 PostgreSQL、openGauss、SQLite 中选择。三者提供相同业务契约，允许通过受控迁移切换；不承诺相同吞吐，也不支持运行中修改连接串直接热切换。

用户已确认“千级并发”指 **1,000 个在线采集端，持续上报并同时进行查询、分析和评测**。它不等于 1,000 个并行数据库事务，也不等于 1,000 个重型分析查询。容量需要用 Span/s、请求/s、载荷、查询窗口及延迟进一步定义。

本设计包含评估器、Skill、Agent、评测集多版本，Benchmark 插件与指标扩展，超大 Trace，可靠接收、并发执行和跨库一致性。后端接口与既有 Python 后端方向兼容；本专项不实施语言迁移，也不以先完成全平台 Python 化作为存储试点前提。

## 原有功能保留：本次重构的硬约束

2026-11-12用户纠正：原有功能全部保留，变化的是功能背后的数据支持。此约束优先于本目录此前按Trace切片交付的界面简化方案。

- 保留原有登录入口及登录后首页、导航、页面路由、模块入口、操作流程和功能行为；不因某领域尚未迁移而隐藏菜单、替换成精简工作台或将原有操作长期改成501。
- 重构表结构、数据库适配、查询与数据生命周期，通过现有服务/Repository/API边界接入。保留调用方依赖的响应语义、过滤、排序、统计口径、错误与权限；必要新增分页字段采用兼容扩展。
- 超大Trace的虚拟化、结构分页和正文懒加载服务于原有Trace界面及分析能力，不能删除原有树/时间线、筛选、标签、详情、导出和业务联动来满足性能门槛。
- 保留原有账号、客户端接入配置、资源ID/引用、历史数据与运行结果；新增IAM/default项目须显式映射和安全迁移，不要求用户重新注册或重新上报才能看到历史数据。
- 现有Next.js平台与评测功能仍是交付主体。本次存储重构不代替前后端分离、全平台语言迁移或独立评测服务改造；已完成的Python存储样例是技术验证资产，不表示新增产品部署依赖已获批准。
- 以“同一用户/权限、相同输入、原有页面操作，在目标存储下得到等价业务结果”验收全部既有能力。底层专项通过、仅显示菜单或回退旧库不能替代功能接管证明。

| 当前位置 | 当前约束 | 目标 |
| --- | --- | --- |

| Experiment / ExperimentEvalResult | 已有配置快照、尝试和人工分等语义，但结构分散 | 冻结依赖图；操作状态与不可变评分事实分离 |
| `src/lib/benchmark/adapter-base.ts` 等 | 已有五方法 Adapter、公私 Case、环境与结果 Schema | 保留契约职责，增加实现版本、指标版本和存储隔离 |

先前仓库外的 openGauss + ClickHouse 专项稿是参考材料。本次扩大为三事务后端和完整领域模型；旧稿的“固定 openGauss”不再作为本设计约束。仓库内本目录为本次设计入口，不改写旧稿历史结论。

## 3. 可比较的容量场景

以下数字是**首轮容量设计及验收候选值**，不是实测性能或设备采购承诺。实施阶段先校准，再冻结验收基线；任何调整都须记录原因，不能用降低负载伪装通过。

| 场景 | 负载候选值 | 观测/验收候选值 |
| --- | --- | --- |
| R1000 常态 | 1,000 在线端，每端平均 1 Span/s；合计 1,000 Span/s | 连续 24 小时混合负载；无不可解释缺失/重复统计 |
| R1000 高吞吐 | 每端平均 10 Span/s；合计 10,000 Span/s，持续 1 小时 | 积压可稳定受控，记录实际吞吐和全部资源占用 |
| 突发补传 | 常态吞吐的 3 倍持续 5 分钟 | 可限流/重试；已确认接收的数据可恢复；回落后积压持续下降 |
| 混合查询 | 列表 80 req/s、Span/结构 15 req/s、分析 5 req/s，至少 100 个独立读会话 | 七日窗口列表 P95 ≤500ms；首屏结构 ≤1s；正常单 Span 正文首块 ≤500ms；常用分析 ≤3s |
| 大 Trace | 单条 10,000 / 100,000 Span；多层、多 Agent、乱序及持续追加 | 首屏 200 节点和单节点正文读取不获取完整 Trace；100,000 为压力边界档 |
| 大正文 | 每 Span 正文 4KiB/64KiB 两档，另含 1/16/64MiB 单 Span 载荷 | 大正文分块、流式导出；无静默截断；请求内存有上界 |
| 评测 | 100 活跃实验、合计 1,000 个 queued/running Case；实际并行数受模型和执行器配额约束 | 无重复有效领取；取消、续租、迟到回调与结果发布一致 |
| 历史规模 | 10M/100M Span 两档，7/30 天查询窗口；冷热缓存分开 | 吞吐、P50/P95/P99、错误率、扫描字节、峰值内存、合并积压均入报告 |
| 可见性 | accepted → indexed，常态 P95 ≤2s；最终评分独立记录发布延迟 | 明确 accepted/indexed/published；不以 HTTP 成功代替查询可见 |

延迟指标对应参考服务端部署 PG/openGauss + ClickHouse，包含服务端网络、排队和序列化，不包含模型生成时间；列表页大小 50、树页 200、正文块上限 256KiB。数据库、日志、对象存储版本、拓扑、CPU/RAM/NVMe/网络及压缩情况必须随报告公布。上述延迟不能同时套用于任意正文大小、任意筛选或无限并发。

容量算式：原始日增量 = Span/s × (平均结构字节 + 平均正文字节) × 86,400。10,000 Span/s、每条 1KiB 结构 + 4KiB 正文约为 **4.42TB/日（十进制）**，尚未计原始备份、索引、版本和副本；不能将峰值吞吐默认当成全天平均，也不预设压缩倍数。大载荷比例、留存、复制和热冷分层必须单独测算。

## 4. 功能与正确性要求

1. 每个 Span 有稳定逻辑身份；原生 Span、内部节点、interaction 之间显式映射，不假定所有采集框架一一对应。父子树、跨 Trace 协作关系和多 Agent 关系分别保存。
2. 接收可重试，事件有去重身份；同一 Span 的修订、结束后补充、乱序和恢复重放不丢字段、不重复计费。
3. 评估器、Skill、Agent、Dataset、Benchmark、Metric Schema 均可固定版本。运行不读取可变 latest。历史输入和结果不被重评或人工修改覆盖。
4. 支持草稿、发布、分支、差异、回滚别名、依赖锁定；发布版本不可变。名称是对外 key，内部稳定 ID 不随重命名改变；Skill 继续以 name 暴露路由。
5. Benchmark 新接入不向核心表加专属列，不向调度器写 Benchmark 名称分支；公有输入和私有答案/评测材料分开授权。
6. 数据扩展有命名空间、Schema 版本、类型和索引预算；缺失/未知不得伪造为 0。货币、时间和大整数有统一跨语言契约。
7. 三事务适配器有真实数据库合同测试；openGauss 不以“兼容 PG 协议”代替语法、类型和事务认证。
8. 删除、权限撤销、保留期、实验输入固定引用与导出必须跨库闭合。不存在跨数据库外键或分布式原子提交的隐含假设。
9. 各模块独立拥有自己的控制表和事实命名空间；独立评测服务通过版本化协议交换结果，不直接读写平台数据库。

## 5. 方案比较

| 路线 | 优点 | 代价 | 结论 |
| --- | --- | --- | --- |
| 不可变分析事实在 CH，控制事务在所选 OLTP，可靠日志连接 | 符合大 Trace、扩展分析与版本追溯，事务热点可控制 | 需处理可见性、重放和跨库引用 | **采用** |
| 所有明细先入 OLTP，再复制 CH | 事务读取直观 | 巨量 Span/正文持续写 OLTP，控制库继续承压 | 不作为主路径 |
| 一切放入通用 JSON/EAV 表，由应用解释 | 初期少建表 | 类型、索引、版本、关联和成本不可控 | 不采用 |

## 6. 非目标与交付边界

不实现跨事务库热双活，不承诺 SQLite 千级重写吞吐，不承诺“任意字段任意查询恒定延迟”，不把所有数据都塞入 ClickHouse；需要强事务的资产发布、任务、权限、租约仍在 OLTP。大附件/原始包进入 ArtifactStore，数据库保存引用。

本轮交付完整设计、领域归属、关键表和一致性机制、开发与验收路线；DDL 是设计草案，不直接作用于运行库。代码实施、远端提交和部署在设计确认后另行执行。
