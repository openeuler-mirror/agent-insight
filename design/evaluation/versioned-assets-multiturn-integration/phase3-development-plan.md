## 二、范围与迁移原则

### 本次基本闭环

1. Agent 可以登记并选择已有版本，外部发生变化时由用户新增版本。
2. 评估器可以查看旧版本、编辑并发布新版本，实验选择确定版本。
3. 评测集可以按版本查看 Case，逐条修改草稿、保存或回退，统一发布新版本。
4. 同一个数据集中可以包含单轮、多轮 Case；多轮 Case 有逐轮输入、预期与工具规则。
5. 新建实验选择对象及版本，冻结配置，实际执行或关联已有 Trace，然后查看结果和按原条件复测。
6. 实验详情展示冻结版本；多轮 Case 仍是一条 Case，在详情中查看逐轮评估点与证据。

### 沿用主线现有能力

- Skill 使用已有 `Skill` / `SkillVersion`；本次不另建一套 Skill 版本库。
- 保留原实验向导、Agent/IP/客户端/模型选择、Trace 选择、评估器中心和数据集详情。
- 保留主线 LLM 评估、Code 配置编辑、评估器 Skill、可配置预置评估器及其参数冻结能力。当前通用自建评估器执行分支仍要求 LLM 配置；本次版本化不能把 Code 编辑入口等同于通用代码评估已真实可执行，Benchmark 确定性评估另沿用原运行链。
- 保留 Benchmark、可靠性数据集、Trace 回流生成数据集和 Skill 工作台的现有流程。
- 原有 A/B 流程做兼容回归；本次不以新增全部消融维度作为闭环前提。

### 不随本次迁入的演示内容

演示导航白名单、隐藏原页面的构建开关、Demo 默认对象与业务数据、导入压缩包、专用启动器不进入本次迁移。演示分支中独立静态分析、模型生成等相邻能力单独登记，不捎带扩大本次范围。

## 四、开发顺序与每批交付

### 第 1 批：版本数据底座及存量兼容

**要解决的问题**：三个对象都能保存多个确定版本，已有数据和历史实验不被改写。

1. 从更新后的主线创建独立 `codex/` 功能分支与工作区，保留当前 master 上的本地草稿。
2. 先补 Phase 1 / Phase 2 文档，明确对象身份、版本字段、发布边界、权限和接口增量，再开始 schema / API 开发。
3. 优先评估“统一不可变版本记录 + 绑定各现有本体”的方案；表的最终结构在详细设计中确定。不要照搬演示 `target` 的混合对象语义。
4. 为现有 Agent、评估器、评测集建立可追溯的首版映射，明确按需初始化或批量迁移策略。迁移幂等，不能每次读取都生成新版本。
5. 草稿可编辑；发布版本只读。并发发布必须由唯一约束、事务或冲突重试保证版本号不重复，不能只靠 `max(version)+1`。
6. 为历史实验保留原快照与旧值；未记录版本的历史数据标记为未记录，不能补成当前最新版本。

**验收**：旧数据能正常读取；同对象存在 v1/v2；旧版本不变；重复迁移不增加记录；跨账号不可读写；SQLite 迁移不丢数据，并核对当前项目数据库适配边界。

### 第 2 批：三个对象的版本管理界面

**要解决的问题**：用户可以直接在原页面完成查看、修改和发布。

- **Agent**：保留原 Agent 卡片/身份，在详情或实验选择中增加版本下拉和新增版本。用户说明外部变化并登记新版本。运行机器、平台和模型继续由原执行目标选择负责。
- **评估器**：在原评估器中心和详情中增加版本查看、编辑草稿和发布。自建 LLM/Code 及其 Skill、评分点、模型配置都要保留。预置评估器版本只读，保留已有实验级配置能力。
- **评测集**：原卡片对应一个数据集，详情切换版本；每条 Case 可独立编辑、保存草稿和回退，再统一发布整个数据集的新版本。导入、Trace 回流、生成数据集和 Benchmark 的现有入口需要分别适配版本初始化/发布行为。
- **Case**：列表继续显示首次输入与最终预期输出；类别为单轮/多轮。逐轮输入、规则与工具约束放在单 Case 的详细配置中，不把全部 Case 堆进一个编辑弹窗。

**验收**：发布 v2 后查看 v1 仍显示原内容；只改一个 Case 不影响其他 Case；取消编辑和回退有效；可靠性/Benchmark 的内置保护与字段语义按主线现有规则保留。

### 第 3 批：实验选择版本、冻结配置和复测

**要解决的问题**：一场实验对应确定的对象版本，并可复用原条件重跑。

1. 在原向导的合适步骤增加 Agent、数据集、评估器版本选择，本体与版本使用两个下拉框；保留原实验类型和执行参数布局。
2. 创建实验时冻结三个对象的版本引用、内容指纹、选中 Case 顺序及逐轮定义；沿用已有 `configSnapshotJson` 和自建评估器冻结逻辑。
3. 执行与重试读取冻结定义，不在运行中重新读取最新版本；复用配置默认仍指向原版本，用户可明确切换到新版本。
4. 保留原 Trace 多选和 Case 关联流程；已有 Trace 的版本确认依据与用户登记版本分开保存。
5. 版本不是运行机器的替代项，不能因为增加版本下拉而丢失平台、客户端/IP、模型及 Agent 参数。

**验收**：开始实验后修改或发布对象不影响本实验；旧实验详情可追溯原版本；按原条件复测保留版本及执行条件；主线原有单组、A/B、Skill 工作台和 Benchmark 实验入口不被切换到专用演示流程。

### 第 4 批：真实多轮执行、回放与规则评测

**要解决的问题**：多轮 Case 在同一对话上下文执行，逐轮留下证据，并纳入原评测结果。

1. 约定 `turns[]` 的版本化输入、预期输出与规则结构；旧 Case 归一化为单轮，不要求用户批量改历史数据。
2. 对现有 Trace 按真实用户轮次、助手输出、工具调用 ID 和返回值重建逐轮证据，不用文本相似度猜测工具关联。
3. 为主线执行端增加多轮能力声明及会话续接合同。首先打通当前常用的一个原生执行端；其余端未支持时明确禁止多轮下发，同时仍可使用已有 Trace 评测。具体首个执行端在 Phase 2 依据可用联调环境确定。
4. HTTP 目标可复用演示协议的 history/sessionId 思路；需要验证真实上下文。不能把 N 次独立调用当成同一场多轮对话。
5. 一条 Case 内串行执行各轮，不同 Case 可并发；Case 与 A/B 组之间隔离会话。用户取消、超时和重试沿用主线 Attempt、取消及过期结果隔离机制。
6. 第一版失败后按整个 Case 创建新 Attempt 并重新执行；避免从中间轮盲目恢复造成会话污染。旧 Attempt 的 Trace 与失败信息保留。
7. 将逐轮业务规则作为内置轨迹评估器接入原引擎，按 2026-10-31 收敛范围覆盖逐轮输出精确/包含、必需/禁止工具与参数、实际 Skill 使用，历史高级规则仅兼容读取；与原结果评估器并行使用。
8. 每个检查点输出判定、分数、轮次、证据和建议。工具证据未采集与明确未调用工具必须区分；执行失败或证据不足应为未评完整，不能记为通过或默认 0 分。

**验收**：构造必须依赖上轮信息的 3 轮 Case；确认第三轮确实使用前两轮信息；工具参数错误落到对应轮；新会话之间不串信息；取消/超时/重试不串旧结果；HTTP 演示验证和原生执行端实测分别记录。

### 第 5 批：详情、追溯与版本趋势

**要解决的问题**：用户能看懂哪一版、哪一轮发生了变化，并找到原始证据。

- 实验概要显示所选版本和真实执行条件，操作沿用原布局。
- 多轮 Case 在列表中仍是一行，详情在原“结果评测 / 轨迹评测”结构中展示评估器维度及逐轮评分点，跳转原 Trace 对应位置。
- 已有 A/B 用例按稳定 Case 身份在一行并排显示两组输出与分数；分页不能拆开配对。单侧新增、用例定义变化都显式标明，不硬算改善。
- 在原版本分析/管理工作区增加实验资产版本追溯；原 Trace 版本标签分析保留。先支持 Agent、评估器、评测集版本组合的实验记录和基础趋势，Skill 沿用现有版本引用。
- 趋势按相同执行条件分组并显示分组配置；模型、Case 范围、运行参数不一致时不混成一条改善曲线。数据集内容变化与 Agent 能力变化要区分。

**验收**：能从实验找到冻结版本，从失败 Case 找到具体轮次、检查点和 Trace；旧版本结果不会被最新版本覆盖；现有版本标签分析仍可用。

### 第 6 批：回归、真实验收与合入

1. 每批先写关键行为回归，再移植实现，形成可独立审查的提交/MR；不做一次覆盖大量旧页面的总合并。
2. 跑相关模型/API/版本/规则/状态机测试、应用类型检查、生产构建及全仓测试；单独记录主线既有失败，不能沿用 9 月演示分支的旧测试统计。
3. 用独立数据库测试“已有旧数据升级”和“空库首次使用”两条路径，验证权限和旧数据完整性。
4. 浏览器跑通“登记 Agent v2 → 数据集修改一个 Case 发布 v2 → 发布评估器 v2 → 新建单轮/多轮混合实验 → 查看逐轮证据 → 按原条件复测 → 版本追溯”。
5. 至少一个真实原生 Agent/客户端完成多轮执行、Trace 采集与评测；模型调用、模拟执行、已有 Trace 回放分别标注验证性质。
6. 验证旧单轮实验、Code 配置编辑、LLM/Skill 评估执行、Trace 关联、Benchmark、可靠性和 Skill 工作台的关键兼容路径。
7. 按最新文档结构更新中文教程、操作指南、解释与参考，英文跟随；普通功能变更不再给开发者索引写 provenance commit。
8. 开发完成后按仓库流程从功能分支提交到 `origin`，MR 目标为 `upstream/master`；本次同步与计划阶段不执行合并或推送。

## 五、开发前需要明确的设计边界

这些事项在详细设计阶段落实，不影响当前 master 同步完成：

- 统一版本记录如何绑定原 Agent、评估器及数据集；旧 ID、内置定义与发布权限如何保留。
- Agent 的版本是用户登记/外部声明的版本，还是执行端可验证的加载版本；两者必须分别记录，不以用户选项冒充执行实证。
- 多轮执行先支持哪个真实客户端；已有接口是否能可靠续接 session、控制超时和完整采集逐轮工具证据。
- 评测集编辑草稿与旧 API 更新语义如何兼容，Benchmark 和回流生成流程何时初始化或发布版本。
- 评估器版本如何沿用现有自建定义、预置运行配置、评估器 Skill 和模型连接引用，避免复制一套凭证管理。

## 六、推荐实施节奏
