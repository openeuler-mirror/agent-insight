# Benchmark 自动接入 Skill：开发计划

本计划对应[需求分析](phase1-requirements-analysis.md)和[需求设计](phase2-requirements-design.md)。实施状态统一见[需求清单](../../README.md)，试验结论记录在实际运行报告中。

## 1. 实施顺序

| 阶段 | 工作内容 | 完成条件 |
|---|---|---|
| P0 宿主验证 | 固定宿主版本，验证完整 Skill 加载、参考资料读取、脚本调用和运行记录回读 | 宿主能够按 Skill 完成最小验证任务，依赖与权限缺口有明确记录 |
| P1 单包布局 | 建立包内 `references/`、`scripts/`、`assets/`、`tests/`，定义版本和包外运行记录格式 | 完整包移到新路径后可调用；资源无遗漏，运行产物不写入安装目录 |
| P2 接入流程 | 编写按项目地址定位工作副本、来源分析、能力查询、接入设计、开发、验收修复及交付指令，配套记录读写程序 | 从项目地址与 Benchmark 来源生成可复核计划；再次调用可核对记录续接，缺口有明确停止条件 |
| P3 公共验收 | 在包内组合契约检查、官方评分对照、真实链路验证及报告生成 | 正常、错误、缺失证据和基础设施失败能正确区分，未通过不能输出 `accepted` |
| P4 三类试验 | 按第 3 节依次执行 T1、T2、T3，记录全部尝试 | 每类都有完整记录；成功和未解决项均保留证据 |
| P5 发布准备 | 执行 OpenCode 主宿主与 Codex 可移植性验收，整理 Skill 包、使用说明、兼容声明和试验材料 | 声明范围与实测一致，可通过宿主原生机制加载完整包并复现验收 |

P0 若发现宿主缺少加载资源或执行程序的能力，记录具体限制和依赖，不静默增加常驻编排器、宿主插件或后台服务。公共能力缺口按仓库设计流程单独处理。

## 2. Skill 包自身的测试

### 2.1 包完整性与可移植性

- 完整包包含入口及所有引用的参考、脚本、模板、Schema 和脚本测试；只复制入口时能报告缺失资源。
- 将完整包复制到临时目录，从不同工作目录显式指定目标仓库和运行目录，验证包内引用及脚本调用；不依赖原源码目录中的同名资源。
- 将 Skill 安装目录设为只读后运行验收，报告、下载数据和日志均写入包外目录。
- 使用宿主既有加载方式验证同名冲突、用户修改和版本切换；保留其他 Skill、用户配置、生成代码及历史运行记录。
- 模板与目标接入协议不一致、报告 Schema 不兼容、文件摘要不匹配时给出可行动的原因，不直接使用旧结果。
- 验证协议快照的来源与包内文件摘要；同 HEAD 的未提交协议变化、协议路径移动得到待审阅结果，只有无关 commit 变化不误判不兼容；包内材料损坏报错。核对命令不执行目标代码、不写安装目录、不把文件一致当成动态能力或真实验收通过。
- 缺少解释器、平台连接或任务所需执行能力时准确报告前置条件，不静默修改宿主或升级系统依赖。

### 2.2 流程、续接与报告

- 仅提供 Agent Insight 项目地址与 Benchmark 来源的最小请求可启动；可查询的资料不交给用户重复填写。
- 仓库 URL、本地路径、已有匹配副本、当前目录属于其他项目等场景均能正确定位；不可访问的仓库、多个候选副本或仅提供部署服务地址时，准确报告需要补齐的定位信息。
- 使用目标项目实际版本的协议与能力查询入口，记录分支、commit、文档摘要及未提交改动；不读取 Skill 源码仓库或其他工作副本的协议代替。
- 未知来源、公开数据不可访问、官方评分标准不明确分别得到可行动的结果。
- 模拟缺组件、未就绪、协议缺口，验证不会混为“需要新开发”。
- 修复预算耗尽、人工处理中断、宿主退出后再次调用，以及输入或 Skill 版本变化后的恢复；续接不能重置已用预算。
- 开发 Agent 结束但验收未完成、Mock 全绿但真实链路未跑、官方基线失败、退出码与报告矛盾，均不能报告完整通过。
- 保留所有尝试和版本；记录半写、证据缺失或摘要变化时不采信旧结果；多个未完成任务不猜测选择。
- 在平台任务提交后、记录回写前中断，续接时核对在途任务；不能确认且无幂等保证时进入 `needs_action`，不重复提交。
- 同一工作目录并发调用会被检测并停止冲突写入；宿主退出不会被误描述为 Skill 自动重启。

### 2.3 判分与真实链路

- 按目标 API/CLI 形成验证矩阵，覆盖 L1 正反契约、L2 真实执行与官方评分、L3 从创建到清理；记录阶段门禁、异步截止、幂等重试、ID/摘要关联与失败路径清理。对状态/反馈耦合的 Benchmark 明确分段适用性及耦合验证方案。

- 官方正确/错误/非法/边界提交的差分测试；注入错误解析或聚合实现时验收必须失败。
- 隐藏数据进入 Agent 输入、允许搜索与官方规则冲突、必需状态未保存等情况能被拒绝。
- 超时、取消、下载失败、评分服务失败和清理不完整，分别记录基础设施事实。
- 真实环境验证数据安装、Agent 执行、Artifact 上传、Evaluator 判定、Evidence 查询及适用的重评。

测试可复用 Mock 验证失败处理，但发布声明的真实链路必须使用实际宿主、被测 Agent 和官方 Harness。包内脚本测试应能独立执行；仓库现有测试入口若只扫描 `test/`，可增加一个仅加载包内测试的薄入口，测试实现和夹具仍以 Skill 内为唯一源。不得假定 `npm run test` 自动覆盖包内测试。

所有新增代码按仓库要求执行包内专项检查与 `npm run test`；已有失败保留基线，不修改无关模块凑齐全绿。确需调整仓库测试脚本或 CI 时单独遵循仓库授权规则。

## 3. 三类试验执行协议

### 3.1 共用前置条件

每类试验开始前固定：Skill 版本与内容摘要、脚本和模板版本、开发 Agent 版本、开发模型及参数、用户提供的项目地址及其对应工作副本、目标仓库基线、所读协议版本、官方源码/数据版本、Case ID、被测 Agent、环境要求、预算和成功判据。三类试验使用同一包内公共验收入口，差异由接入包与冻结配置表达。

每类至少覆盖一个官方成功基线、一个业务未通过样例、一个非法提交或基础设施异常；具体 Case 可复用，原始结果必须分别保存。小样本试验用于验证接入流程，不替代官方全量排行。

### 3.2 T1：静态回答与独立评分

从需求分析所列的八个问答/推理 Benchmark 中选择一个公开数据和权威评分代码可访问的代表。优先选择无外部 Judge 依赖、能够确定性复核的路径；来源分析决定最终对象并写入试验记录。

试验须证明：

1. 数据版本、子集及实际导入数一致，标准答案只进入评测边界。
2. 同一批固定回答经过官方评分入口与平台 Evaluator，提取、判定和聚合结果一致。
3. 至少完成一条真实被测 Agent 执行到评分的链路，并验证重评复用已有提交物。
4. 搜索与工具权限按官方规则设置，避免将闭卷任务变成联网回答。

### 3.3 T2：EdgeBench 迭代反馈任务

从[EdgeBench 官方仓库](https://github.com/ByteDance-Seed/EdgeBench)的公开任务中，按依赖可准备性、官方基线可运行性和预算选择代表。其官方说明强调可执行环境中的反馈与持续迭代，不能将接入简化为只读题目和保存最终文本。

试验须证明：

1. 官方执行、反馈、评分入口和时间预算被准确追踪并映射。
2. 公共反馈与隐藏判分材料有明确边界；阶段状态或提交物足以支撑对应评分。
3. 缩短时长仅作为接入 Smoke 时明确标记，不与官方完整预算成绩比较。
4. 验证中断、恢复、状态保存和资源清理；无法复现官方过程时报告具体能力缺口。

### 3.4 T3：Terminal-Bench 环境任务

根据[Terminal-Bench 官方入口](https://github.com/harbor-framework/terminal-bench)定位固定数据发布及配套 Harness，记录任务版本和环境后端。不能把仓库当前分支、旧版任务布局与新数据发布混用。

试验须证明：

1. 官方参考解/Oracle 在所选环境可以通过，先排除任务与环境基线问题。
2. 被测 Agent 完成终端交互，Verifier 按官方要求观察最终环境状态。
3. 明确哪些信息可独立提交、哪些必须保留容器或其他状态；声称支持重评时实际验证状态恢复。
4. 运行失败、超时与取消后保留证据并验证清理，不把销毁环境后的日志当作可重评状态。

### 3.5 完整试验记录

每类记录至少包含：

- 原始用户请求、项目地址与工作副本对应关系、冻结配置、Benchmark 来源地址与 revision/摘要；
- 开发过程的阶段产物、决策理由、代码差异和人工介入原因；
- 每次尝试的命令、日志、退出码、耗时、Case 结果及证据摘要；
- 官方基线与适配后结果的逐条对照；
- 成功、失败、修复、恢复和清理记录；
- 可复现步骤、资源消耗、未验证范围及剩余缺口。

完整记录按 `runId` 保存在包外受控运行目录。发布时将脱敏试验总结、机器可读摘要和证据索引放入 Skill 的 `references/validation/<trialId>/`，标明原始材料的保留位置、摘要及访问条件；不在设计目录再维护一份试验真源。原始大文件、隐藏答案、私有材料和凭据不随 Skill 分发。只保存最终成功截图或汇总分数不算完整记录。

## 4. 量化评估与发布条件

| 指标 | 统计口径 |
|---|---|
| 接入验收结果 | 每类、每次运行的必需检查通过/失败/阻塞/跳过数量，按声明范围汇总 |
| 人工介入 | 介入次数、阶段和原因；区分业务澄清、凭据配置、公共扩展批准和人工编码救援 |
| 自动修复 | 首次结果、修复次数、最终结果与预算耗尽次数 |
| 评分一致性 | 固定样本上逐项差异；确定性结果必须一致，随机评分按预先固定规则判定 |
| 成本与耗时 | 分阶段墙钟时间、模型用量、环境准备时间；无法获得的成本明确标记为未知 |
| 可复现性 | 使用同一冻结输入及版本重新运行的结果，宿主切换后的差异 |

发布“自动接入已验证”前，三类试验的声明范围都须完成必需检查，且 Skill 包完整性、脚本测试、可移植性及续接验证通过。若某类仍受公共能力缺口阻塞，可以交付探索报告和完整记录，但不得宣称该类已经支持。

首个完整宿主使用 OpenCode；Codex 至少加载同一 Skill 包完成 T1 全链路和再次调用续接。由此只能声明 Codex 的已测范围，不能推定其完成 T2/T3 或全部宿主等价。发布兼容矩阵同时标注版本、加载方式、试验类型与证据入口。

## 5. 文档与交付清单

最终交付应包含：

1. 一个可独立发布的 `benchmark-onboarding` Skill 包、内容摘要清单及源码版本。
2. 包内入口、参考资料、公共验收与记录脚本、模板、Schema 及配套测试。
3. 使用宿主原生机制加载、调用、升级和再次调用续接的说明，以及必要运行依赖。
4. 三类试验的完整记录及跨宿主验证记录；包内提供脱敏摘要和索引，受控原始证据按索引访问。
5. 本次生成的 Benchmark 接入实现、测试与验收报告。
6. 已验证兼容范围、未解决限制，以及公共能力扩展的独立设计链接。
