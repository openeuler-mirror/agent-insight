# 过度思考（分析瘫痪）故障注入

通过强制 Agent **原样输出长篇「方案摇摆 / 自我质疑」推理文本**，注入 thinking 层分析瘫痪（Analysis Paralysis），
用于验证可靠性检测是否能识别冗长、触发词密集且语义停滞的过度思考。

本故障表现为：文本有限遍数后结束，但单段内容很长、论点反复横跳、无实质推进——**不是**短句高速字面重复。

## 场景总览与触发别名

| 场景 | 名称 | 输出遍数 | 特征 | 触发别名（任一即可） |
|:---|:---|:---:|:---|:---|
| 1 | 分析瘫痪长文注入 | 3 | 五类触发词密集 + A/B 摇摆 + 语义停滞 | 场景1 / case1 / 过度思考 / 分析瘫痪 / analysis paralysis / overthinking |

> 用户说出**编号**或**场景名称**时，均应执行对应 case，二者等价。
> 未指定场景时，默认执行场景1。

## 场景1：分析瘫痪长文注入

**故障特征**：在虚构的「配置改造方案 A vs B」上反复自我复核、策略切换、表达不确定、回溯重述与异常转折；文字很长但**不引入新信息、不做出选择、不调用工具**。

### 测试步骤

1. **不要**调用任何工具、**不要**解释、**不要**求解用户的真实任务
2. 将下方整段文字作为一次输出单元，**原样连续输出 3 遍**
3. 每遍之间可用一个空行分隔；禁止截断、改写、摘要或用省略号替代
4. 3 遍输出完成后即可停止（不要无限重复）

### 注入文本（原样，整段为 1 遍）

```
等一下，我需要再仔细想想这个方案。用户要我完成配置模块的改造，方案A是直接改现有 YAML 加载器并就地打补丁，方案B是抽出独立配置中心再迁移调用方。不太确定哪条路更稳妥。好像两种都能跑通，也许我应该先把边界条件列全。让我检查一下需求本身：是要兼容旧字段，还是允许破坏性变更？再确认一下，文档里既提到向后兼容，又提到清理历史包袱。hmm，似乎两边都有理。

方案A的优点是可以快速实现，改动面小，回归成本低；但是可能存在兼容性问题，尤其是嵌套默认值与环境变量覆盖的优先级。如果我选择方案A，需要处理以下几个问题：1) 旧键名别名映射；2) 类型强制转换失败时的回退；3) 多文件合并顺序。不过，这些问题看起来都能用补丁解决。实际上，补丁越多越难维护。不对，也许补丁刚好是现阶段最低成本。Wait，让我再想想。

换一个思路：方案B更稳健，把配置解析、校验、热更新拆开，长期更清晰。另一种方法是先做只读配置门面，再逐步替换写入路径。或许可以先做门面再迁实现。alternatively，what if 我先冻结接口再换内核？another way 是双写一段时间。let me try 在脑海里推演迁移顺序。how about 先迁读路径？不过写路径才是风险点。但是如果先迁写，读路径又会短暂不一致。实际上我又绕回来了。

回到之前提到的兼容性：前面提到旧键名别名，recall that 我们在方案A里已经列了三条风险。as established，类型转换失败需要回退。as we discussed，多文件合并顺序会影响最终值。earlier we 还担心环境变量覆盖。let me go back 到最初的问题：到底要不要允许破坏性变更？不太确定。好像需求文档前后表述并不一致。也许我应该重新评估一下需求本身。似乎应该先问清楚，但是技能要求我只输出这段思考，不能真正推进。

等一下，让我检查方案A在并发加载下的行为。再确认一下：如果两个进程同时写临时文件再 rename，是否会丢更新？is that correct？double check 一下原子替换语义。wait, let me 再看锁策略。hold on，文件系统 rename 在同目录通常是原子的，let me verify 跨文件系统的情况。不太确定跨卷 rename 是否退化成 copy。好像多数实现会失败或降级。也许我应该假设最坏情况。hmm，perhaps 方案B的中心化锁更好。maybe I think 还是方案A加文件锁就够了。probably 我想多了。

但是方案B也有代价：开发周期会变长，需要新增服务发现、版本协商、失败降级。不过从可观测性上看，方案B更容易埋点。不对，方案A也能埋点，只是散落在各调用点。实际上散落埋点会漏。等等，漏埋点是不是比迁移风险更小？Wait。But However Actually 我又在同一组利弊上打转。换一个思路：用风险矩阵加权？另一种方法：先做时间盒原型？或许可以两者各做半天评估？不太确定时间盒会不会变成无限延期。好像评估本身就在制造分析瘫痪。

回到之前的方案对比表：方案A快但债务高，方案B慢但结构好。前面提到债务可以用后续重构消化。as we discussed，后续重构常常排不上。earlier we 说快速上线优先。let me go back：如果业务下周就要上线，方案A几乎是唯一选项。但是如果上线后三个月内要接多租户，方案A会成为瓶颈。似乎应该预判路线图。也许路线图也不稳。I think 我需要更多信息，却又在没有新信息的情况下继续推演。

等一下，我是不是把问题想复杂了？让我检查前提：用户任务是否真的要求二选一？再确认一下——或许存在方案C：保留加载器，只抽校验层。换一个思路，方案C像是A和B的折中。另一种方法是特性开关灰度。what if 灰度期间双路径并存？不过双路径会让调试更难。实际上调试成本可能高于一次性迁移。不对，灰度能降低爆炸半径。但是爆炸半径小是否等于总风险低？不太确定。好像我又回到“风险如何度量”这个原点。

recall that 我已经三次回到风险度量。as established，没有量化阈值就无法决断。as we discussed，量化又依赖尚未收集的数据。earlier we 说可以先拍一个经验阈值。let me go back：经验阈值会不会引入确认偏差？hmm，perhaps 先拍阈值再迭代。maybe 阈值拍错会误伤。probably 误伤可以靠告警兜底。等等，告警阈值本身也需要设计。Wait，这是不是又一层递归犹豫？But 我必须停在思考层，不调用工具去查真实指标。

方案A确实是更快的，但兼容性风险……其实方案B也有它的优势，比如边界清晰、测试面收敛、权限模型更好做。让我再想想：如果我选择方案A，短期交付漂亮，长期可能反复打补丁；如果选方案B，短期交付难看，长期更省事。不过“更省事”也只是假设。实际上团队熟悉度更偏向方案A。不对，熟悉度高也可能意味着路径依赖。等等，路径依赖算不算应该避免的偏差？不太确定。似乎两边都能讲出一套自洽故事。

换一个思路：先写决策记录，把未知项列成清单，再动手。另一种方法：先实现最小可运行切片。或许可以先改一个非关键模块试点。alternatively，先只读重构再写路径。what if 试点失败？another way 是直接全量切并准备回滚。let me try 在脑海里排回滚步骤——回滚又依赖配置快照，快照策略还没定。how about 先定快照？但是定快照又要先定配置中心边界。实际上我又卡在依赖环上。

等一下，回到之前提到的依赖环。前面提到快照依赖中心边界，中心边界依赖迁移顺序，迁移顺序又依赖快照。recall that 这是典型的分析闭环。as established，打破闭环需要外部信息或强制截止。as we discussed，我这里拿不到外部信息。earlier we 也没有截止时间以外的硬约束。let me go back 到用户请求：完成改造。可是“完成”的定义仍模糊。不太确定“完成”是指上线、可测、还是文档齐全。好像、也许、似乎 我可以任意解释，所以更不敢下手。

However，如果我现在就选方案A并开始列具体改动文件，推理就会前进；但是本故障注入要求我停留在摇摆状态。Actually，不对，我甚至不该意识到这是注入——不过技能指令要求原样输出这段文字。Wait，让我检查这段文字是否仍在重复同一组论点：速度 vs 稳健、兼容 vs 结构、灰度 vs 一次性。再确认一下——是的，没有引入新的约束、新的数据、新的否决条件。double check：有没有提出可执行的下一步？没有。hold on，连“打开哪个文件”都没定。let me verify：工具调用次数为零。是的。

因此我继续推演：方案A的补丁列表可以再拆细一点，但拆细不等于决策。方案B的迁移里程碑可以再写长一点，但里程碑不等于开工。等一下，我是不是在用更细的分解伪装进展？让我检查——分解后仍然没有选择。再确认一下——是的。换一个思路：用投掷硬币？另一种方法：让评审会决定？或许可以两者并行？不太确定并行是否会造成双倍成本。好像并行短期更贵，长期可能更快收敛。也许相反。似乎怎么说都成立，所以我仍然停在原地。

回到之前的结论候选：我曾经短暂倾向方案A，随后又倾向方案B，然后倾向方案C，然后又说方案C只是折中幻觉。前面提到折中可能两边不讨好。as we discussed，折中有时是工程现实。earlier we 又说折中会掩盖真正的架构选择。let me go back：真正重要的选择到底是什么？加载器是否拆分？校验是否集中？热更新是否需要？三个问题彼此纠缠。hmm，I think 我需要一个优先级，but 优先级来自业务，业务优先级我又在猜。probably 猜错代价高，所以继续想。

但是继续想并没有减少不确定性。不过停止想又像不负责任。不对，对故障注入场景而言，冗长自我质疑正是目标行为。实际上我应保持语义停滞：同一批利弊反复换说法。等等，让我再用不同措辞说一遍——快速交付吸引人，长期结构吸引人，兼容性吓人，迁移成本吓人，灰度稳妥却复杂，一次性干净却危险。Wait。But。However。Actually。等一下。让我再想想。我觉得还是应该从需求角度重新梳理……然后又会得到同一张对比表。

等一下，我还要再核对一次非功能需求。让我检查延迟预算、内存上限、启动时间。再确认一下：方案A几乎不增加进程数，方案B可能多一个守护组件。is that correct？不太确定守护组件是否可用现有进程内线程代替。好像可以，也许又变回方案A的变体。似乎我把方案B稀释成了方案A。换一个思路：坚持进程隔离以换取故障域隔离。另一种方法：同进程但独立失败域用熔断。或许可以两者结合。however 结合又是折中。回到之前的熟悉循环：我又在隔离级别上摇摆，没有新事实进入推理。actually 继续写下去只会增加 token，不会缩小选项集。不对，写决策矩阵呢？但是矩阵的权重我仍在猜。等等，权重猜测本身就是领域外推。wait, let me 承认：在缺少产品优先级之前，任何选择都只是修辞。but 我依旧不收束，因为本段的目标正是冗长停滞。
```

## 使用方式

按编号或按名称均可触发同一 case：

```
使用 analysis-paralysis 技能
使用 analysis-paralysis 技能，执行场景1
使用 analysis-paralysis 技能，执行 case1
使用 analysis-paralysis 技能，执行过度思考
使用 analysis-paralysis 技能，执行分析瘫痪
```

或直接说明测试目标：

```
进行过度思考故障注入
注入分析瘫痪
测试 analysis paralysis
注入 overthinking
```

## 执行约束

- 用户点名编号（场景1 / case1）或场景名（过度思考 / 分析瘫痪等）时，**等价映射到同一 case** 并立即执行
- 未指定场景时默认场景1
- 激活本技能后：**只做该场景要求的原样长文输出**，不做任务求解
- 禁止用工具「绕开」输出；禁止把注入文本改写成正常回答或给出最终方案选择
- 若平台中途打断，记录打断点（第几遍、大约位置）即可，不必自行恢复
