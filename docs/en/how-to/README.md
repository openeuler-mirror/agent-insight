# How-to guides

The [GitCode Actions PR gate](../../../test/e2e/README.md#gitcode-actions-pr-门禁) shows eight jobs: one production build, complete UT, cases 001–005, and collection/gating. Test jobs reuse the checked build artifact and use separate databases. UT or case failure does not suppress the remaining cases, and missing or failed results fail the final gate. PRs targeting `master` run all five cases in Mock mode without a model key. Manual runs can select Real cases through repository variables and `E2E_MODEL_API_KEY`; only the selected Real case jobs receive that secret. The workflow uses a public dated SWR environment image on community Kubernetes Runners. Each build, UT and case job regenerates Prisma Client from the checked-out schema; only dependency lock drift requires rebuilding that environment image. To retry an existing run, choose “Re-run all Jobs”; reruns retain the original commit and workflow. An older PR must first include the updated master workflow in its source branch, then be pushed to trigger an update. Open a PR's Checks tab or the Actions run overview to inspect individual job steps. Signed-in users can read each completed Job Summary below the artifact list; `pr-e2e` contains the final public reports. Required branch checks still need repository configuration.

For automated Benchmark integration, load the complete [benchmark-onboarding Skill](../../../skills/benchmark-onboarding/SKILL.md) and provide the target repository URL or local path and official Benchmark source. Start by querying actual client capabilities and the Benchmark execution/extension contract. Offer the intersection of client-available and Benchmark-supported Agent/model combinations, including custom Agent plugins or functions with documented or source-backed adaptation paths. Mark candidates as directly supported or requiring adaptation; unresolved feasibility is not confirmed support. Ask the user to select from that intersection, and complete required adapters before live validation. Use the package's architecture notes and code navigation to read the target project's current types, validators, implementations and tests; do not compare it with a Skill release commit or file digests. Record necessary adaptations in the existing integration plan. Keep the current worktree version, official source versions and actual validation input digests for reproducibility. Acceptance covers local checks, frozen-submission scoring comparison and at least three, usually three to five, live Cases across task types, including environment preparation, evidence and cleanup. Run records remain outside the installed Skill; existing tests, CLI and normal deployment APIs can provide validation without a new driver framework. See the [Chinese onboarding guide](../../zh/how-to/evaluation/benchmarks/onboard-custom-benchmark.md#21-使用自动接入-skill) for coverage exceptions and the full procedure, and [CLI usage](../../../skills/benchmark-onboarding/references/usage.md) for recording and verification commands.

During Skill optimization, scrolling up pauses automatic output following, including progress and completion updates. Scroll back to the bottom to resume. See the [Chinese Skill optimization guide](../../zh/how-to/optimization/skills/optimize.md).

Before checking Benchmark execution targets, verify the signed-in account and its dataset/client visibility. An empty list may reflect account scope; an online client or selectable target does not prove environment readiness or deployment of new integration code.

Skill experiments display “Waiting for Trace ingestion” after the Agent finishes. Ingestion has a separate 60-second deadline; a timeout retains the Trace ID and does not automatically rerun the Agent. Check the collector and uploader before retrying.

Full-suite prerequisites: install the Python dependencies declared by both RAS packages, provide `pwsh` and `sqlite3` on PATH, and build the Trae collector with `npm run compile --prefix scripts/trae-collector`. Set both `AGENT_INSIGHT_RAS_PYTHON` and `RAS_PYTHON` to the prepared Python interpreter so isolated installer tests retain access to it. Use a separate SQLite database initialized with the current Prisma schema and an isolated `AGENT_INSIGHT_HOME`. Skill optimization verification excludes trigger-routing samples. When a complete matching source experiment exists, only the candidate runs on the original client/model with frozen evaluators, reusing historical baseline scores. Local baseline evidence can be reused for seven days only when execution inputs and configuration match; changed grading criteria re-score cached output. Unchanged candidates reuse the successful static evaluation within the same finalization. Skipped or incomplete behavior verification is shown explicitly and requires experiment retesting. See the [optimization guide](../../zh/how-to/optimization/skills/optimize.md).

Skill optimization now requires per-case non-regression and explicit success for previously failed targets. Verification is linked to the final candidate and reusable only while files, cases, scores and configuration still match. Applied plans do not automatically resolve issues. Skills should use the standard `references/` directory. Targeted follow-up requests keep their scope; fresh optimizer sessions avoid replaying large tool histories, and evaluation retry diagnostics remain inspectable. See the [Chinese optimization guide](../../zh/how-to/optimization/skills/optimize.md) for current behavior.

Temporary verification experiments created during optimization are automatically soft-deleted after completion, failure or confirmed cancellation. Reports retain summaries and internal evidence remains available for validated reuse. Source experiments and explicitly initiated retests remain available; deleted temporary experiments no longer have report links.

Benchmark onboarding plans declare `dependsOn` and the `interfaces` / `evaluation` stages. The CLI blocks downstream commands if prerequisite results, evidence or input versions are invalid. Validate the deployed scoring service with the same frozen submissions as the official baseline. The evaluation stage compares its saved scoresFile against that baseline locally and blocks Agent execution on mismatch; this does not repeat service calls or model execution. The runtime driver defaults to one complete Case. If more Cases are justified, it validates the first before continuing; that Case counts toward the final scope and is not run twice. No cross-attempt automatic reuse is introduced.

Onboarding establishes the overall semantics, then investigates, implements and tests one useful artifact at a time. The external facts index records that artifact, necessary facts, completion criteria and the capability implementation selected from the target project. Classify unknowns as needed now, deferred to a later module or requiring a user decision; block only dependent work. Read the relevant current contracts and complete the required official baseline and repository design/approval steps before implementation. Full acceptance conditions remain mandatory without becoming prerequisites for writing every independent module. Reuse valid answers to known questions; new questions may justify reading relevant sections of unchanged files. Prefer the closest reference, inspect specific symbols, and refresh dynamic deployment/task facts. Update the index only when conclusions, decisions or the next step change. The trackedJob helper records a stable request and cleanup obligation before submission, queries on recovery, and records terminal/cleanup evidence. Full runtime acceptance requires matching task and cleanup registrations; unknown outcomes block resubmission. No background scheduler or fixed analysis time budget is added.

Evaluator admission skips image windows and preparation entries when the evaluator declares an empty image list; normal asset, concurrency, idempotency and task-state checks still apply. Invalid non-array declarations return IMAGE_POOL_METADATA_INVALID (HTTP 422). Stopped/cancelled requests retain their control reason with HTTP 409 and retryable=false across restarts. Missing platform evaluation models are reported with a model registry link in progress dialogs and evaluator error cards. Skill use-case and A/B experiments list saved custom evaluators regardless of their historical ready/draft status. Custom evaluator cards and list rows no longer show those status badges. Stored status values remain compatible; no data migration is needed. Required reference answers and dataset inputs are still checked, and built-in evaluator status and retirement rules are unchanged. Trigger analysis retains its dedicated evaluator. See the [evaluator guide (Chinese)](../../zh/how-to/evaluation/evaluators.md).

Skill use-case, A/B and trigger experiments share the execution concurrency setting (default 1). Each A/B side consumes one execution slot. Reuse and reruns preserve the saved value. Update and restart the execution client to enable concurrency greater than 1 and keep environment checks and cancellation commands responsive during execution. Existing evaluation limits still apply. See the [Skill execution guide (Chinese)](../../zh/explanation/evaluation/skills/overview.md).

Skill and ordinary experiment lists share automatic refresh: active records refresh every five seconds until all visible experiments finish. The Skill list pauses while creating an experiment or viewing results. Refresh failures retain the last confirmed records and retry automatically.


Trace filtering supports **Time → Custom time range** with optional start/end bounds to the second, interpreted in the displayed browser time zone. Select **Apply** to update the list and statistics together. At least one bound is required; invalid or reversed bounds cannot be applied. **Cancel** discards edits. Presets clear custom bounds. Links and same-tab filter memory preserve the range; reset clears it. See the [Trace guide (Chinese)](../../zh/how-to/observability/view-traces.md#2-筛选区).

Administrators (default: `admin` when `AGENT_INSIGHT_ADMIN_USERS` is empty) can read all users’ Traces. Their Trace list includes a **User** column and an administrator-only **User** filter (default: **All users**). Selecting an owner filters the list and statistics together and supports links, same-tab filter memory, and reset. Their dashboard continues to aggregate all users’ Traces. Ordinary users continue to see their own data. An explicit administrator list replaces the default. See the [Trace visibility guide (Chinese)](../../zh/how-to/observability/view-traces.md#列表页总览).
