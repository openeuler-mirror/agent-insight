OpenCode compatibility: updated Agent Insight resident clients support Skill snapshot isolation and read-only trigger analysis on OpenCode 1.x and 2.x (native validation: 2.1.4). Skill case generation and A/B require snapshot capability; trigger analysis additionally requires routing capability. If capabilities are missing, check the resident client version and reported capabilities; upgrading OpenCode alone is insufficient. See the [Chinese execution guide](../../zh/explanation/evaluation/skills/overview.md#opencode-执行兼容性).

Skill experiments display “Waiting for Trace ingestion” after the Agent finishes. Ingestion has a separate 60-second deadline; a timeout retains the Trace ID and does not automatically rerun the Agent. Check the collector and uploader before retrying.

Full-suite prerequisites: install the Python dependencies declared by both RAS packages, provide `pwsh` and `sqlite3` on PATH, and build the Trae collector with `npm run compile --prefix scripts/trae-collector`. Set both `AGENT_INSIGHT_RAS_PYTHON` and `RAS_PYTHON` to the prepared Python interpreter so isolated installer tests retain access to it. Use a separate SQLite database initialized with the current Prisma schema and an isolated `AGENT_INSIGHT_HOME`. See the [Chinese development guide](../../zh/how-to/platform/conventions-and-extension.md).

Skill optimization verification excludes trigger-routing samples. When a complete matching source experiment exists, only the candidate runs on the original client/model with frozen evaluators, reusing historical baseline scores. Local baseline evidence can be reused for seven days only when execution inputs and configuration match; changed grading criteria re-score cached output. Unchanged candidates reuse the successful static evaluation within the same finalization. Skipped or incomplete behavior verification is shown explicitly and requires experiment retesting. See the [optimization guide](../../zh/how-to/optimization/skills/optimize.md).

Skill optimization now requires per-case non-regression and explicit success for previously failed targets. Verification is linked to the final candidate and reusable only while files, cases, scores and configuration still match. Applied plans do not automatically resolve issues. Skills should use the standard `references/` directory. Targeted follow-up requests keep their scope; fresh optimizer sessions avoid replaying large tool histories, and evaluation retry diagnostics remain inspectable. See the [Chinese optimization guide](../../zh/how-to/optimization/skills/optimize.md) for current behavior.

Temporary verification experiments created during optimization are automatically soft-deleted after completion, failure or confirmed cancellation. Reports retain summaries and internal evidence remains available for validated reuse. Source experiments and explicitly initiated retests remain available; deleted temporary experiments no longer have report links.

Dify native Workflow can send OTLP/HTTP traces directly to Agent Insight without source changes or a collector plugin. Configure `ENABLE_OTEL=true`, `OTEL_EXPORTER_OTLP_PROTOCOL=http`, the full `OTLP_TRACE_ENDPOINT`, an empty `OTLP_API_KEY`, and `OTEL_EXPORTER_OTLP_TRACES_HEADERS=x-witty-api-key=<your-key>` in both Dify API and Worker processes. Use `OTEL_SAMPLING_RATE=1.0` for validation. Keep Metrics pointed at a compatible Metrics collector. The server adapter filters infrastructure spans and preserves Workflow nodes, text message roles and LLM token usage, grouped by trace ID. Start → LLM → End Workflow is real-task verified. Agent internals use a separate native pipeline in the Agent run service: set `DIFY_AGENT_TRAJECTORY_ENABLED=true`, `DIFY_AGENT_TRAJECTORY_OTLP_TRACES_ENDPOINT` to the same full Trace URL, `DIFY_AGENT_TRAJECTORY_OTLP_HEADERS` to a JSON object containing `x-witty-api-key`, and `DIFY_AGENT_TRAJECTORY_INCLUDE_CONTENT=true` when message/tool content is required. The server preserves model → tool → model steps, reported reasoning, tool arguments/results and per-model usage without double-counting root aggregates. A real single Agent SDK run through the official Dify LLM gateway and a real Workflow tool has been verified through ingestion and the browser. On SQLite deployments, Workflow details now link internal Agent traces by the authenticated owner, tenant, app and exact node execution ID; conflicting workflow/run/node IDs are rejected. Separate trace IDs, retry attempts and source records are preserved. OpenGauss deployments configured with `DB_HOST` retain the original per-trace view; cross-trace queries do not fall back to local SQLite. Late child traces can be loaded with Refresh. The detail token total includes linked model spans, while stored execution counters remain per trace. Linked payloads are bounded to 4 MiB per trace and 16 MiB total, with a partial-results notice. A published native Workflow with two serial Agent v2 nodes and a final DeepSeek summary has passed real-model ingestion and browser verification: 7 model calls, 4 tool calls, 28,716 tokens, approximately 38 seconds. Each Agent made 3 model calls and 2 Workflow tool calls. Browser checks covered hierarchy, tool results in the next model input, tool arguments/results and independent Agent Trace navigation. Tool Workflows retain separate internal model traces, which are not recursively included in these counts. The AGENTS count includes the Workflow root container. Chatflow completion status remains a known limitation. See the [Chinese Dify configuration and scope](../../zh/how-to/observability/develop-trace-collector.md#dify-原生-otlp-接入).

Supplemental Chatflow tests preserved two-turn history, answers and tokens, but completion status is incorrect because Answer nodes are not recognized by the current completion rule. Upgrading Docker Desktop from 4.41.0 to 4.97.0 provided Landlock ABI 8 and unblocked the native two-Agent Workflow acceptance. No Dify source changes were needed. Real parallel/retry, pause/resume, multimodal and autonomous Shell tool scenarios remain unverified.

Ordinary TOOL rows now nest under their initiating LLM only when original response tool blocks, projected model-output call IDs, or an exact parent span in the same trace provide an unambiguous link. OpenCode parts and Claude content blocks can provide this evidence. Time-based adapter grouping alone is insufficient. Skill, TASK, child Agents and dispatch anchors keep their existing positions. The display projection preserves event indexes, source records, counts and token totals; Tool filters and tool-name search retain the LLM ancestor.
