For automated Benchmark integration, load the complete [benchmark-onboarding Skill](../../../skills/benchmark-onboarding/SKILL.md) and provide the target Agent Insight repository URL (or local path) and official Benchmark source. The package includes a versioned protocol snapshot with source commit and file digests, validation scripts, templates and tests; run records remain outside the installed Skill. Read the snapshot, compare it with the target repository using `protocol-check.cjs`, record differences and adapt templates before implementation. The target repository remains authoritative; available Agents, Git sources, collectors and deployment readiness are discovered at runtime. A matching snapshot does not prove readiness. Acceptance proceeds through endpoint contract tests, real execution/evaluation segment tests, then a fresh end-to-end run. Discover actual endpoints and identities, wait for business terminal states, correlate Case/Run/Artifact/evaluation identities and digests, and verify cleanup on success and failure. The CLI enforces explicit dependsOn prerequisites; the generated driver validates business steps and deployed versions. Dependencies are not inferred automatically. When a material decision remains unresolved after inspecting project and official sources, the Agent discusses the facts, options, trade-offs and recommendation with the user. Existing decisions remain valid; independent work continues while dependent steps wait. Record decisions and re-freeze affected plans; silence is not consent. Dataset acceptance must read and parse actual files or objects, verify persisted database or index records, compare their transformed contents and resource references, and test repeated imports and recovery from failed imports in an isolated dataset. Discover storage locations and contracts from the target project; record installation scope, real versus mocked evidence, and equivalent checks for other storage types. Missing access or evidence blocks acceptance. New onboarding runs have no default task-wide attempt or elapsed-time limit. Per-command timeouts, bounded retries and polling deadlines still apply; configure task-wide limits only when explicitly requested by the user. Existing numeric limits remain effective until explicitly changed or removed with `budget ... unlimited`, with the reason recorded. Attempt counts do not measure model calls or spending. The runtime driver template saves existing responses and submission bytes during execution. The read-only `check-result.cjs` checks format first, then saved evidence, digests and per-Case execution/evaluation links without launching models or platform work; it never produces accepted or certifies compatibility with the current code version. Acceptance requires frozen official scoring comparisons and required live checks, not just generated code or fixture tests. See the [Chinese onboarding guide](../../zh/how-to/evaluation/benchmarks/onboard-custom-benchmark.md#21-使用自动接入-skill) and [CLI usage](../../../skills/benchmark-onboarding/references/usage.md).

During Skill optimization, scrolling up pauses automatic output following, including progress and completion updates. Scroll back to the bottom to resume. See the [Chinese Skill optimization guide](../../zh/how-to/optimization/skills/optimize.md).

Before checking Benchmark execution targets, verify the signed-in account and its dataset/client visibility. An empty list may reflect account scope; an online client or selectable target does not prove environment readiness or deployment of new integration code.

OpenCode compatibility: updated Agent Insight resident clients support Skill snapshot isolation and read-only trigger analysis on OpenCode 1.x and 2.x (native validation: 2.1.4). Skill case generation and A/B require snapshot capability; trigger analysis additionally requires routing capability. If capabilities are missing, check the resident client version and reported capabilities; upgrading OpenCode alone is insufficient. See the [Chinese execution guide](../../zh/explanation/evaluation/skills/overview.md#opencode-执行兼容性).

Skill experiments display “Waiting for Trace ingestion” after the Agent finishes. Ingestion has a separate 60-second deadline; a timeout retains the Trace ID and does not automatically rerun the Agent. Check the collector and uploader before retrying.

Full-suite prerequisites: install the Python dependencies declared by both RAS packages, provide `pwsh` and `sqlite3` on PATH, and build the Trae collector with `npm run compile --prefix scripts/trae-collector`. Set both `AGENT_INSIGHT_RAS_PYTHON` and `RAS_PYTHON` to the prepared Python interpreter so isolated installer tests retain access to it. Use a separate SQLite database initialized with the current Prisma schema and an isolated `AGENT_INSIGHT_HOME`. See the [Chinese development guide](../../zh/how-to/platform/conventions-and-extension.md).

Skill optimization verification excludes trigger-routing samples. When a complete matching source experiment exists, only the candidate runs on the original client/model with frozen evaluators, reusing historical baseline scores. Local baseline evidence can be reused for seven days only when execution inputs and configuration match; changed grading criteria re-score cached output. Unchanged candidates reuse the successful static evaluation within the same finalization. Skipped or incomplete behavior verification is shown explicitly and requires experiment retesting. See the [optimization guide](../../zh/how-to/optimization/skills/optimize.md).

Skill optimization now requires per-case non-regression and explicit success for previously failed targets. Verification is linked to the final candidate and reusable only while files, cases, scores and configuration still match. Applied plans do not automatically resolve issues. Skills should use the standard `references/` directory. Targeted follow-up requests keep their scope; fresh optimizer sessions avoid replaying large tool histories, and evaluation retry diagnostics remain inspectable. See the [Chinese optimization guide](../../zh/how-to/optimization/skills/optimize.md) for current behavior.

Temporary verification experiments created during optimization are automatically soft-deleted after completion, failure or confirmed cancellation. Reports retain summaries and internal evidence remains available for validated reuse. Source experiments and explicitly initiated retests remain available; deleted temporary experiments no longer have report links.

Benchmark onboarding plans declare `dependsOn` and the `interfaces` / `evaluation` stages. The CLI blocks downstream commands if prerequisite results, evidence or input versions are invalid. Validate the deployed scoring service with the same frozen submissions as the official baseline. The evaluation stage compares its saved scoresFile against that baseline locally and blocks Agent execution on mismatch; this does not repeat service calls or model execution. The runtime driver completes and validates the first Case before the rest; that Case counts toward the final scope and is not run twice. No cross-attempt automatic reuse is introduced.

Onboarding maintains an external facts index with source/version evidence and the next actionable step. Reuse unchanged static findings and enter implementation once the minimum analysis questions are answered; refresh dynamic deployment and task facts. The trackedJob helper records a stable request and cleanup obligation before submission, queries on recovery, and records terminal/cleanup evidence. Full runtime acceptance requires matching task and cleanup registrations; unknown outcomes block resubmission. No background scheduler or fixed analysis time budget is added.

Evaluator admission skips image windows and preparation entries when the evaluator declares an empty image list; normal asset, concurrency, idempotency and task-state checks still apply. Invalid non-array declarations return IMAGE_POOL_METADATA_INVALID (HTTP 422). Stopped/cancelled requests retain their control reason with HTTP 409 and retryable=false across restarts.
