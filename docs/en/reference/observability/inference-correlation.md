# Inference request correlation contract

Agent → local client gateway → original inference service. The original model address is registered explicitly by the user; installation never rewrites it. Trace collection paths are unchanged, and correlation data stays in existing interaction metadata with no new database tables or platform APIs.

Two `X-Request-Id` values exist on this path, with different origins and purposes:

- **Gateway call ID**: a UUID generated by the local gateway for each actual forwarded model HTTP request, used for service-side record lookup and local correlation.
- **Model service response ID**: the `X-Request-Id` returned in the model service (or fronting gateway) response headers, used to find that service's own inference records.

Neither value overwrites the other, neither is assumed globally unique, and neither replaces platform Trace/Span IDs.

## Gateway call ID: inference services adapt one request header

The gateway forwards each supported model HTTP request with a fresh UUID v4 in **`X-Request-Id`**, replacing any incoming value. Each retry gets a different ID. This identifies an HTTP attempt, not a Trace or logical LLM span.

Inference services read and persist this header with each inference record, including errors, and provide `/model-performance?GlobalTrackNO=<UUID>` for one selected request. Intermediate proxies must preserve it. No Agent-specific logic is required. HTTP errors retain the same header contract. A request that never reaches the service cannot deliver its ID there; gateway-local failures remain locally observable. The gateway does not retry automatically.

## Model service response ID: capture the other layer

When the model service returns `X-Request-Id` in its response headers, the gateway and enrolled collectors capture it separately as the **model service response ID**:

| Rule | Behavior |
| --- | --- |
| Header name | `X-Request-Id`; HTTP header names are case-insensitive. Only this agreed header is collected — never authorization, cookies or other response headers |
| Value | Preserve the service value verbatim; do not coerce it to a UUID or swap it with the gateway UUID |
| Timing | Record once response headers arrive, without waiting for the response body or stream end; streaming and non-streaming behave the same |
| Attempt scope | One value per actual HTTP attempt; retries may each carry a different service ID |
| Duplicates | Repeated headers with the same value collapse to one; conflicting values are treated as unavailable rather than guessed |
| Missing | If the service omits the header, middleware strips it, transport fails or headers never arrive, show an explicit "not provided" state. Never backfill from the call ID, Trace ID or timing |
| Errors and cancellation | If headers arrived before a 4xx/5xx, timeout or user cancellation, retain the real service ID and call state |
| Provenance | Results carry source `model-response-header`, distinct from the gateway-generated call ID |

The gateway stores the service ID in its local journal and relays it to Agent-side collectors through the internal response header `x-agent-insight-upstream-request-id`. That internal header is not forwarded to the inference service, and unrelated `x-agent-insight-*` upstream response headers are stripped. In direct-connect mode, the value is recorded only when the SDK/fetch exposes response headers and call ownership is provable; otherwise it stays in the Trace-only unassigned list.

## Supported paths

| Path | Model response ID support |
| --- | --- |
| OpenCode 1.x / 2.x → local gateway | Supported; 2.x reads the gateway relay header in its native HTTP hook |
| Qoder CN CLI → local gateway | Supported; the CLI hook reads the gateway journal at session end |
| OpenCode direct connect, unmanaged provider | Conditional; only when response headers are visible to the Agent and call ownership is provable |
| Qoder Desktop / JetBrains | Not supported; no verified response-header access path |
| OTLP/log-based collectors (Claude Code, Codex, Hermes, Langfuse, etc.) | Not supported; framework telemetry does not expose raw HTTP response headers |
| Platform built-in evaluation/optimization model calls | Not stored as user Traces; outside this contract |

## Agent differences

OpenCode 1.x uses message/fetch evidence; 2.x uses native model/http hooks and delayed step events. Only explicitly enrolled endpoints are intercepted. Qoder CN CLI uses the session header and a unique genuine response ID; synthetic local error IDs are excluded. Desktop/JetBrains response identities are unverified.

The model service response ID is not a message ID or response-body ID. It exists only after HTTP response headers arrive, so a failed Qoder CLI call with no usable `message.id` can still retain its service ID in the Trace-only unassigned calls.

Internal `x-agent-insight-*` and Qoder session headers are removed before forwarding. Responses to the Agent include `X-Request-Id` and a legacy local alias `x-agent-insight-call-id`; the alias is not sent downstream.

## Storage and ownership

Existing interaction metadata stores `inference_call_ids`, `inference_attempts` and Trace-only `inference_unassigned_calls`; no new database tables are required. Model response IDs additionally use:

| Field | Meaning |
| --- | --- |
| `inference_upstream_request_ids` | Owned `{ call_id, request_id, source }` entries; `source` is currently `model-response-header` |
| `inference_attempts[].upstream_request_id` | Service ID for one attempt |
| `inference_unassigned_calls[].upstream_request_id` | Service ID whose LLM ownership cannot be proven and which belongs only to the whole Trace |

Service IDs attach only to proven `call_id` ownership and never cross LLM boundaries; multiple attempts on one call are kept individually. Async upload, retry, service restarts and history refresh all use the existing interactions JSON; Traces without the field keep rendering normally.

Local journals are account-scoped and contain IDs/timing/status, not prompts or model credentials. OpenCode rechecks changed journals and retries failed uploads. Parent Traces aggregate child calls; LLMs only receive proven IDs. Unknown ownership stays Trace-only. The UI lists retries separately and recommends a latest attempt only if timestamps establish one uniquely.

## Display and lookup

When a service ID exists, LLM detail shows it with copy support: one value is shown directly, multiple values show a count and direct users to the inference analysis dialog, and calls without a service ID show "not provided". The dialog keeps both the gateway call ID and service ID and offers lookup links for each, controlled by `AGENT_INSIGHT_INFERENCE_ANALYSIS_ORIGIN`. Service IDs are URL-encoded, and no link is rendered when the origin is unset or invalid or the ID is missing.
