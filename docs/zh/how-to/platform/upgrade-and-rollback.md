升级需要同时管理程序版本、数据库结构和运行目录。Agent Insight 的安装与启动流程可能执行数据库结构同步；仅换回旧程序不能保证兼容升级后的数据。平台目前没有统一的 `upgrade` / `rollback` CLI 命令。

## 升级前

1. 记录当前版本、源码提交或镜像摘要，以及平台运行目录、数据库、外部配置目录和客户端版本。
2. 确定目标发布版本，阅读该版本的变更与配置迁移要求。使用明确版本或镜像摘要，保留当前安装包、源码构建或镜像。
3. 暂停新任务和写入，停止平台及相关写入进程，完成[备份](./backup-and-restore.md)。备份应在安装新版本之前完成：npm 安装的 `postinstall` 也可能同步数据库结构。
4. 推荐先在备份副本上验证目标版本。测试实例使用独立运行根、数据库和端口，隔离真实客户端与模型调用。

已有 `.env` 不会因模板更新自动补齐所有新配置。对照目标版本的模板检查新增、删除及改名项，保留本机密钥和实际地址；不要用模板直接覆盖现有配置。核心变量见[运行配置参考](../../reference/platform/configuration.md)。

## 按原部署方式更新

| 部署方式 | 更新步骤 | 需要保留的内容 |
| --- | --- | --- |
| npm | 停机备份后，在原安装范围内安装指定版本，例如全局安装使用 `npm install -g agent-insight@<目标版本>`；使用原运行用户和运行根 | 原版本号与安装包、运行根、外部配置和数据库备份 |
| 源码 | 在独立部署目录检出指定提交，按该版本的构建说明安装依赖并构建；验证后切换启动目录。正式启动沿用 `bash scripts/start.sh` | 原源码提交和可运行构建、运行数据；不要通过覆盖有未提交改动的工作目录来升级 |
| Docker | 在原部署配置中改为明确的目标镜像 tag 或 digest，停止旧容器后启动新容器，确认持久化卷映射一致 | 原镜像摘要、部署配置、持久化数据卷的备份；不要同时启动两个容器共享运行根 |

尖括号中的版本是占位符，执行前替换为实际发布版本。不要在升级过程中顺手切换部署方式或数据库类型。源码构建步骤见[仓库 README](https://gitcode.com/openeuler/agent-insight/blob/master/README.md)，镜像材料见[Docker 镜像发布](./release-docker-image.md)。

## Next.js 安全升级

当前依赖基线为 `next` / `eslint-config-next` 16.4.3。更新时一并提交 `package-lock.json`，在干净构建目录按锁文件安装并重新生成 standalone、静态资源和发布包。不要复用升级前的 `.next`。确认最终产物实际加载的 Next.js 为 16.4.3，图片处理依赖 `sharp` 至少为 0.35.5，且平台原生库与包版本匹配。

Docker 源码模式使用镜像预装的依赖。源码依赖变化后必须重建镜像；仅更新挂载源码并重启不够。入口会检查依赖是否存在，并校验声明为固定版本的直接依赖（包括 Next.js）；缺失或版本不一致时停止启动并提示重建。范围版本仍应通过锁文件和最终产物审计核实。

升级验证除测试和生产构建外，还需覆盖真实发布包启动、登录、旧采集 URL、SSE 输出与取消、RAS WebSocket 指令与回执、长轮询。测试使用隔离运行根和数据库；切换前排空评测任务，启动回收逻辑可能将未完成任务标记为失败。回退时使用已保留的旧发布产物，注意旧版仍可能包含已知漏洞。

## 首次启动与验收

使用原部署入口启动目标版本。观察启动日志中的配置解析、数据库结构同步和后台任务状态；如提示同步可能丢失数据，停止升级并核对差异，不要把 `prisma db push --accept-data-loss` 作为常规升级步骤。

确认以下结果后再恢复外部写入：

- 登录、历史 Trace、历史实验和附件可以访问。
- 模型配置和客户端接入配置仍在，运行根与数据库指向预期位置。
- 在受控测试客户端上发送一条 Trace，确认接收、消费和界面展示完整。
- 如使用评测或可靠性功能，完成一个既有小用例，确认独立 Evaluator、RAS/FI 客户端与平台协议兼容；需要升级客户端时按发布说明逐台处理。

安装成功、端口可访问或健康检查通过，都不能单独证明历史数据和全部业务功能兼容。

## 回滚

1. 停止新版本和相关写入进程。把升级后的数据另外保存，记录升级后新增的 Trace、实验等数据范围。
2. 恢复原程序版本或镜像。
3. 将升级前的备份恢复到新的运行目录或独立数据库，按[恢复步骤](./backup-and-restore.md)核对绝对路径，再启动原版本。
4. 验证历史数据、登录和核心用例，随后切回服务入口和客户端连接。

如果数据库结构已变化，应默认使用与旧版本匹配的升级前备份，不能假定直接降级程序会自动降级数据库。恢复升级前备份也意味着之后新增的数据不会自动出现；保留新数据副本，另行评估导出或迁移，避免直接混合两套数据库文件。

本指南不提供跨任意版本的兼容保证。升级失败时保留日志、版本和配置差异供排查；分享日志前移除密钥和业务敏感内容。

### 评测诊断功能的 SQLite 升级

先在与部署一致的隔离副本上演练。核对服务解析出的实际数据库路径，暂停写入和后台任务。为数据库外的 Skill 文件及报告资产创建一致性备份并核对清单。以下路径均为示例，备份目标必须是一个尚不存在且仅管理员可访问的文件。

```sh
python3 scripts/migrations/diagnosis-inputs.py --database /path/to/witty_insight.db
python3 scripts/migrations/diagnosis-inputs.py --database /path/to/witty_insight.db --apply --backup /backup/diagnosis-before.db
```

第一条执行预检。第二条使用 SQLite backup API 保存副本，在事务内新增 DiagnosisRun、扩展 SkillOptPlanItem，逐表核对原有字段、记录数量、索引与触发器，并检查外键和数据库完整性。保留输出的 JSON 对账记录。已有异常或差异必须先排查。首次建空库可沿用启动流程；已有部署库必须先完成迁移。演练时再用新备份路径重复执行一次，在另一目录恢复首次备份，核验摘要、资产和旧业务，再开放写入。

恢复旧版本时确认其启动过程能保留扩展后的表结构。若升级后已有新写入，先冻结写入并备份当前状态，优先前向修复。只有尚未恢复写入的失败升级才能直接用已验证的完整备份和对应资产回退。停服务并关闭所有 SQLite 连接后，在新目录恢复和核验，不单独替换打开的 .db 文件。
