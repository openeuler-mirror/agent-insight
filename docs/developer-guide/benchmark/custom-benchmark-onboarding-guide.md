# 自定义 Benchmark 接入指南

> 面向提出评测需求的客户和业务人员。本指南不要求你理解 Manifest、Adapter、Evaluator，也不要求先填写技术表格。

## 1. 你需要做什么

你只需要用自然语言说明：

- 想评测 Agent 的什么能力；
- 手上已经有哪些数据、代码、测试或参考材料；
- 从业务角度看，什么结果算成功。

执行输出、评测程序、运行环境、资源限制和页面字段通常是接入设计的结果。AI 应当先分析材料并提出建议，再请你确认关键选择。

最简单的请求可以只有一句话：

> 我有一批代码修复任务，每条数据包含仓库、问题描述和隐藏测试。我希望 Agent 修改代码后，通过隐藏测试判断是否修复成功。请帮我接入为 Agent Insight Benchmark。

如果你已经有材料，可以直接一起提供：

- 一至三条真实或脱敏 Case；
- 字段说明或数据集文档；
- Git 仓库、Dockerfile、依赖锁文件；
- 现有测试命令、评分脚本或官方 Harness；
- 一份成功结果和一份失败结果；
- 不能发送给 Agent 的隐藏测试、答案或敏感字段说明。

不完整也没关系。AI 应当先从已有材料中推导，不应把一整张技术表格退回给你填写。

## 2. 推荐的发起方式

你可以复制下面这段话，再换成自己的业务描述：

```text
请先阅读《Benchmark 文档关系与开发指南》和《Benchmark 接入开发规范》。

我想评测：<用自然语言描述目标>。
我目前有：<数据、仓库、测试、脚本或参考材料>。
我认为成功大致是：<业务上的成功标准；不确定可以写“不确定”>。

请先检查已有材料并进行需求发现，不要立即编码。能从材料中确定的内容直接给出判断；
不能确定且会改变接入方案的问题，每轮最多问我 1～3 个，并给出推荐选项及影响。
最后先生成一份《Benchmark 接入确认单》，经我确认后再开发。
```

## 3. AI 会怎样与你协作

### 3.1 理解目标

AI 首先应当复述：

- 被评测的对象和能力；
- 一条 Case 代表什么；
- 已有的权威判定材料；
- 当前已知信息和仍需确认的信息。

如果理解有偏差，你只需要纠正业务含义，不需要替 AI 设计接口。

### 3.2 阅读材料

AI 应优先检查数据样例、仓库、测试脚本和运行说明，从中推导：

- Case 的唯一标识和任务输入；
- 哪些字段可以发送给 Agent，哪些只能交给 Evaluator；
- Agent 应修改或产生什么；
- 测试入口、依赖版本和运行环境；
- 可以归一化成什么主指标和评分点；
- 页面上适合展示哪些字段和文件。

能从材料中确定的问题不再询问你。

### 3.3 提出候选方案

对于技术设计，AI 应给出推荐方案和理由，例如：

> 根据数据字段和现有测试脚本，建议每条 Case 创建 Git 工作区，让 Agent 修改代码，执行器收集相对基线的 Git Patch。Evaluator 在隔离环境中应用 Patch 并运行隐藏测试，主指标为是否全部通过，同时保留测试通过数和运行日志。

你主要确认业务语义是否正确，而不是确认每个协议字段。

### 3.4 逐步确认关键选择

AI 每轮只应询问少量、确实会改变方案的问题，例如：

- 必须全部测试通过，还是允许按通过比例计分；
- Agent 是否允许联网；
- 哪些数据绝不能暴露给 Agent；
- 测试失败与评测环境故障是否需要分开统计；
- 时间和资源成本是否有硬限制。

AI 应同时给出推荐答案及其影响，不能只抛出开放问题。

## 4. 哪些事情由谁决定

| 内容 | 默认责任人 |
|---|---|
| 评测目标和业务成功标准 | 客户确认 |
| 数据授权、隐私和可见范围 | 客户确认 |
| 是否允许部分得分 | 客户确认 |
| 时间、成本和安全硬限制 | 客户确认 |
| Case 字段映射和公开/私有拆分方案 | AI 提议，客户确认 |
| Agent 最终提交物 | AI 根据任务和执行能力提议 |
| Evaluator、Harness 和 Evidence 设计 | AI 根据权威判定材料提议 |
| 运行环境、依赖和资源初值 | AI 从材料推导并提议 |
| Manifest、Schema、Adapter 和 Presentation | AI/开发者实现 |
| 测试、错误处理和页面兜底 | AI/开发者实现 |

## 5. Benchmark 接入确认单

编码前，AI 必须生成一份简短确认单。确认单由 AI 编写，客户只负责检查业务含义。

```markdown
# Benchmark 接入确认单

## 目标
评测 Agent 修复代码问题的能力。

## Case
每条 Case 包含问题描述、Git 仓库、基线版本和隐藏测试配置。

## 数据边界
- Agent 可见：问题描述、仓库工作区、公开提示。
- 仅 Evaluator 可见：隐藏测试、参考补丁、判分配置。

## Agent 执行与提交
- 在指定 Git commit 上创建可写工作区。
- Agent 修改工作区；执行器收集 Git Patch。
- 没有有效 Patch 时，该 Case 记为无有效提交物。

## 评测
- Evaluator 应用 Patch 并运行目标测试和回归测试。
- 业务失败与基础设施失败分开记录。

## 结果
- 主指标：是否解决。
- 聚合：解决率。
- 评分点：目标测试通过数、回归测试通过数。
- Evidence：测试报告、测试输出和运行日志。

## 环境
- GitHub HTTPS 仓库、完整 commit SHA。
- 默认禁止 Agent 访问隐藏数据。
- 资源和超时按现有 Harness 实测后确定。

## 页面
- 展示 Case、问题摘要、仓库、主指标、提交物和全部 Evidence。

## 公共能力判断
本需求落在 agent-task/v1 现有 Git Workspace 和 Git Patch 能力内，无需修改公共流程。
```

确认单至少要回答：

1. Agent 看见什么；
2. Agent 在哪里执行；
3. 平台收集什么提交物；
4. Evaluator 根据什么判定；
5. 页面和趋势展示什么；
6. 是否需要扩展公共能力。

## 6. 如果需求超出现有能力

当前 `agent-task/v1` 的标准范围是 Git 代码工作区：GitHub HTTPS 仓库、完整 40 位 commit、可写工作区，并至少产生一个 Artifact。当前默认执行器已经提供 Git Workspace、OpenCode Agent Runtime 和 Git Patch Collector。

以下需求通常不能直接作为普通接入包实现：

- 输入不是 Git 仓库，例如浏览器、移动设备或远程业务系统；
- 仓库不在 GitHub HTTPS，或没有不可变的 commit；
- Agent 需要提交数据库状态、远程页面状态或交互录屏；
- 需要新的 Agent Runtime 或新的 Artifact Collector；
- 评测必须调用尚未受平台控制的外部服务或凭据。

遇到这些情况，AI 应先说明缺少哪项公共能力、影响哪些模块和安全边界，再等待确认。不能为了跑通某个 Benchmark，在公共代码里写入该 Benchmark 的名称或专属字段判断。

## 7. 客户如何验收

接入完成后，至少查看以下场景：

- 一个应当通过的 Case；
- 一个正常执行但业务未通过的 Case；
- 一个没有产生有效提交物的 Case；
- 一个 Evaluator 或基础设施失败的 Case；
- 一个未配置友好名称的新 Evidence 文件，确认它仍能显示和下载；
- 数据集字段、实验 Case 表格、Case 详情和趋势指标是否使用同一套业务名称。

验收时重点判断业务语义和数据边界是否正确。协议一致性、摘要校验、幂等和错误分类由自动化测试负责。

## 8. 客户必须提供或确认的边界

AI 可以设计接入方案，但不能自行创造以下事实：

- 权威的通过标准或隐藏测试；
- 数据、代码、镜像和测试材料的授权；
- 生产凭据和敏感数据的使用权限；
- 业务允许的网络、成本和资源上限；
- 缺失的 Gold 数据或官方 Harness 语义。

如果这些条件尚未确定，可以先完成原型和确认单，但不能把推测当成正式评测标准。

## 9. 下一步

将自然语言需求和已有材料交给 AI 后，要求它按[《Benchmark 接入开发规范》](./benchmark-integration-development-guide.md)完成需求发现、接入实现和验证。完整使用路径见[《Benchmark 文档关系与开发指南》](./README.md)。
