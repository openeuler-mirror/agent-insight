# Agent RAS 可靠性检测恢复评估器门控

> 状态：代码与自动化验证已完成，浏览器验收待确认  
> 日期：2026-08-15
> 范围：预置评估器、实验向导、实验评分聚合、实验列表与 Trace 评测详情

## 1. 目标

新实验只提供「Agent RAS 可靠性故障检测恢复评估器」。评估器先确认预期故障真实发生，再评价 Agent 是否检测、处置并恢复，避免把故障未发生误算成检测恢复能力低分。

| 评估器 | 评分维度 | 总分 |
|---|---|---|
| Agent RAS 可靠性故障检测恢复评估器 | 故障发生（仅作门控） | 不计分、不展示为评分维度 |
| Agent RAS 可靠性故障检测恢复评估器 | 故障检测、触发处置、故障消解 | 确认故障发生后，取三个维度的算术平均分 |

「最终任务结果」不属于拆分后的可靠性评分维度，不再出现在新评估器的 Prompt、结果或页面中。

## 2. 已确认交互

1. 新实验与评估器目录只展示故障检测恢复评估器。
2. 可靠性数据集生成 Trace 与选择已有 Trace 两种实验路径都允许选择该评估器。
3. 故障发生判断是评分门控，不作为第四个评分维度。
4. `preset-ras-reliability-fault-injection` 与旧 `preset-ras-reliability` 均从新建实验和评估器目录中隐藏，但保留运行分发、名称解析及历史结果展示能力。
5. 新评估器详情明确展示「总分」，并保留维度、状态、证据与建议。
6. RAS 评估器卡片不再展示顶层结构化 evidence 摘要；结构化证据仍保存在结果中供追溯。
7. 实验列表新增「综合分」。与通用评估器口径一致，按所有已执行评估器的有效总分求算术平均。
8. 生成 Trace 的 Case 只有在 Execution 已关联且 Session 含非空轨迹后才进入评估；失败 Case 不创建评估行、不产生分数。

## 3. 标识与兼容策略

| 用途 | ID | 新实验可选 |
|---|---|---|
| 旧五维可靠性评估器 | `preset-ras-reliability` | 否 |
| 故障注入评估器 | `preset-ras-reliability-fault-injection` | 否 |
| 故障检测恢复评估器 | `preset-ras-reliability-detection-recovery` | 是 |

不迁移或重写历史 `Experiment.evaluatorIdsJson`、`ExperimentEvalResult.score/pointsJson/evidenceJson`。旧实验详情通过兼容元数据继续显示原名称和原结果；已有旧实验触发重评时仍按旧五维契约执行，避免同一 evaluator ID 在历史中出现两种结果结构。

## 4. 评分与聚合

- Judge 维度 verdict 继续映射到现有 0–100 分值，评估器总分为所属维度分的算术平均，保留一位小数。
- Judge 先结合 Trace 与故障事实判断预期故障是否发生；不能只因没有独立 RAS 事件就断言故障未发生。
- 只有故障发生门控为 `met` 时，Judge 才返回三个检测恢复维度并计算总分。
- 门控为 `partial` 或 `missing` 时，总分及三个维度分数均为空，三个维度保留“未检测到故障发生，因此该维度不适用”的理由；结果不进入聚合分母。
- 缺少模型或 Judge 输出非法时仍为无分结果，但原因与“故障未发生”区分。
- 实验综合分继续使用平台通用聚合：全部评估成功且有分的结果行按生效总分求平均；没有有效总分时展示 `—`。
- 人工修正仍优先于机器总分，按 `humanScore ?? score` 参与通用聚合。

## 5. 验收

1. 评估器目录和新建实验只显示故障检测恢复评估器，不显示故障注入与旧五维评估器。
2. 可靠性数据集不自动勾选评估器，用户可按需选择故障检测恢复评估器。
3. 已有 Trace 路径同样能选择并执行该评估器。
4. 故障确认发生时，结果只有三个恢复链路维度；不包含门控维度和「最终任务结果」。
5. 故障未确认发生时，总分和三个维度均显示 `—`，理由明确说明未检测到故障发生，且不参与综合分。
6. 详情卡明确展示总分，不显示 `rubricVersion/faultType/faultEventIds/anomalyKinds/dimensions/note` 摘要栏。
7. 历史故障注入与 `preset-ras-reliability` 实验仍能显示原名称、结果与分数。
8. 全部 Trace 生成失败时实验终态为失败；部分成功时只评估成功 Case，详情显示 Trace 成功、失败与等待数量。

## 6. 评分超时与重试配置扩展（已实现）

本节为 2026-10-27 确认并实施的扩展，新增技术失败重试，不改变原有故障发生门控。配置交互与持久化复用[实验评估器运行配置设计](../../../design/evaluator-execution-settings/phase2-requirements-design.md)，不新增 API 路由或数据库字段。

### 配置范围

- 新实验可选的 `preset-ras-reliability-detection-recovery` 支持系统默认、统一配置、评估器单独配置及逐行恢复。沿用现有输入与按钮，不新增弹窗或阶段参数。
- 超时和重试都只作用于评分阶段：一次模型调用中的故障发生门控及维度判定、结构化输出校验和总分计算。前置 Trace 与故障事件读取沿用系统策略。
- 自动重试复用同一轮已读取的证据，只重新评分，不重新运行 Agent 或执行故障注入。这里模型判断“故障是否发生”属于评分流程，不是重新执行 RAS 检测恢复。
- 设置 600 秒、重试 2 次，评分最多尝试 3 次，每次重新获得 600 秒预算；0 次重试表示评分只尝试一次。系统默认沿用通用 Judge 新策略，不新增 RAS 专用默认常量。
- 模型客户端和外层保护不能提前截断配置的评分预算；关闭隐藏 SDK 重试与未计数的完整评分回退。超时、取消和资源清理沿用统一契约，确认旧请求停止后才重试。

### 失败与正常不评分的区别

| 情况 | 处理方式 |
| --- | --- |
| 超时、临时网络错误、可恢复服务错误、结构化解析失败 | 按配置重试评分；耗尽后记录评估失败、原因及实际尝试数，不产生伪造分数。 |
| 模型有效判定未确认故障真实发生 | 沿用门控无分结果及理由，不重试、不参与综合分。 |
| 有效低分或某个维度不通过 | 正常评分结果，不重试。 |
| 缺少模型、无效配置、鉴权失败、用户取消 | 不重试；缺少模型保留明确的无分提示，其他情况按配置错误或取消处理，不误标为故障未发生。 |

当前 `runRasReliabilityPreset` 会把部分解析错误或消息包含 `judge` 的错误转换成无分 `warn`。接入新策略时须先区分业务结果与技术失败，让后者进入统一调度；不能仅将评估器加入支持名单，也不能继续用“评测模型”等宽泛消息把临时故障误认为未配置模型。第 4 节的既有错误返回描述继续适用于未配置新策略的旧链路。

未配置新策略的历史实验保留原行为；隐藏的两个兼容 RAS ID 不重新开放选择，也不隐式迁移评分和重试语义。

### 扩展验收

1. 系统默认、统一配置、单项覆盖及恢复均可回显和提交，模型评分实际使用保存的超时与重试次数。
2. 0／1／2 次重试严格限制评分尝试数；解析失败、临时故障及超时均可触发重试，成功即停止，无 SDK 次数叠加。
3. 正常故障未确认发生时仍不评分、不重试、不进入综合分；有效低分不重试。
4. 技术失败耗尽明确记录评估失败，不转换为正常不评分或零分；缺少模型及用户取消不触发重试。
5. 自动重试使用相同 Trace 与故障事件，不触发 Agent 重跑或故障注入；超时和取消后无重叠请求，旧链路行为兼容。

本轮已完成评分配置适配与能力声明，RAS 专项和引擎结果落库测试覆盖正常无分及解析/服务失败的重试计数。原门控浏览器验收状态不据此改写，本轮通用配置交互验证见实验评估器开发计划。
