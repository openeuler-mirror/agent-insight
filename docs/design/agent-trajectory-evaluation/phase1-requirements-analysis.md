# Agent 执行步骤效率与执行过程质量评估器：Phase 1 需求分析

> 关联任务：[openeuler/opensource-intern#168](https://gitcode.com/openeuler/opensource-intern/issues/168)<br>
> 阶段：Phase 1 需求分析<br>
> 日期：2026-08-23<br>
> 基线：`master@0f8006e7`
> 状态：已通过（2026-08-24）

## 1. 背景与目标

Issue #168 要求提供两个独立的预置 LLM Judge：

- **Agent 执行步骤效率评估器**：从步骤必要性、路径绕路、资源消耗、步骤密度、重试与回退五个维度评价执行效率；
- **Agent 执行过程质量评估器**：从目标对齐、规划完整、推理连贯、异常处理、路径稳健、信息利用六个维度评价过程质量。

两个评估器均读取完整执行轨迹，返回 0–100 总分、各维度 0–100 分、中文结论、问题步骤或工具锚点，以及改进建议。Issue 给出的 24 个场景是必须逐条覆盖的验收集，但不能原样写入生产 Prompt 或代码分支。

本需求的目标是在现有实验评测链路内交付最小可运行闭环，不另建评测平台。

## 2. 当前仓库事实

当前仓库已经具备以下基础能力：

- `FaithfulPresetContext` 可向轨迹类评估器提供任务输入、最终输出、原始 `interactions`、压缩轨迹、Execution 和用户信息；
- `trace-summarizer.ts` 已能提取步骤类型、名称、参数摘要、结果摘要、耗时，以及全轨迹调用数和 Token 总量；
- `judge-llm.ts` 提供可测试的统一 Judge 调用边界；
- `EvaluatorOutput` 已支持总分、评分点、证据、建议和 `step-N` 锚点；
- 实验引擎已经具备注册、分发、重试、超时、并发和结果持久化能力；
- 现有 `preset-agent-trace-quality` 使用完整性、工具选择和冗余度三维口径，并被部分 Skill 对齐与质量分析链路读取。

因此，本需求不需要新增 Prisma 字段、API 路由或独立结果页面。主要工作位于轨迹事实、Judge Prompt、结构校验、确定性计分、实验适配和测试。

## 3. 已确认的产品决策

### 3.1 新建独立的执行过程质量评估器

新增稳定 ID：

```text
preset-agent-process-quality
```

该 ID 使用 Issue #168 定义的六维过程质量口径，由通用实验评测链路执行；其卡片在三个既有 Skill 评测页面沿用统一的 `status === 'ready'` 可见性规则，不增加按 ID 特殊隐藏。现有 `preset-agent-trace-quality` 仍保留原名称、三维口径、opencode runner 和旧轨迹入口，不因本需求改变行为。

### 3.2 兼容原则

- 历史评估结果不重算、不覆盖；
- 旧评估器的 ID、卡片元数据、runner、API 和消费者均保持原样；
- 新评估器使用独立 ID 和 `rubricVersion`，不复用旧三维结果的语义；
- 新评估器统一由 `experiment` surface 执行，并可在单次、批量和灰度三个 Skill 评测选择器中按既有 `ready` 规则展示；不进入旧 `/api/eval/trajectory/run` 入口；
- 不修改质量监控、Skill 对齐和其它旧消费者。

### 3.3 新增效率评估器

执行步骤效率使用新的稳定 ID：

```text
preset-agent-step-efficiency
```

该卡归入 `traj`，不依赖参考答案或显式 Tool/Skill 目录，不加入默认勾选集合，避免用户在未选择时额外触发一次 Judge 调用。

## 4. MVP 范围

### 4.1 必须交付

1. 一个可复用的轨迹事实层，向两个评估器提供同一套可核验步骤和统计。
2. 执行步骤效率五维 Judge、严格输出校验、代码聚合和严重问题封顶。
3. 轨迹质量六维 Judge、严格输出校验、代码聚合和严重问题封顶。
4. 两个评估器接入现有卡片、registry、实验分发和一致性守卫。
5. 每个评分点同时具有分数、状态、证据；问题可定位时提供 `step-N` 锚点和工具名。
6. Issue 的 24 个验收场景逐条建立测试与验收记录。
7. 在 openEuler 24.03 LTS SP4 环境运行真实评测闭环。
8. 更新评估器开发指南的维度台账、用户指南和本设计索引。

### 4.2 明确不做

- 不新增数据库表或字段；
- 不新增评估结果专属页面或仪表盘；
- 不提供用户可编辑权重；
- 不按模型价格换算货币成本；
- 不实现跨多次运行的同类轨迹排名；
- 不读取、推断或展示未记录的隐藏思维链；
- 不重算历史实验分数；
- 不把 24 个验收输入原句写入生产 Prompt 或代码特判。

## 5. 输入事实边界

MVP 以当前可观察数据为准。统一轨迹事实至少包含：

```ts
interface AgentTrajectoryStepFact {
  index: number;
  kind: 'user' | 'llm' | 'tool' | 'skill' | 'task';
  name?: string;
  argsSummary?: string;
  argsFingerprint?: string;
  outputSummary?: string;
  durationMs?: number;
  status?: 'ok' | 'error' | 'timeout' | 'unknown';
  errorSummary?: string;
  tokenCount?: number;
}
```

还应提供全轨迹统计：总步骤数、LLM/Tool/Skill/Task 调用数、总 Token、总耗时、重复调用候选、同参重试候选和连续同类调用候选。

数据缺失必须保留为“未知”，不得补造为 0、成功或失败。若底层 interaction 没有逐步 Token、错误码或显式推理文本，评估器只能使用实际存在的消息、工具调用、返回结果和状态变化，并在证据中说明限制。

## 6. 维度边界

### 6.1 执行步骤效率

| 维度 | 负责 | 不负责 |
|---|---|---|
| `step_necessity` | 无关步骤、无新增信息的重复步骤、无策略变化的重试 | 工具是否符合目录定义 |
| `path_detour` | 偏离主任务、上下文来回切换、明显可避免的长路径 | 最终答案本身是否正确 |
| `cost_efficiency` | 可避免的 LLM/Token/耗时浪费、低信息增量调用 | 缺少预算时做跨模型价格比较 |
| `step_density` | 过细拆分、可安全合并的连续同类操作 | 合法分页、分片和必要串行依赖 |
| `retry_efficiency` | 原地重试、过度回退、恢复路径明显膨胀 | 是否最终完成任务 |

### 6.2 轨迹质量

| 维度 | 负责 | 不负责 |
|---|---|---|
| `goal_alignment` | 执行过程是否持续服务原始目标 | 最终答案的独立准确性 |
| `planning_completeness` | 明显必要的前置、关键子任务和验证是否覆盖 | 凭空要求不存在的标准流程 |
| `reasoning_coherence` | 可观察决策是否有依据、前后一致 | 未记录的隐藏思维链 |
| `exception_handling` | 错误识别、验证、恢复、降级和终止是否合理 | 单纯执行失败即自动判 0 |
| `path_robustness` | 决策反复、试探后无依据回退、路径不稳定 | 多条独立轨迹间的统计方差 |
| `information_utilization` | 上下文和工具返回是否被正确、充分利用 | Tool/Skill 目录覆盖率 |

### 6.3 与现有评估器的边界

- `preset-agent-tool-selection` 继续负责工具必要性、工具匹配、参数、结果利用和调用顺序；效率卡不再重复评价目录级工具选择。
- `preset-agent-tool-utilization` 继续负责显式能力目录的覆盖和合理闲置；本需求不依赖能力目录。
- 结果准确性、答案质量和任务完成度继续评价最终结果；新的执行过程质量评估器只评价过程证据。
- 旧轨迹质量评估器仍保留完整性、工具选择和冗余度三维口径；新卡不替换、不迁移也不重解释旧结果。

## 7. Judge 与计分约束

Judge 只做离散语义判断，不直接生成总分、权重或封顶值：

```text
met = 100
partial = 50
missing = 0
```

每个 Judge 必须返回完整且唯一的维度集合。`partial` 或 `missing` 必须给出原因和建议；问题引用的步骤必须能在真实轨迹事实中找到，否则不得参与封顶。

MVP 以等权作为默认评审基线：效率五维各 20%，质量六维各 `1/6`。严重问题使用通用问题代码触发维度上限和总分封顶，解决普通平均无法满足 Issue 阈值的问题。最终权重和封顶表在 Phase 2 冻结。

## 8. 验收原则

### 8.1 自动化测试

- 24 个 Issue 场景逐条有测试，不抽样；
- Judge fake 注入统一发生在 `setJudgeLlmCallerForTest` 边界；
- 测试覆盖 Prompt 输入、Zod 校验、事实锚定、离散映射、基础分、封顶、`EvaluatorOutput` 和实验分发；
- 破坏计分公式或移除封顶规则时，相应测试必须失败；
- 注册一致性测试确保新卡只有一个执行归属。

### 8.2 真实环境验收

- openEuler 24.03 LTS SP4；
- 配置一个真实 Judge 模型；
- 运行 24 个场景并记录总分、子维度分、证据和是否达到阈值；
- 至少人工复核低分定位、合法重复、合理重试和单步回答四类边界；
- 区分“自动化契约通过”和“真实模型语义验收通过”。

## 9. Phase 2 必须解决的问题

1. 新六维质量能力放在 `engine/evaluation/` 作为 canonical 能力，还是只在实验域适配；必须保证新 ID 在实验入口下语义一致。
2. 新评估器如何与旧 `preset-agent-trace-quality` 完全隔离，避免改变旧 runner、API 和消费者。
3. 轨迹事实如何从原始 interactions 补齐逐步状态、错误和 Token，同时保持现有 `trace-summarizer` 兼容。
4. 两个 Judge 的完整问题代码、事实锚定和封顶表。
5. 无 Skill 关键动作时，规划完整性如何限制为“明显必要步骤”，防止 Judge 发明流程。
6. 没有预算或同类基线时，成本效率如何只评价可证实浪费，不把绝对 Token 高误判为低效。

## 10. Phase 1 完成条件

Phase 1 在以下事项复核后结束：

- 接受新增独立 ID、旧评估器保持不变的兼容原则；
- 接受 MVP 必做项与非目标；
- 接受两个评估器的维度边界；
- 接受“离散判断 + 代码聚合 + 通用封顶”的评分方向；
- 同意进入 Phase 2 输出详细需求设计。
