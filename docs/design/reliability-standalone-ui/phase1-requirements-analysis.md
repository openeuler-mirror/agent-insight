## 导读

**这是什么** —— 将 agent_ras 从现有链路追踪中**剥离**出来，新建独立的"AgentRAS 可靠性"导航分组（与"运行观测"同级），包含两个子页面：可靠性追踪（带故障统计的 Trace 列表）和故障注入与评测。

**为什么要做** —— 现有方案（agent-ras-migration D-003）将 RAS 标识嵌在链路追踪列表和详情中，导致 RAS 能力与通用观测混在一起，用户感知弱、不可独立导航。本期将 RAS 提升为与"运行观测"同级的独立一级入口。

**这一期做到哪**

1. 侧栏新增"AgentRAS 可靠性"分组，内含"可靠性追踪"和"故障注入与评测"两个子页面。
2. 可靠性追踪：展示有 RAS 事件的 Trace 列表 + 故障类型统计面板 + Trace 详情 + 故障节点定位跳转。
3. 故障注入与评测：故障类型目录 + 注入配置 UI + 多平台支持；本期用 mock 数据，后端后续补齐。
4. 清理现有链路追踪页中的 RAS 徽章/面板。

**明确不碰**

- 不改 agent_ras/core/ 检测算法。
- 不替换 /fault AgentDebug。
- 不将 RAS 控制面并入 OTel ingest 主路径。
- 故障注入本期不实现后端 API（仅 UI + mock）。

## §1 基本信息

### 1.1 背景

| 当前状态 | 问题 | 目标 |
|---------|------|------|
| RAS 异常事件通过 `/api/ingest/ras/v1/events` 落库 `RasAnomalyEvent` | 只在链路追踪列表显示 Badge + 详情面板 | RAS 独立为一等公民入口 |
| agent-ras-migration D-003 决策"仅链路追踪标识，无侧栏" | 用户感知弱，无法独立导航 | 新建独立分组 |
| 链路追踪是通用观测入口，混杂了 RAS 内容 | 概念边界模糊 | 从链路追踪中清理 RAS 标识 |

### 1.2 设计漂移说明

本需求**主动偏离** agent-ras-migration 的设计决策：

| 原决策 | 新决策 | 理由 |
|--------|--------|------|
| D-003: "无 `/ras` 页与侧栏项" | 新建独立分组 + 两个子页面 | RAS 能力成熟，需要独立入口 |
| D-008: RAS 与 OTel 并列安装 | 不变 | |
| D-003: 静态监控台弃用 | 不变 | |

agent-ras-migration 的 D-003 记录为"已漂移"，在开发计划中标注本次设计为更新源。

### 1.3 结构化信息

| 维度 | 内容 |
|------|------|
| Who | 平台维护者；关注 Agent 可靠性的开发者；需要注入故障做评测的 QA |
| When | 线上运行后查看故障分布；开发阶段注入故障验证鲁棒性 |
| What | 独立 RAS 导航分组 + 故障统计 + 故障列表 + 故障注入 UI |
| Why | RAS 能力独立成产品模块，不再作为链路追踪的附属 |
| Where | `(main)/agent-ras/trace` + `(main)/agent-ras/fault-injection` |
| How | 新路由 + 新组件；复用 RasAnomalyEvent 模型和 AgentTraceView 组件 |

## §2 核心能力

### 2.1 场景

| 编号 | 路径 | 触发 | 期望 |
|------|------|------|------|
| S-001 | 查看 RAS 故障总览 | 导航进入"可靠性追踪" | 看到有 RAS 事件的 Execution 列表 + 故障类型统计 |
| S-002 | 深入单个故障 Trace | 点击列表项 | 展开完整 Trace 树，异常节点高亮，可跳转定位 |
| S-003 | 注入故障 | 进入"故障注入与评测"，选择类型和平台 | 配置面板可用，提交后看到注入记录（本期 mock） |
| S-004 | 批量注入 | 选择多个故障类型 + 目标 | 批量提交面板可用 |
| S-005 | 平台切换 | 故障注入页选择平台 | 故障目录按平台过滤 |

### 2.2 功能需求

| ID | 需求 | 优先级 |
|----|------|--------|
| FR-001 | 侧栏新增"AgentRAS 可靠性"分组（与"运行观测"同级） | P0 |
| FR-002 | 可靠性追踪：按故障类型统计的列表页 | P0 |
| FR-003 | 可靠性追踪：单 Trace 详情 + 故障节点高亮 + 跳转 | P0 |
| FR-004 | 故障注入与评测：故障类型目录 | P0 |
| FR-005 | 故障注入与评测：注入配置面板（类型/平台/参数） | P0 |
| FR-006 | 故障注入与评测：批量注入 | P0 |
| FR-007 | 故障注入与评测：多平台切换 | P0 |
| FR-008 | 清理链路追踪页中的 RAS 徽章和面板 | P0 |
| FR-009 | 故障注入使用 mock 数据，预留 API 接口 | P1 |

### 2.3 非功能

| ID | 要求 |
|----|------|
| NFR-001 | 可靠性追踪列表性能不低于现有链路追踪页（分页 + 虚拟列表） |
| NFR-002 | 不可引入新色板（使用共享 `--color-*` / `--primary` 等令牌） |
| NFR-003 | UI 组件复用现有 `AgentTraceView`、`PageContainer`、`PageHeader` |
| NFR-004 | 故障注入 mock 数据结构预留扩展为真实 API 的字段 |

### 2.4 业务规则

| ID | 规则 |
|----|------|
| BR-001 | RAS 检测算法真源不变（Python `agent_ras/core/`） |
| BR-002 | 可靠性追踪只展示有 `RasAnomalyEvent` 的 Trace（无事件不展示） |
| BR-003 | 故障注入 UI 的故障类型定义应与 agent_ras/detectors/ 对齐 |
| BR-004 | 侧栏图标使用系统共享 SVG 令牌，不引入独立图标库 |

## §3 边界

### 做

- 新导航分组 + 两个子页面（全 UI）
- 从链路追踪清理 RAS 标识
- 故障注入 mock 数据

### 不做（本期）

- 故障注入后端 API 实现
- 从页面向真实 Agent 下发故障（本期保持 Mock）
- 实时通知 / WebSocket 推送
- 将 /fault AgentDebug 替换或合并

### 与现有模块关系

| 模块 | 关系 |
|------|------|
| 链路追踪 `/trace` | **解耦**：移除 RAS Badge 和面板 |
| RasAnomalyEvent 模型 | **复用**：作为可靠性追踪的唯一数据源 |
| AgentTraceView | **复用**：作为 Trace 详情展示组件 |
| AppSidebar | **修改**：新增 AGENT_RAS_TREE |
| 运行观测分组 | **并列**：新增同级分组 |

## §4 验收要点（概要）

1. 侧栏可见"AgentRAS 可靠性"分组，展开有"可靠性追踪"和"故障注入与评测"。
2. 可靠性追踪列表显示有 RAS 事件的 Trace，顶部有故障类型统计。
3. 点击列表项进入 Trace 详情，异常节点高亮，可跳转定位。
4. 故障注入页可浏览故障类型、切换平台、配置注入参数。
5. 链路追踪页不再显示 RAS 相关 Badge 和面板。
6. `npm run test` 通过。
