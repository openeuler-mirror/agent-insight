# Skill 工作台重构：需求分析

## 背景

当前 Skill 生命周期被拆分到 Skill Hub、生成、静态分析、触发分析、用例分析、A/B 测试和优化等多个入口。底层已经具备 Skill 版本、生成 Agent、静态评估、真实实验、优化草稿与发布能力，但用户必须理解平台内部模块，才能自行拼接完整流程。

本需求以以下两份材料为产品输入：

- `tmp/高保真/Skill对话工作台-高保真.html`：页面布局、交互状态和视觉参考。
- `tmp/高保真/phase2-requirements-design.md`：用户可见功能、状态机、业务规则和验收口径。

## 现状问题

### 1. 信息架构按内部能力拆分

`/skills`、`/skill-generator`、`/skill-eval` 和 `/skill-opt` 是并列入口。生成、评估、实验和优化没有共享的工作 Skill、版本或会话上下文。

### 2. 会话与任务状态割裂

- `SkillGeneratorSession` 只恢复生成对话和文件。
- `SkillOptSession` 只恢复某个 Skill 版本的优化对话、计划和草稿。
- 静态评估、触发分析、A/B 和通用实验分别保存状态，无法恢复到同一工作台会话。

### 3. 候选版本与正式版本边界不清

现有优化草稿的“采纳”操作会立即创建并激活 `SkillVersion`，随后删除该会话的草稿历史。当前实现没有“候选版 → 复测 → 用户确认 → 发布”的独立生命周期。

### 4. 评估口径容易混淆

静态质量、触发结果、任务效果和 A/B 结果在旧 Skill 分析页并列展示。静态规则只能证明结构与内容质量，不能证明真实任务成功率；候选版本没有复测时也不应展示推测的效果提升。

### 5. 实验执行已经部分统一，但产品链路仍分裂

通用 `Experiment` 已承担用例分析和部分 A/B backing 实验，但触发分析仍使用 `SkillTriggerEvalSet/Run`，A/B 编排仍以 `GrayscaleTask` 为主。三种入口没有统一配置快照和 Skill 工作台上下文。

## 目标

1. 用一个 Skill 工作台承接生成、上传、选择、评估、实验和优化。
2. 左侧对话负责意图澄清与生成协作，右侧固定页签负责确定性配置、进度、结果和历史。
3. 在同一会话中始终保持唯一的工作 Skill 与工作版本。
4. 生成与优化使用同一质量规则；上传内容保持原样，由用户显式评估。
5. 将触发分析、用例分析和 Skill A/B 收敛为统一实验流程的三种预设。
6. 建立候选版、复测、发布和放弃的可追溯闭环。
7. 所有历史实验、评估和优化记录绑定当时的版本或内容快照。

## 非目标

- 不新建第二套实验执行引擎。
- 不把全局 Agent、模型或框架对比收进 Skill 工作台。
- 不在本期删除旧页面、旧 API 或旧数据表。
- 不自动复测、不自动发布候选版本。
- 不在重构过程中升级依赖、修改 CI、修改 `.env*` 或 `package.json` scripts。
- 不一次性迁移全部历史触发分析和 A/B 数据；首期通过兼容读取保留可见性。

## 不影响其他功能的硬约束

### NR-001 旁路开发

新工作台先实现于内部路由 `/skill-workbench`。完成静态检查、专项测试和旧功能基线对比后，`/skills` 切换为正式工作台，原资产管理页迁到 `/config/skills`；`/skill-workbench` 与旧业务路由保留兼容。

### NR-002 只做增量数据库变更

Prisma 只新增可空字段、新模型和索引；不删除、不重命名、不收紧旧字段，不改变现有模型的默认行为。数据库同步不得使用 `--accept-data-loss`。

### NR-003 旧 API 保持兼容

现有 `/api/skills`、`/api/skill-generator`、`/api/skill-eval`、`/api/skill-opt`、`/api/debug/grayscale-tasks` 和 `/api/experiments` 的请求与响应契约保持不变。工作台使用新的 BFF 路由和内部服务适配器。

### NR-004 不复制执行内核

静态评估、通用实验、生成 Agent 和优化 Agent 继续复用现有引擎。新增代码只负责编排、快照、状态和兼容转换。

### NR-005 最后切流

只有在新链路通过定向测试、全量 `npm run test`、golden path 和边界场景后，才把 `/skills` 切换为工作台，并把 Skill 管理中心迁到 `/config/skills`。旧深层链接保留重定向或兼容页。

### NR-006 设计系统隔离

新 UI 只使用 `globals.css` 的共享令牌、`src/components/ui` 和 `.ai-*` 工具类，不新增 `--sk-*`、`--sa-*`、`--ev-*` 等局部色板。

## 用户场景

1. 用户新建会话，通过生成、上传或管理中心选择准备 Skill。
2. 用户查看 Skill 文件和当前版本，显式运行静态评估。
3. 用户选择触发分析、用例分析或 A/B 预设，进入统一实验向导。
4. 用户根据评估、实验或明确要求生成候选版本。
5. 用户查看证据和 Diff，决定是否使用原实验复测。
6. 复测完成后，用户发布、继续优化或放弃候选版本。
7. 用户恢复历史会话时，不重新运行任何任务。

## 验收标准

- 新会话仅展示三个不重复的 Skill 准备入口。
- 左右区域始终指向同一 Skill 和版本。
- 上传内容不被静默改写，不自动启动评估。
- 静态评估有持久化进度和版本/内容快照。
- 三种 Skill 实验使用同一实验执行能力，只改变预设。
- 候选版不覆盖或激活正式版本。
- 未复测候选版不展示推测的运行效果。
- 复测复制原实验快照，唯一主动替换变量是 Skill 版本。
- 发布必须二次确认；失败、取消和放弃均保留记录。
- 工作台未切流时，所有旧页面和 API 的既有测试保持通过。

## 已确认决策

| 编号 | 决策 |
|---|---|
| D-001 | 最终 `/skills` 为 Skill 工作台，Skill 管理中心位于 `/config/skills`。 |
| D-002 | 候选版本在确认发布前不创建正式 `SkillVersion`。 |
| D-003 | 旧历史首期兼容读取，不做破坏性批量迁移。 |
| D-004 | 旧页面先保留，最终按入口逐步重定向，不直接删除。 |
| D-005 | 开发以当前本地分支为基线，不拉取远端。 |
