# 基于 Trace 自动生成理想输出评测集：需求分析

更新：2026-10-13。本文定义当前业务需求和效果目标；[需求设计](phase2-requirements-design.md)说明实现契约，[开发计划](phase3-development-plan.md)列出当前证据与待完成项。

本特性的采样能力对外名称为**智能采样**。当前生产实现版本为 `trace-coverage-v6.35`；这是内部策略版本名，不是用户界面名称。已冻结的 v4/v5 任务按原版本恢复。生产默认已确定，但产品验收与效果目标分别判定；不存在相对 v5 的覆盖、质量、耗时或内存门槛。

## 1. 背景与目标

用户已有 Agent 执行 Trace，希望减少整理评测样本的工作。用户选择平台、Agent、时间范围和生成数量后，系统自动提取问答、去重、采样，并发布一个理想输出评测集，继续使用现有数据项管理和评测入口。

生成不依赖人工标签、LLM 或发布前审核。参考输出直接来自历史回答，发布不表示答案已被验证正确；不判断输入能否脱离对话历史独立执行。用户可按评测目标编辑生成结果。

效果目标是：在规定的数据集、数量和预算条件下，智能采样在开发池保留的对应指标超过微软公开实验数值，五个独立新来源仅与同池随机采样比较覆盖及指定质量。均值结果与独立统计、产品验证分别判定，不表示整体目标已经完成。

## 2. 范围与产物

每次成功生成一个 `ideal_output` 数据集，每条数据只有以下两个业务字段：

| 字段 | 约束 | 来源 |
| --- | --- | --- |
| `input` | 非空文本 | 对应轮次的用户输入 |
| `reference_output` | 非空文本 | 对应轮次可确认的最终助手回答 |

名称和描述属于数据集信息；内部 ID、状态和兼容存储字段不作为额外业务列。类型固定，不支持增加列或切换类型。

首期包含后台生成、来源临时冻结、结构过滤、精确去重、多样性采样、进度、取消、失败回填、恢复与既有评测衔接。不包含语义上下文过滤、自动纠错、自动脱敏、人工审核、手动发布、主题聚类、版本库、专属评测 Runner 或业务文档生成。预留内容处理接口，当前仅透传。

不为本功能新增 Trace 采集证据字段或额外的原始数据存储；所有问答判断在生成时基于已有 Trace 数据完成。

## 3. 功能需求

### R01：入口与配置

入口为 **评测数据集 → 新建评测集下拉菜单 → 基于 Trace 生成**，菜单项带图标。打开或取消配置不创建任务。

| 配置 | 约束 |
| --- | --- |
| 名称 | 必填，首尾去空白后 1–50 字符 |
| 描述 | 可选，最多 200 字符 |
| Agent 平台 | 单选，产品支持且当前身份可访问的历史 Trace 平台 |
| Agent | 单选，显示所选时间范围内的 Trace 数量；按稳定身份区分同名 Agent |
| 时间范围 | 最近 24 小时、7 天或 30 天；默认 7 天；提交时固定绝对起止时间 |
| 生成条数上限 | 1–500 整数，默认 20 |

生成服务在主服务启动流程返回后后台初始化，不阻塞其他功能。初始化未完成时，配置界面显示等待提示并禁用生成，自动检查就绪状态；初始化失败时说明原因并支持重试。直接请求生成接口同样受就绪保护，不能提前创建任务。

必填星号为红色。没有有效 Agent、选项加载中或配置无效时禁用“开始生成”。切换平台或时间范围清空 Agent；重新选中有效 Agent 后按完整配置恢复按钮状态，旧异步响应不能覆盖新选项。

### R02：平台与 Agent 目录

平台汇集现有安装目录和已注册适配器并归一别名，不限于 OpenCode/WorkBuddy。平台是否有数据按当前身份可访问的全部历史判断；Agent 数量按所选时间范围的 Execution 记录统计。历史平台近期没有 Trace 时保留平台选项、显示 Agent 空态。

Agent 使用执行记录中的身份信息区分；不要求必须存在独立的 Agent 注册记录。选项中的 Trace 数表示来源执行数，不表示结构检查后的候选数；后续可排除子 Agent 或异常执行。

### R03：提取、去重与采样

按已存储消息顺序，以每条用户消息划分轮次，提取该轮最终助手回答。一条 Trace 可生成多条数据项。无需原始模型请求或额外轮次证据，不因多轮、历史上下文或指代词过滤样本；不补写问题或拼接历史。

保留结构检查：执行已结束且没有明确执行失败；输入为完整非空文本；回答存在且没有明确失败或截断；问答归属不存在已知冲突；回答之后没有未完成的工具活动等。某轮不合格只排除该轮，执行级错误可排除整个来源。完整规则见设计 §4。

- 输入与回答均相同才合并；同输入不同回答保留为不同候选，不按语义判错。
- 同输入共享文本特征，重复出现不增加采样权重。
- 根据输入文本规则进行任务归类；根据已有工具顺序和恢复、重试、委派记录构造行为特征。不使用参考回答、质量评分或隐藏标签判断任务类型与文本距离。
- 默认生成使用智能采样（当前实现版本 `trace-coverage-v6.35`）：保留任务与真实行为，按全局输入长度预算和分布约束优化词项覆盖，再按词项共识、长度与重复片段比例选择参考回答；不验证语义或事实。所有特征仅在生成过程中使用，不增加 Trace 存储。旧 v4/v5 任务按冻结版本恢复；没有行为信息时仍可生成。
- 若去重后有 N 条有效候选，上限为 K，则成功生成 `min(N,K)` 条。N=0 时提示失败，不发布空的生成结果。

例如三条 Trace 分别提取 2、1、2 轮，得到 5 条候选；若无重复且上限 20，最终为 5 条，并非固定为 3 条。

### R04：进度与本次筛选明细

进度显示读取 Trace、筛选与去重、任务与行为归类、多样性采样、生成数据项、保存数据集六个阶段；阶段进度不等于已处理 Trace 的百分比。后台成功后自动发布，“完成”仅关闭窗口。

筛选明细根据规则执行结果统计，不由 LLM 生成：读取 Trace 数、保留 Trace 数、候选数、重复数、因上限未入选数，以及排除原因涉及的 Trace/轮次数。同一 Trace 可既保留又跳过部分轮次，原因涉及的 Trace 数可能重叠。

明细仅供本次窗口查看，关闭后不保留用于回看的数据。列表无“生成详情”按钮；关闭不取消生成，也不删除已发布数据集。生成中和失败卡片仍可打开进度或错误信息，但不恢复已清除的明细。

### R05–R06：状态、编辑和评测

| 状态 | 进度窗口 | 编辑信息 | 数据项与评测 |
| --- | --- | --- | --- |
| 生成中 | 取消可用，完成禁用，无返回 | 禁用 | 禁止修改与评测 |
| 异常 | 取消、返回可用，完成禁用 | 回填生成配置 | 禁止修改与评测 |
| 已发布 | 完成可用，取消禁用，无返回 | 修改名称和描述 | 查看、添加、编辑、删除、导入双字段数据；非空时可发起评测 |

关闭窗口、刷新或离开页面不取消任务；网络读取失败不能被当成任务生成失败。

失败进度“返回”先清理旧任务，再回填配置；此后取消配置不会恢复旧记录。失败卡片“编辑信息”先回填，取消编辑仍保留旧记录，重新提交时才清理旧任务并创建新任务。时间范围恢复为原时长，新提交重新计算起止时间，并重新检查 Agent 是否可用。

已发布数据集独立于成功任务记录存在。编辑信息不重新生成或清空用例；数据项编辑保持双字段与评测投影一致。删空后仍为已发布，但不能发起评测。

### R07：取消、删除与成功清理

生成中取消、失败返回、失败重提和列表删除复用后台清理。清理必须停止旧任务，清除其拥有的数据集、临时来源、中间结果、错误及任务记录，防止迟到结果重新发布。清理失败保留恢复状态并提示，不提前宣布删除成功。

**成功发布并完成临时文件清理后删除任务记录；失败或未完成任务继续保留。** 失败任务自动清理临时文件，但保留错误和配置供查看、回填。成功清理暂时失败时保留任务并重试，已发布数据集仍存在。

重复提交同一创建请求不能因成功任务记录已删除而再建数据集；删除后的旧请求不能使数据集复活。系统仅保留不含正文的有期限操作回执处理重试。数据集无成功任务记录时仍能查看、编辑、评测和删除。

所有清理不删除原始 Trace、其他数据集或已有实验的独立案例副本。

### R08：权限、后台运行与资源

接口基于经过验证的身份校验归属，不接受任意 `query.user` 越权。需要常驻 Node 服务、SQLite/Prisma 和可写任务目录；不支持时明确报错。

实例最多 4 个 Worker 同时生成，同一用户可占用 4 个槽位，其余进入 FIFO 队列；最多接受 20 个未完成任务。取消或线程异常应隔离到对应任务；重启从持久状态恢复，不重复发布。

不以固定文本长度直接淘汰有效样本。当前已分页读取来源、分块哈希及分步计算；候选、单来源消息及签名仍占用内存。全流程磁盘索引、有界内存和任意规模的取消延迟保证尚未完成，不作为现有能力宣称。资源不足应明确失败，不能悄悄丢弃大样本后宣称完整成功。

### R09：兼容性

旧数据集的新生成字段为空，继续原行为。手工创建、导入、单条 Trace 回流、轨迹、可靠性和 Benchmark 流程不被强制转型。本来源的生成及后续数据项保存不调用模型提取关键观点，既有其他来源保留原逻辑。

既有数据集不会随提取规则变化自动增加用例；需要采用当前规则时重新生成。

## 4. R10：效果目标与验证范围

### 4.1 微软公开实验对照目标

必测数据集为 WildChat、Dolly、No Robots、OASST2、ShareGPT-GPT4、UltraChat、HelpSteer2、Summarize from Feedback，共八个。目标按数据源和指标逐项判断，不以平均收益抵消某一数据源的失败。

微软参照来自[微软公开实验报告](https://techcommunity.microsoft.com/blog/azure-ai-foundry-blog/intelligent-sampling-in-microsoft-foundry-the-science-behind-selecting-better-pr/4523722)。覆盖增幅使用本地采样相对本地同池随机抽样的独立输入词项数增幅，与微软公开增幅作数值对照：

| 数据集 | 微软公开覆盖增幅 | 本地覆盖目标（微软值＋5 个百分点） |
| --- | --- | --- |
| WildChat | +44.8% | ≥49.8% |
| Dolly | +5.7% | ≥10.7% |
| No Robots | +44.5% | ≥49.5% |
| OASST2 | +55.7% | ≥60.7% |
| ShareGPT-GPT4 | +86.3% | ≥91.3% |
| UltraChat | +49.3% | ≥54.3% |

有人工评分的数据源还需满足以下要求。下限仅用于对应开发池和原量纲，不能跨标注口径套用：

| 数据源 / 指标 | 微软公开结果 | 对应开发池目标 |
| --- | --- | --- |
| OASST2 / quality | 相对随机 +8.1% | 均分 ≥0.729，且相对本地随机增幅超过 +8.1% |
| Summarize from Feedback / overall | 总体相对随机 +8.3% | CNN-DM/test、TLDR/valid2、TLDR/valid1 各自相对本地随机 ≥+10%，分别验收；不把微软总体结果写成各分层结果 |

摘要 accuracy、coverage、coherence 均单列，不以 overall 掩盖退步。旧开发池 TLDR/valid2 的 coherence 下限为 6.339；其他摘要防退步条件沿用本地随机/v4 对照。上述下限是当前认可的验收标准，不代表来自微软的标准。

本节保留的微软对照目标是“超过公开实验数值”。微软与本地的来源快照、候选池及处理协议未完全对齐，因此达标不能直接宣称算法严格优于微软。严格算法比较须另取得同池、同预算、同指标的微软结果。未披露的指标不补造，未有答案真值的数据源不宣称正确率提高。HelpSteer2 的 helpfulness、correctness 不纳入开发池和新来源的目标或结果展示。

### 4.2 五个独立新来源纳入必测目标

以下五个来源均列为正式验收项，不能用开发池达标替代。它们是不同取数范围的验证池，并非五个从未出现过的数据集名称；SummEval 是新增外部摘要数据集。

五个新来源统一只与同一个候选池的均匀随机采样比较：两种方法使用相同候选、样本数和冻结验证协议，不再使用微软公开增幅或 v4/v5 作为验收门槛。§4.1 除取消这两项 HelpSteer2 门槛外，其余开发池目标保持不变。

| 验证来源 | 取数范围 / 当前有效候选数 | 效果要求 |
| --- | --- | --- |
| HelpSteer2 | 官方 validation；924 条 | 覆盖相对同池随机提高 |
| No Robots | 官方 test；489 条 | 覆盖相对同池随机提高；没有人工质量评分，不用覆盖代替质量结论 |
| OASST2 | 官方 validation 的根问题直接回答；1,949 条 | 覆盖相对同池随机提高；已标注入选回答的 quality 均值不低于同池随机；披露评分分母 |
| SummEval | 新文章组的专家摘要标注，关联 CNN/DailyMail 正文；1,454 条 | 覆盖相对同池随机提高；consistency/fluency/relevance 均不低于同池随机，coherence 采用下述容忍范围；没有微软对应实验值，不虚构比较 |
| WildChat | 此前未采集的数据页；5,000 条 | 覆盖相对同池随机提高；没有人工质量评分，不用覆盖代替质量结论 |

这里的候选数是已验证快照的有效数量，不是后续取数的最低数量或强制截断规则。开发池质量绝对下限不机械套用新来源：新 OASST2 包含未评分回答；SummEval 为 1–5 量表，与 Summarize from Feedback 不同。

五个新来源共有 10 项效果均值目标：5 项覆盖、OASST2 的 1 项 quality、SummEval 的 4 项质量。覆盖要求相对同池随机增幅 >0%；质量指定轴除摘要 coherence 外，均值不得低于同池随机，并检验量表跨度 1% 的非劣界；摘要 coherence 保留相对随机下降不超过量表跨度 0.6% 的容忍范围，SummEval 对应 0.024。均值通过与统计支持分别记录，样本不足不能标为完整通过。

这些来源已完成一轮冻结验证，但“运行完成”不等于“目标通过”。若继续据此调参，本批即成为开发回归数据，下一轮独立确认必须另取未参与优化的来源；不能继续称其为盲测。

### 4.3 共同约束与验证边界

- 生成与采样不读取人工评分、数据集名称或微软指标；标签只用于选样后的评估，不使用 LLM 或来源特定规则。
- 固定来源、映射、去重、算法版本、种子和输入预算，保存入选 ID 与指标复算证据。原始及同 token 覆盖均报告，v5 仅供历史参考，不参与通过判断。
- 独立来源须排除全部旧原始映射中的来源组、相同输入及词法近重复输入；按来源组隔离，不把同一来源的多种子当作独立人群样本。
- 验证 K=20/100/500、数量不足、预算不可行、已观测行为与长文本；公开聊天没有真实工具行为时，另用真实 Trace 验证行为保留。
- 按指定规模和并发记录实际耗时、峰值内存、取消及清理表现；不设相对 v5 的倍数目标，绝对资源 SLA 尚未约定。

## 5. 验收与交付

R01–R09 按可观察行为及正反例验收，覆盖真实 SQLite/Worker、鉴权、恢复、清理、幂等和实际 Web UI。R10 同时要求八源公开值目标、五个新来源目标、预算与数据隔离、统计证据和如实报告；不能仅凭生成可用或报告完成宣布整体目标完成。

交付包括生产源码、数据库增量结构、Worker 构建、用户/开发者指南及验证材料。逐平台真实格式、完整部署链路、大规模并发和既有入口兼容的缺口在[开发计划](phase3-development-plan.md)逐项登记。本文与[需求设计](phase2-requirements-design.md)只描述当前要求与实现，不保留逐轮迭代记录；实验指标在[对比报告](eight-datasets-comparison-report.md)中查证，原始材料按报告中的历史 Git 提交恢复。
