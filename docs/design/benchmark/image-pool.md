# Benchmark 评测镜像池方案

## 1. 范围与基本规则

镜像池是 Benchmark 评测服务的公共能力，解决两件事：控制缓存镜像占用，保证有限磁盘上的持续评测；提前准备近期要用的镜像，减少实验等待。SWE-bench 作为首个接入示例，公共实现不依赖其仓库命名、patch 格式或 Harness。

镜像池默认开启，正常启动服务无需填写单镜像大小或临时空间大小。显式传 `--evaluator-env IMAGE_POOL_ENABLED=false` 可关闭；预取仍是独立可选能力，不因镜像池默认开启而自动启用。

第一版只保留四项机制：

1. 保留高水位预警和安全预留：提前检查近期镜像需求，不足时逐个回收，够用即停止。
2. 在用镜像禁止删除，近期要用的镜像优先保留，其余按 LRU 淘汰。
3. 在 Agent 执行或前一个 case 运行期间，提前准备当前及下一个 case 的镜像。
4. 同一镜像只拉取一次，限制全机镜像操作并发。

只管理各 Benchmark 接入包明确声明、由本服务登记拥有的评测镜像，不自动接管机器上的全部镜像。不依赖 Docker 镜像的 Benchmark 无需接入。

同一个 Docker daemon 上的不同 Benchmark、用户和实验共用一个镜像池、一份空间预算和镜像操作并发限制，不为每个 Benchmark 重复分配磁盘容量。不同机器分别管理自己的池。用户配额、实验/case 运行并发、CPU/内存分配和任务公平排队不属于本方案。

| 公共镜像池负责 | Benchmark 接入包及外部执行流程负责 |
|---|---|
| 空间预算、高水位、安全预留与按需回收 | 声明每个 case 需要的镜像，一个 case 可以需要多个镜像 |
| 拉取去重、镜像操作并发、使用保护和 LRU | 解析镜像来源、版本、架构及允许使用的范围 |
| 固定镜像身份，准备近期镜像并返回状态 | 提供当前/下一个 case 的需求，决定何时执行 case |
| 记录镜像等待、拉取和删除耗时 | 运行 Benchmark 自身的评测逻辑，清理容器后释放使用标识 |

公共层使用接入包提供的结构化镜像描述，并统一校验调用方身份和管理归属；不硬编码 SWE-bench 仓库前缀，也不接受任意命令作为拉取逻辑。镜像已在池中不代表所有 Benchmark 都有权使用，命中路径仍校验该接入方的允许范围。

## 2. 空间控制

保留高水位和安全预留，不恢复低水位。两者分工不同：

| 控制项 | 作用 | 默认口径 |
|---|---|---|
| 高水位 | 提前唤醒后台检查，根据近期镜像需求准备回收，减少临时等待 | 镜像池容量的 90% |
| 安全预留 | 给下载解压、运行写入等留出空间，约束新镜像能否开始拉取 | 可管理空间的 30%，由服务自动计算 |

按机器实际空间计算，不固定为某台机器的 GB 值：

```text
可管理空间 = 当前可用磁盘空间 + 镜像池占用估计
安全预留 = 可管理空间 × 30%
镜像池容量 = max(0, 可管理空间 - 安全预留)
高水位 = 镜像池容量 × 90%
```

不再要求用户设置 `IMAGE_POOL_ESTIMATE_BYTES` 或 `IMAGE_POOL_TEMPORARY_BYTES`，旧配置不再读取。下载解压及运行写入由按比例计算的安全预留覆盖，不建设自动学习或高分位预测机制。

case 对应的镜像由接入包确定，拉取需求按以下顺序处理：

```text
case → 确定镜像地址 → 检查本地镜像
                         ├─ 已有：直接复用，不查询远端大小
                         └─ 缺失：优先接入包有效估值，否则查询对应架构的镜像清单
                                  ├─ 成功：按压缩层总大小保守估算
                                  └─ 超时/失败/格式不支持：内部默认估值
```

远程查询复用 `docker manifest inspect --verbose`，只读取元数据、不下载镜像层。一个镜像需求的所有候选源共用总计 2 秒预算，超时终止查询子进程；不对每个源分别等待 2 秒。成功结果缓存 15 分钟，失败回退缓存 1 分钟，最多 256 项，同一需求合并查询。成功按压缩层总大小 × 4 估算（内部下限 256 MiB），无法查询时暂用内部 8 GiB 估值；这是估算规则，不是池容量或用户配置项，不保证未知大镜像不会超过估值。不精确扣除本机已有共享层，允许保守高估。

每次准备镜像，只判断：

```text
当前可用空间 >= 安全预留
              + 已接受拉取尚未落盘的镜像空间
              + 本次镜像预计新增空间
```

- 满足条件：登记空间预留，开始拉取。
- 不满足：选择一个可回收镜像删除，重读实际可用空间，再判断。
- 没有可安全回收镜像且仍不足：返回明确的容量错误，当前 Case 失败，不无限等待或换源重试；后续 Case 沿现有实验流程推进并重新检查容量。
- 只计算即将准备的镜像，不为整轮实验一次性预留空间。所有 Benchmark 的在途预留合并计算；同一镜像需求被多个请求共享时预留一次，运行写入使用公共安全余量。拉取槽位被占用时仍遵守原等待期限。

镜像池占用达到高水位，或加上已接受拉取的新增占用后预计达到高水位时，唤醒后台检查当前/下一个镜像的空间需求，有缺口才提前回收。高水位是提前检查的信号，不是固定的删除终点：空间已经够用时，即使仍高于高水位也不继续删除；没有近期需求时，不为预警本身批量清理。

每次准备镜像仍必须检查真实可用空间，不需要等达到高水位才检查。后台保持每 30 秒检查安全余量，不增加拉取过程中的高频检查。外部数据增长挤占安全预留时逐个回收；安全检查不通过时不启动新拉取，没有可回收候选则报容量错误，满足条件立即放行。高水位不意味着删除固定数量或固定比例，任何时候都不做“清一半、再清全部”的两轮批量回收。

以此前 119 的粗估说明分母：可用约 61GB、池占用约 7GB，则可管理空间约 68GB，安全预留约 20.4GB、池容量约 47.6GB、高水位约 42.8GB。这些是计算示例，不是部署固定值；新机器使用自己的空间数据。

读取 Docker 实际数据文件系统的可用空间。镜像占用使用缓存的估计值、在同一 daemon 内按唯一 image ID 去重并考虑共享层，不建设精确层归属系统；无法准确统计时标明估计质量。跨 Benchmark 复用依据实际镜像身份和架构，不能仅因 case 名称或 tag 相同就合并。不能直接把所有 tag 的 SIZE 相加，也不能把缺失统计当成 0。全量统计在后台更新，不放进每个 case 的同步路径。删除后是否够用以真实可用空间为准。

支持本机 Linux 传统 Docker 存储，以及 macOS Docker Desktop 的传统/containerd 存储。Mac 的“当前可用空间”取 Docker VM 数据盘与 Docker.raw 所在宿主文件系统可用空间的较小值，再沿用上面的安全预留与高水位公式。启动前核实宿主探测目录与 Docker.raw 同盘，并只读验证实际数据目录；错误或未知布局不放行。containerd 的逻辑镜像大小仅作为估计，回收后不假定立即释放同等物理空间。LRU、租约、预取与 Linux 共用，不增加一套 Mac 调度逻辑；不支持远程 daemon、Colima、OrbStack 或 Linux containerd 独立数据盘。具体配置与故障处理见[部署指南](../../developer-guide/benchmark/service-deployment-guide.md#53-可选跨-benchmark-共享镜像池)。

例如扣除安全预留和已接受的拉取预算后，只剩 1GB，下一镜像预计新增 3GB，就先回收约 2GB。删除一个镜像后若空间已经满足，就立即停止，不继续清到某个比例。镜像大小未知时采用保守估值；拉取期间监测余量，估值不足时停止准入新操作并回收或报错，不能保证未知镜像绝不会超过估值。

Docker 拉取明确返回 `ENOSPC`、`no space left on device` 或 `disk quota exceeded` 时，归类为不可自动重试的 `IMAGE_POOL_SPACE_LOW`，不再切换镜像源下载；确认拉取返回后释放该操作预留，记录当前 Case 失败，由原平台回调及后续执行流程推进。若只是连接中断或等待超时，不能认定 Docker 已结束；结果不确定时继续保留在途预算并阻止新拉取。安全预留不是物理磁盘配额，突发外部写入仍可能填满磁盘；此时日志和状态持久化也可能失败，不能承诺后续 Case 无条件继续成功。

## 3. 淘汰规则

采用「使用保护 + 近期准备保护 + LRU」，不实现普通/复用双队列、跨实验频次、历史热门保护或复杂打分。

删除候选按以下顺序确定：

1. 排除任一 Benchmark 正在使用、正在拉取、正在删除，以及仍被任何容器引用的镜像。
2. 尽量排除外部明确告知即将使用的镜像，仅保护当前准备窗口，不保护整个实验列表。
3. 在剩余镜像中选择最久未使用的一个，删除后重新检查空间。

近期准备保护可以撤销，在用保护不能撤销。实际使用请求缺空间时，可以回收仅为未来 case 准备但尚未使用的镜像；普通预取不应为了自己反复淘汰其他有效准备窗口的镜像，空间不足就推迟。

镜像使用时间在实际使用时更新，预拉取不算一次使用。该策略不保证跨实验命中率最优，但近期使用信息可以减少刚准备好就被删除的问题；第一版先用实际等待时间验证效果，再决定是否需要更复杂的缓存算法。

只删除本服务拥有的镜像引用，不强制删除。镜像源别名指向同一镜像时一起核对；去掉一个 tag 不等于释放了镜像空间。平台镜像、构建缓存和 Volume 不在自动删除范围内。

## 4. 提前准备与外部配合

完整 case 列表和实验进度仍由现有实验执行流程管理，镜像池不再维护一套完整实验计划及其状态机。

外部只需告诉镜像池「当前 case 要准备哪些镜像、下一个 case 要准备哪些镜像」。流程如下，镜像准备与 Agent 执行、评测并行推进；无 Agent 阶段的 Benchmark 可在前一个 case 执行期间准备：

```text
时间向右 ───────────────────────────────────────────────────────────→

外部流程：更新准备窗口 → Agent 执行 / 生成产物 → 获取镜像 → 当前 case 评测 → 更新窗口
镜像池：                准备当前镜像 ──────────→ 就绪
                                    准备下一镜像 ─────────────────→ 等待使用
```

图中箭头表示可重叠的工作，不保证每次都能提前完成。当前镜像先准备，已就绪且有空间、拉取槽位时再准备下一个；获取镜像时仍未就绪，就只等待剩余准备时间。获取镜像时登记使用保护，评测容器清理后释放。下一窗口由外部更新，镜像池不自行推进实验。

准备窗口固定为当前及下一个 case，不做可变窗口预测；这是 case 数量限制，不要求每个 case 只能使用一个镜像。多个必需镜像逐个准备，调用方确认所需镜像全部就绪后才运行；中途取消或失败时释放不再需要的使用标识，不能带着缺失镜像启动评测。

每个实验的更新替换旧窗口；实验取消或窗口过期后取消尚未开始的预取、解除该实验的软保护。已经在用的镜像和其他实验的准备关系不受影响。窗口以 Benchmark 标识、实验标识和调用方标识隔离，带递增序号，防止不同 Benchmark/实验互相覆盖、迟到消息恢复旧窗口。

同一镜像的准备请求合并。实际使用请求优先于预取；全机默认最多同时拉取 2 个不同镜像，其中预取最多占 1 个槽位。删除并发固定为 1，每删一个就重新判断是否继续，不建设自动 I/O 调参控制器。

准备阶段不占用 case 的运行名额，也不改变 case 执行顺序。拉取和删除在后台进行，但仍可能竞争磁盘 I/O；通过固定的小并发控制影响，是否需要调整通过实际实验耗时判断。

准备信息必须能在 Agent 执行或前一个 case 运行期间到达目标评测主机。当前服务只执行单个评测作业，因此需要现有实验执行接入层提前传递这些信息；不能只在产物已生成、开始评测后才发起准备。先核实并复用已有鉴权通信通道，不为此建设新调度器。接入未完成或没有窗口信息时，按需拉取仍可独立工作，不宣称获得预取加速。

## 5. 管理与使用保护

公共实现放在评测服务侧，复用现有评测服务作为本机镜像池的管理入口，不新增独立 Pool Manager 进程。管理模块异步处理镜像操作，各 Benchmark 接入包与 Runtime 通过统一客户端访问，不能各自实现独立的容量预算或回收器。

运维统一使用 `scripts/evaluator.sh`：`images list` 查看池内登记，`images purge --dry-run` 预览空闲候选，`images purge` 在服务运行期间清理池拥有的空闲镜像；`stop` 立即停服，`stop --purge-images` 停服后清理全部安全可删的受管 Case、Runtime 和 Controller 镜像。在线命令通过数据卷内的 Unix Socket 进入现有 Controller，与评测请求共用互斥和保护，不新增 HTTP 路由。存在拉取操作时不执行在线批量清理；原有镜像、在用镜像、准备窗口保护镜像、容器或池外引用镜像均保留。

每个 Docker daemon 只允许一个镜像池管理入口；部署需保证这一点。第一版不做多管理者选主或分布式协调。同机多个用户不影响这一约束，未来增加多个 Controller 时也必须继续共用一个入口。

使用保护简化为按请求标识登记使用者：

```text
请求使用镜像 → 登记使用保护 → 确保镜像就绪 → 返回固定镜像引用
           → 调用方运行 case → 清理容器 → 解除使用保护
```

- 使用登记与删除状态变更必须互斥，避免在「镜像已就绪、容器尚未创建」期间误删。
- 释放操作幂等，使用标识关联 Benchmark、实验及任务；同镜像有多个使用者时，跨 Benchmark 的所有使用者全部释放后才可回收。一个接入方不能释放另一个接入方的使用保护。
- 正常结束由调用方释放，取消或异常退出由现有任务清理流程补偿；服务启动时结合未完成任务记录与 Docker 容器状态对账。
- 不引入独立的租约 TTL、定时续租和 generation 协议；必须能识别使用者对应的任务/Runtime 生命周期。状态不确定时继续保护并报告异常，不能仅因没有容器或一段时间没消息就删除。
- 等待或取消不能直接宣称 Docker pull/delete 已停止。操作未确认结束前继续保留其空间预留和保护。
- 长时间拉取或删除不能占住管理模块的全局锁；其他镜像的命中与释放操作仍可处理。

只持久化必要的镜像归属、最近使用时间和未完成操作记录，使用简单原子状态文件，复用现有任务记录恢复使用关系。第一版不建设自定义操作日志回放系统。恢复期间先对账后删除；单靠 Docker 镜像清单无法证明哪些镜像属于本服务，归属不明的镜像不自动接管。

若现有任务记录无法覆盖 Runtime 生命周期，应先补齐这条可靠的关联再启用自动删除；不能用裸引用计数替代异常恢复。

## 6. 最小接口与配置

内部只保留三类能力，传输方式复用现有服务通道：

| 能力 | 职责 |
|---|---|
| 更新准备窗口 | 提交 Benchmark/实验标识和当前/下一个 case 的镜像列表；清空窗口仅撤销该调用方未开始的准备 |
| 获取镜像 | 校验接入方声明范围、合并拉取、等待空间、登记使用者；成功返回固定镜像引用和使用标识 |
| 释放镜像 | 清理容器后解除使用保护，更新最近使用信息 |

镜像等待有期限，可取消；失败返回容量不足、拉取失败或镜像版本不可用等明确原因。运行结果回调及实验状态管理沿用现有流程，不额外建设一套请求查询 API。

主要可配置项收敛为以下主机级配置，由该 daemon 的公共镜像池统一生效；各 Benchmark 不分别配置一份容量预算：

| 配置 | 初始建议 |
|---|---|
| 镜像池启用 | 默认开启，启动时完成归属与数据盘预检；可显式关闭 |
| 安全预留比例 | 可管理空间的 30% |
| 高水位比例 | 镜像池容量的 90%，用于提前检查，不规定批量删除目标 |
| 最大同时拉取数 | 2；预取最多占其中 1 个 |
| 提前准备启用 | 接通窗口信息后启用 |
| 镜像等待期限 | 服从现有任务总期限，不无限等待 |

前瞻深度 1、删除并发 1、后台检查周期 30 秒、元数据查询预算及内部估算规则不扩展成用户必填项。

接入包负责提供允许的镜像源及回退顺序、目标架构和版本要求，公共池按这些约束完成镜像操作并返回固定身份。任务重试时重新检查本地镜像，已被回收则按固定版本重拉，不能因为 latest 变化而替换评测镜像。

## 7. SWE-bench 首个接入示例

- SWE-bench 接入包根据 case 解析评测镜像，保留现有镜像源回退、架构校验及正式评测资格规则；这些专属规则不放进公共池。
- 在 Agent 生成 patch 或上一个 case 运行期间，向公共池提交当前及下一个 case 的镜像需求。
- Harness 运行前获取固定镜像引用和使用标识；运行并清理容器后释放。patch 处理、Harness 执行和结果判定仍由 SWE-bench 接入包负责。
- 后续其他 Benchmark 按相同的三类接口接入，不复制空间管理、LRU 或使用保护逻辑；无镜像依赖的 Benchmark 保持原执行流程。

## 8. 验证与实施顺序

先验证五件事：

1. 默认开启且无需两个字节配置；安全预留随实际可管理空间自动变化。高水位提前检查，无缺口不多删；不足时逐个回收、够用即停，在用镜像不误删，无候选时明确报容量错误。
2. 同镜像并发请求只拉取一次，空间预留不重复消费；服务重启和异常清理后状态可恢复。
3. 当前/下一个镜像能提前准备，取消、顺序变化及旧窗口更新不会破坏在用保护或镜像版本。
4. 记录镜像请求实际等待、拉取/删除耗时及整轮实验完成时间，确认提前准备没有因 I/O 竞争拖慢整体实验。
5. 用两个 Benchmark 的接入请求验证共享预算、同镜像去重和跨 Benchmark 使用保护；一个实验取消不影响另一个实验，未授权镜像不能因缓存命中绕过校验。另验证单 case 多镜像准备与无镜像依赖的流程。

另补针对性验证：远程估算总预算不超过约 2 秒、超时后查询进程退出、本地命中不查询、缓存及架构选择正确；容量失败不继续换源，当前 Case 失败后 Controller 可处理下一 Case；不新增高频定时器。

实施顺序：先在评测服务侧落地公共容量检查、LRU 回收与使用保护，以 SWE-bench 完成首个接入，再接当前/下一个 case 的镜像准备窗口，并验证其他 Benchmark 通过相同接口复用。使用现有顺序评测流程验证，不引入用户级并发调度。

第一版不做分段缓存、访问频次统计、完整计划管理、独立管理服务、自动空间预测、动态 I/O 调参或复杂性能归因。只有实际等待或故障数据证明需要时，再单独增加相应机制。
