# 实验执行环境准备：开发计划

本计划以[需求分析](phase1-requirements-analysis.md)和[需求设计](phase2-requirements-design.md)为依据。设计文档不记录逐项实施进度，状态统一维护在[需求清单](../README.md)。

## 1. 接入协议与执行端接口

1. 定义共享的执行上下文、检查结果、准备进度与错误码，明确两个方法 `checkEnvironment`、`prepareEnvironment`。
2. Benchmark 接入协议增加 executor 环境准备声明；扩展 Manifest 校验、生成 Catalog、版本/摘要计算和客户端 bundle，支持不使用 Git 策略的接入包。
3. 根据数据集元数据解析受信接入实现，提供普通数据集、可靠性数据集对应实现；不允许浏览器下发动态代码路径。
4. 统一接入实现调用公共检查/安装能力的方式，避免引入多层注册框架或复制现有执行后端。

## 2. 首批接入实现

| 接入实现 | 工作 |
| --- | --- |
| 普通数据集 | 复用所选 Agent 执行与 Trace 能力检查，检查模型配置及实际声明的基础要求 |
| 可靠性数据集 | 结合 Agent 和选中故障/Case 配置检查 FI 组件、适配能力与权限；复用已有受管理安装能力，人工条件给出指引 |
| SWE-bench | 在接入包 `executor/` 下组合不同 Agent/执行方式要求；Pi/xiaoO 调用 xGovernor 公共模块，MCTS 使用自身检查 |
| 已有其他 Benchmark | 按自身执行路径补齐同一协议，复用原有探测；明确无需自动准备的条件，不留无条件放行分支 |

拆分 xGovernor 现有 setup：只读检查、受管理依赖准备、宿主系统人工条件分开。保留安装锁、兼容版本、产物验证、原子切换与旧版保留策略。已满足条件的其他 Runtime 不受选中 Runtime 的准备干扰。

## 3. 通用任务服务与控制通道

1. 新增环境准备创建/查询 API，复用用户鉴权、数据集授权与客户端归属验证。
2. 封装 `ReliabilityCommand` 为准备任务，扩展服务端及客户端 action 白名单与严格 payload 校验；不新增数据库表作为默认前提。
3. 实现 checking、preparing、needs_action、ready、failed 状态映射与可读问题回报。
4. 为准备动作独立设置有限的运行期限，保留 ACK 送达规则；处理超时、断线、客户端重启和回执补报。
5. 实现请求幂等、同上下文任务复用、共享组件安装互斥及复查，验证多标签页和 WSS/轮询重复投递。
6. 准备完成后刷新能力和实际 Profile 身份，防止后续创建实验冻结安装前摘要。

## 4. 前端与候选主机接线

1. 调整目标查询与页面可选性：支持准备但当前未就绪的主机可选；不混淆离线、不支持与缺组件。
2. 将第二步下一步动作接入轻量准备 Hook，保留原表单校验和无实际执行时的跳过规则。
3. 底部只呈现等待、人工处理或失败提示，不增加卡片、详情、额外安装/检查按钮。
4. 准备期间锁定配置、导航和重复提交；成功且上下文一致时跳转一次，失败后恢复编辑。
5. 耗时提示由当前动作决定，不能按数据集名或是否存在 xGovernor 固定展示。
6. 处理离开页面、刷新、任务恢复及过期回调；客户端运行事实优先，不能仅因页面关闭判为取消。
7. 保留启动时后端与客户端校验；发生漂移时引导回第二步，不在第四步悄悄编译。

## 5. 安装入口迁移与文档同步

1. 移除 `scripts/install-ras-client.js` 中按 Pi/xiaoO 选择直接调用 xGovernor 安装的路径。
2. 分离框架选择和用户配置查找上下文的保存，避免移除安装后模型配置不可见。
3. 验证采集器与基础常驻客户端正常上线，梳理 FI/采集 Hook 的基础依赖，实验专用准备改为按需调用。
4. 复用已有 xGovernor 安装和显式手动路径，不强制迁移、重编译或覆盖用户配置。
5. 功能实施时同步以下指南；本次设计文档提交不提前把现有使用说明改成未实现行为：

   - [MCTS 实验指南](../../user-guide/evaluation/mcts-experiments.md)：所需的环境检查与主机选择变化。
   - [Benchmark 接入开发指南](../../developer-guide/benchmark/benchmark-integration-development-guide.md)：executor 环境协议与不同 Agent 的组合。

## 6. 验证计划

### 自动化验证

- 接入契约：同数据集不同 Agent 得到不同要求；多份同源数据集复用实现；未知专用实现不能降级放行。
- 模块边界：新增测试用数据集接入可走完整准备流程，无需给通用服务或前端增加分支。
- 准备逻辑：只读检查无安装副作用；可提前判断的人工问题先返回；缺失依赖准备后复查；安装成功但复查失败不得 ready。
- 模型问题：凭据缺失、认证拒绝、网络故障分别报告，不上传密钥、不默认发起计费推理。
- 共享组件：重复请求、多标签页及两个 Agent 共用组件时只安装一次，各上下文独立复查；失败保留原版本。
- 任务生命周期：长编译不被普通 30 秒期限误判，有限任务期限生效；断线、重启、回执重放与过期任务能正确核对。
- 前端行为：只有下一步触发；纯已有 Trace 跳过；仍执行 Agent 的 A/B 检查；准备期间锁定；通过跳转一次；旧结果不污染新选择。
- 文案：普通检查、快速准备、首次编译分别覆盖，无详情入口，无常驻成功框。
- 分发与迁移：新 executor 模块随 Catalog/bundle 分发；无 Git 策略的接入包可声明环境准备；客户端安装不再编译 xGovernor；已有采集接入和手动执行配置不受损。

功能实现后先跑针对性测试，再运行仓库要求的 `npm run test`，结合实际改动运行类型检查/lint；发现新增问题后再补充验证。

### 浏览器与执行机验证

按仓库规则，先询问用户是否需要启动 dev 并验证 UI；得到确认后使用 `bash scripts/develop_start.sh`，不要换启动方式。

Golden path：选择 SWE-bench + Pi + 缺少受管理组件的可用 Linux 主机，第二步点击下一步，底部显示实际准备阶段，完成并复查后自动进入第三步。

至少验证一个边界 Case：所选模型缺少 API Key，底部提示配置；用户在执行机修复后再次点击下一步，重新检查并通过。

补充验证：已有依赖无需重编译、同数据集切换 Agent、可靠性数据集准备、自动下载失败后的重试，以及任务中刷新页面。真实耗时安装应在适合的执行机验证，不能用前端模拟进度替代客户端结果。

未执行浏览器或真实执行机验证时，交付说明明确记录未验证范围。
