把 agent-insight 接入 openJiuwen / JiuwenSwarm

openJiuwen 有编排、有执行，缺一个 agent 观测/评估平台（原计划的 jiuwen-ops 还没做）。agent-insight 正好补这块。本次验证：能否把它接上去，完整追踪一次 jiuwenswarm 执行——并在 trace UI 里看到 agent/子 agent 树、LLM 调用、工具调用、token。

核心结论：能，零改 jiuwen 业务代码。复用 jiuwen 自带的 OTEL 观测子系统接住它本就在发的 span → 转成 agent-insight 富 JSON → 上报。三种执行形态（单 agent / team 消息总线 / Task 隔离子 agent）都已端到端跑通并在 UI 成树。过程中还顺手修复了 jiuwen 一个真实观测 bug（流式 LLM span 不收尾）。

从接入者视角

如何接一次执行

点步骤按钮或用方向键切换。左边是真实跑过的命令/输出，右边解释每步在做什么。整条链路对 jiuwen 业务代码零侵入。

jiuwen 执行 → agent-insight
# 复用 jiuwen 自带观测，喂一个内存 exporter
init_observability(
  ObservabilityConfig(enabled=True),
  span_exporter_override=InMemorySpanExporter())
# 正常跑 jiuwen，啥都不改
await Runner.run_agent(...) # 单 agent
await Runner.run_agent_team_streaming(...) # team
# 拿整次 run 的全部 span（别按 traceId 分组！）
spans = exporter.get_finished_spans()
→ llm.call / tool.<name> / agent.<id>
# bridge：span → agent-insight 富 JSON
payload = transform(spans)
POST /api/ingest/upload
→ 200 {"success":true, "upload_id":...}
# 在 trace UI 看这次执行
/trace?ownership=all&scope=all
  &taskId=<task_id>
→ AGENT 树 + LLM/工具时间线 + token

1挂上观测（一行）

agent-core 自带 agent_teams/observability，会把 OTEL handler 注册到 callback 框架。span_exporter_override 接受任意 exporter——我们塞一个内存 exporter 把它发的 span 截下来。

关键：观测在 agent-core，不在 jiuwenswarm 应用层；单 agent 和 team 都会 fire。

2原样跑 jiuwen

用 jiuwen 自己的入口跑：单 agent 用 run_agent，多 agent 团队用 run_agent_team_streaming。不改一行业务代码。

3收 span

跑完一次性读全部 finished span。不要按 traceId 分组——一次执行的 span 散在多个 trace（agent 与 llm、各成员各自 trace），用「整次 run」当边界。

这正是为什么不直连 agent-insight 的 OTLP 薄端点：它按 traceId 分组会把一次执行拆碎。

4转换 + 上报

bridge 把 span 映射成 agent-insight 的富 interactions（含多 agent 联动），POST 到 /api/ingest/upload（不是 OTEL 薄端点）。

打富端点才拿得到完整时间线 / token / 工具 / 多 agent 树。

5看 trace

外部 agent 默认是 unregistered，trace 列表默认筛掉了——加 ownership=all 即可看到。

方向

关键决策与为什么

  • seam = 接 OTEL span，不直连 OTLP 端点：用 span_exporter_override=InMemorySpanExporter() 接住 agent-core 自己 emit 的 span，复用它做好的关联/嵌套，零改 jiuwen。
  • 打富端点 /api/ingest/upload，不打 OTEL 薄端点：薄端点只收 OTLP/JSON（jiuwen 发 protobuf → 415）、属性名对不上（prompt_tokens vs input_tokens 等）会丢 token/工具名、且按 traceId 分组会拆碎一次执行、还不建多 agent 树。
  • 不按 traceId 分组：一次执行的 span 散在多个 trace，用「整次 run」当边界由 bridge 重组。
  • 多 agent 联动用 task+subagent_type 约定：让子 agent 成独立可下钻节点，而不是堆在 leader 下。
  • 合作叙事成立："你的 agent 本就会发 OTEL，我们直接消费"——而且 spike 顺带给 openJiuwen 挖出两个可回馈的修复点。

证据

实际验证了什么

  • 单 agent 一次执行端到端：POST 200 → 落库 → trace 详情页渲染 AGENT→USER→LLM 时间线 + token（29/135/164）。（实验 2）
  • 多 agent team 执行：leader 真的 spawn 两个成员协作报数；trace 成 3-agent 树，成员的 send_message/claim_task 正确归位。（实验 3、5）
  • Task fan-out：coordinator 派两个隔离 worker，全程 0 通信类工具；agent-insight 渲成 TASK SPAWNS=2。（实验 4、5）
  • jiuwen 流式 span 修复后：team 的 llm.call span 0 → 38，token 完整（335k）。（实验 3）
  • 子 agent 联动修复后：team 与 task 均 AGENTS=3，子 agent 带 Trace 下钻。（实验 5）

给 openJiuwen 的回馈

三个已回馈上游的修复（issue + PR 均已提）

spike 顺带挖到的三个真实 bug，都已带回归单测提到 gitcode（fork → openJiuwen/agent-core develop）。三者正交、可独立 review。点卡片跳对应 PR。

#1023 · PR 1648 已提 PR

流式 LLM span 不收尾

流式调用的 span 开了不关 → 导不出（下游丢 LLM/token）+ span 泄漏。修：终止 chunk 时收尾并 end。team llm.call 0 → 38、token 完整。

解决什么
团队/流式模式下任何 OTEL 消费者都能拿到 per-LLM span 与 token。
#1025 · PR 1652 已提 PR

agent span 未挂 context（子 span 孤儿）

on_agent_invoke_input 建 agent span 却没 attach 为当前 context → 子 LLM/Tool span 全成孤儿根，无法按 agent 归属。修：input attach / output detach。孤儿根 38 → 0。

解决什么
每个 agent 的 LLM/工具精确嵌套到其 agent span 下，多 agent 树可按父链还原。
#1024 · PR 1650 已提 PR

agent span id = "unknown"

_AgentMeta 包绑定 invoke，self.card 不进事件 → 落 unknown。修：用 extra_kwargs 注入 card.name。agent.unknown → agent.spike_agent。

解决什么
span 直接带真实 agent 名，下游零猜测还原多 agent 树。

注意

遗留问题与风险

  • 成员归属是启发式：llm.call span 无成员 id，按 trace→主导 tool 成员投票；同 trace 两成员混跑会归错。缓解：根治靠上游修 agent.id。
  • 本次是事后批量上传：跑完一次性 POST。缓解：生产换成自定义 SpanExporter 在 export() 里增量转换+上报。
  • OTLP 标准直连未打通：要"任何 OTEL agent 直连"，需 agent-insight OTEL 端点支持 protobuf + 兼容 OpenLLMetry 实际属性名。更通用但更大改动。
  • latency 单位：传秒会被详情页头部当 ms 显示。缓解：上报用 ms 或注册 framework 单位换算。
  • 环境：摄入与查看必须同一 server/DB；apikey 每次调用会轮换；外部 agent 默认被 ownership=user 筛掉（用 ownership=all）；真跑需有效 deepseek key（仓库自带的已失效，且是上游泄漏的 secret）。
