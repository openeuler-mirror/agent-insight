# 持续优化 · Skill

Skills 是 Agent Insight 中最有代表性的能力之一。你可以把它理解为一类可被 Agent 调用、可版本化、可分析、可优化的能力资产。

> **Note**
> 在 Agent Insight 里，Skill 不只是 Prompt 片段，而是围绕
> `SKILL.md`、脚本、参考资料、评测结果和版本发布构成的完整工程对象。

## Skills 适合解决什么问题

- 把零散经验沉淀成可复用能力
- 让 Agent 在合适时机自动调用特定能力
- 用结构化方式管理 Skill 的版本、分析结果和优化迭代
- 对“这个 Skill 到底有没有效果”给出更可验证的结论

## 一个 Skill 包含什么

一个完整 Skill 通常由以下部分组成：

- **SKILL.md**：主文档，定义用途、触发条件、输入约束和执行方式
- **scripts/**：可执行脚本，供运行时调用
- **references/**：参考资料或上下文文档，供模型理解使用
- **版本信息**：每次发布都会形成一个可追踪版本
- **分析结果**：包括静态合规、触发分析、A/B 测试、用例分析等

## Skills 的典型生命周期

在平台中，Skill 通常会经历 4 个连续环节：

1. **管理**
   先把 Skill 作为资产纳入平台，查看列表、版本与状态。
2. **生成**
   根据需求描述自动生成 Skill 初稿。
3. **分析**
   判断 Skill 是否触发正确、结构是否规范、效果是否真的提升。
4. **优化**
   基于问题和结果反馈，迭代出新的 Skill 版本。

> **Tip**
> 如果你想把持续优化中的 Skill 能力快速用起来，最推荐的顺序是：
> 先看总览页，再按“管理 → 生成 → 分析 → 优化”逐步使用。

## 工作台怎么使用

从侧边栏进入 **持续优化 → Skill** 后，左侧是 Skill Copilot，右侧是资产工作区。一个会话固定绑定一个 Skill，并保存该会话当前的工作版本；每次在这个会话中发布优化结果，工作版本都会推进。工作区顶部的 **Skill** 和 **版本** 两级选择器控制右侧全部页签，不会修改会话绑定：可以直接查看该版本的详情、评估、实验和优化记录，也可以运行评估或实验。浏览内容与会话版本不一致时，工作台会显示提示；点击“回到会话版本”或重新打开该历史会话即可恢复。新会话从以下任一方式开始：

- **生成一个 Skill**：通过对话澄清目标、输入输出、适用边界与安全约束；生成完成时自动应用静态质量规则。
- **上传已有 Skill**：上传目录先形成未发布快照，不会静默修改或直接写入正式版本。
- **从 Skill 管理中心选择**：同时选择 Skill 与精确版本，作为空会话的起始工作版本；后续发布会在同一会话内推进工作版本，但不会改绑为其他 Skill。

Skill 准备好后，左侧会话输入框上方会固定显示 **Skill 评估、Skill 实验、Skill 优化** 三个确定性操作；它们不会随多轮生成和优化消息滚出视野。点击这些左侧操作时，右侧会先回到会话当前工作版本；右侧页签内的查看、评估和实验则始终以顶部选择的 Skill 与版本为准。右侧四个页签分别承担：

| 页签 | 用途 |
| --- | --- |
| Skill 详情 | 查看文件树、内容、工作版本与未发布状态 |
| Skill 评估 | 检查结构、描述、流程和安全约束，不运行真实任务 |
| Skill 实验 | 以触发分析、用例分析或 Skill A/B 预设运行真实实验 |
| 优化记录 | 查看顶部所选基线版本在各会话中产生的候选、失败、放弃与发布结果；优化依据会同时归并静态评估、用例分析和触发分析中可归因到 Skill 的改进建议；优化摘要使用与指标、Diff 平齐的宽版滚动区，并以行级 Diff 显示 `vN → vN+1` 的文件变化和来源会话 |

历史会话用于恢复生成和优化的对话、消息、任务状态、绑定的 Skill 和当前工作版本。点击某条历史会话时，右侧会立即回到该会话的当前工作版本；其他会话或管理中心后来发布的新版本不会让它自动跳版。同一会话先生成再优化时，左侧按时间顺序保留 Skill 生成记录和后续优化轮次，发布或开始优化不会隐藏原生成消息。右侧选择器仍可查看其他 Skill 或旧版本并直接运行评估、实验，但不会改变左侧会话，也不会为这些资产操作自动创建隐藏会话；只有开始生成或优化时才按需准备过程会话。未发布的生成或上传草稿仍按所属会话隔离。生成完成后系统自动把右侧切到该草稿的 Skill 详情，用户检查文件后从详情页发布。生成、评估、实验与优化一旦由服务端接受，就会继续在后台执行；切换 Skill 页签、离开 `/skills` 或关闭当前页面只会停止该页面的实时刷新，返回后会从持久化状态继续展示。

长期资产管理已移动到 **配置 → Skill 管理中心**；旧 SkillHub、生成、评测和优化深链接在兼容期继续可用。

## Skill 实验的四步流程

**触发分析、用例分析和 A/B 测试**共用同一个四步实验向导，只是默认数据、对比方式和评估器不同：

1. **实验设计**：确认名称、Agent 和可选数据集。触发分析只展示绑定当前 Skill 的触发数据集，并可由 AI 生成应触发/不应触发用例；用例分析和 A/B 可选择当前用户的全部非触发数据集，绑定其他 Skill 的普通数据集会标注来源但不阻止复用。
2. **Trace 来源**：可选择已有 Trace，也可按数据集 Case 生成 Trace。触发分析和 A/B 默认生成，用例分析默认选择已有 Trace。
3. **预期答案**：生成 Trace 时检查本次实验的数据集快照，不回写原数据集；选择已有 Trace 时可导入匹配标注、手工标注或存为新数据集。
4. **评估器与执行**：检查冻结摘要和数据前置条件，再使用当前预设的评估器启动实验。触发分析只使用预置评估器 **`skill-trigger-analyzer`**；用例分析和 A/B 展示除此以外的全部可执行预置与自建评估器，并只默认勾选少量推荐项。评估器名称和描述始终沿用评估器中心的注册信息，不会因实验入口不同而重命名。缺少参考答案或 Tool/Skill 目录、可靠性数据集类型不匹配时，相关评估器保留展示但会禁用并说明原因。触发分析逐条比较“应触发”标注与真实路由结果，每条 Case 只生成一个“触发准确率”评分点。误选与漏选是同一评估结果的分类统计，不会调用任务完成度、结果准确性或轨迹质量评估器。

Skill 工作台中的 A/B 版本语义固定为：**A 组是顶部选择的当前工作版本，B 组是另选的对比版本**。实验及任务主体始终绑定 A 组当前版本；切换 B 组只改变对照对象，不会把实验归属切换到旧版本。

A/B 结果页使用配对对比视图：顶部并排展示 A、B 综合得分，评估器分解为每个评估器展示两条得分条和可比覆盖数；Case 明细在同一行并排展示输入、参考输出，以及 A、B 两侧各自的实际输出、综合得分、结果得分和轨迹得分，不在表格中重复展开具体评估器。长文本默认显示两行并以省略号收起，点击单元格可展开全文；明细区同时支持横向和纵向滚动。综合统计只纳入 A、B 两侧都有得分的 Case；只有单侧完成的 Case 归入“未配对”，不会污染组间均分。Case 可按“全部 / A 胜 / B 胜 / 平 / 未配对”筛选；每侧均提供详情和重试，详情复用标准的单 Case 实验详情。

选择已有 Trace 时，实验评估已发生的真实轨迹；选择平台生成时，触发分析会在隔离环境中固定当前版本并让 Agent 自主决定是否调用 Skill，用例分析会加载当前版本执行任务；这两类都只有一个实验组，A/B 测试才对同一批 Case 运行两侧版本。

启动后仍留在 Skill 实验页签内，可查看执行进度、四个运行阶段、已冻结配置和 Case/评估明细。点击 Case“详情”时只替换 Skill 工作台右侧内容，左侧 Skill Copilot、当前 Skill 和顶部页签保持不变；返回时回到当前 Skill 实验详情，不会进入全局实验页。用户点击开始后，创建到执行接收之间的内部 `draft` 在 Skill 工作台统一呈现为“运行中”；执行请求被服务端接受时会立即把持久化状态推进为 `running`，异步启动失败则转为失败，尚未被接受的启动失败会自动回滚实验及其临时 A/B 任务。Skill 实验记录按当前 Skill 与当前版本隔离，同一 Skill 的其他版本不会混入列表；全局“评估与实验”保持独立，不展示触发分析、用例分析、Skill A/B 或候选复测记录。

## 发布门禁

- 生成或上传得到的是工作快照。平台会按当前全部文件的内容 hash 匹配静态评估，只有评估执行完成且不存在 `high` 问题时，发布按钮才可用。
- “评估执行成功”不等于“质量门禁通过”：评估中、评估失败、文件已变化、存在高风险问题和门禁通过会分别展示。文件发生变化后必须重新评估；评估进行期间不能发布。
- 门禁未通过时，可在 Skill 详情或 Skill 评估中点击 **AI 修复问题**。优化 Agent 会读取本次问题清单、修改未发布工作快照并自动复验；修复结果仍需用户检查，平台不会自动发布。正式版本发起同一操作时则生成独立优化候选。
- 优化得到的是候选版本，不覆盖当前正式版本。
- 优化候选通过静态质量规则后即可出现发布操作，当前流程不要求新建实验复测。
- 发布始终要求二次确认。优化失败、放弃和已发布记录都会保留。

## Skills 和 Agent 的关系

这两个概念经常被一起提到，但职责不同：

- **Agent** 是执行主体
- **Skill** 是 Agent 可调用的能力单元

一个 Agent 可以加载多个 Skill；一个 Skill 也可能被多个 Agent 复用。

因此，Skills 模块本质上是在做“能力资产治理”，而不仅仅是做一次性的 Prompt 编辑。

## 什么时候该创建 Skill

以下情况通常适合把能力沉淀成 Skill：

- 某个任务会被反复执行
- 调用条件可以被相对清晰地描述
- 你希望多个 Agent 复用同一套能力
- 你希望对这项能力做独立分析和优化

不太适合沉淀成 Skill 的情况：

- 只是一次性临时实验
- 能力边界非常模糊
- 还没有稳定场景，不知道何时该触发

## 建议的使用顺序

### 第一次接触 Skills

建议按这个顺序体验：

1. 进入 Skill 工作台，从管理中心选择一个已有资产
2. 用一个真实需求试一次 Skill 生成
3. 在工作区打开 Skill 评估或 Skill 实验查看结果
4. 再进入 Skill 优化理解候选、复测和发布流程

### 已经有现成 Skill

如果你已经有 Skill 资产，可以这样用：

1. 先在 **配置 → Skill 管理中心** 确认列表与版本
2. 回到 Skill 工作台选择该精确版本并运行评估或实验
3. 对问题集中的版本发起优化，复测通过后再确认发布
