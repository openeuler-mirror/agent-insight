# 评测执行

评测执行页用于**真正跑起来一轮评测**：发起批次、监控进度，并在批次完成后下钻到单条样本，分别从「结果」和「过程」两个视角解读表现。

> **Note**
> 数据集定义「生成什么样本」或为已有 Trace 补充预期输出，评估器定义「怎么判」，评测执行页则把它们组合成一次可运行、可复现、可追溯的实验。

## 功能概览

在这一页，你可以完成评测的完整运行闭环：

- 发起新的评测批次
- 查看历史批次及其状态
- 监控当前批次的运行进度与失败情况
- 下钻到单条样本，查看**结果评测**与**链路评测**结果

评测执行页可选择平台已注册的预置评估器和用户创建的自建评估器。自建评估器引用 `dataset_input` 时，只有已选 case 的实际任务输入确定性包含数据集输入才可使用。

## 前置准备

发起评测前，确保以下三项均已就绪。任意一项缺失或定义模糊，都会导致结果难以解释。

| 准备项 | 作用 | 缺失的后果 |
| --- | --- | --- |
| 数据集（生成 Trace 时必需） | 提供生成任务的 Case；也可为已有 Trace 导入预期答案 | 未选择时只能评估已有 Trace |
| 评估器集合 | 定义评分规则 | 无法确定「怎么判」 |
| 评测对象 | 指定被测的 Agent / 版本 | 无法确定「测谁」 |

选择 **轨迹工具利用率** 或 **Agent 工具选择合理性** 前，每条 case 还需提供可用 Tool/Skill 目录。可以在数据集 JSON 中使用 `available_tools` 和 `available_skills` 字段，也可以在 **评测数据集 → 新增字段** 中手动添加同名 JSON 字段后逐条填写，或通过实验 API 的 `evaluatorContext` 提供；trace 中的已调用集合不会被当作完整目录。缺少目录的 case 会触发选择门控。

## 发起评测

启动一次评测前，建议先明确本次实验的目标，再选择对应的运行方式。

### 四步创建实验

从“实验 → 新建实验”进入统一四步向导，不再区分多轮评测和普通 Trace 评测。所有新实验都选择执行 Agent，Skill 是 Agent 使用的配置。第一步在实验名称下选择实验类型，再配置本次对比项与共享条件。对比项以 A/B 两张卡片展示，下方集中显示一个“共享条件”区域。第二步选择 Trace 来源，第三步检查 Case 与预期，第四步选择评估器。单轮、多轮由 Case 内容决定。下面保留原有评测集、客户端和历史 Trace 的操作说明，对比配置见下方“在同一实验中配置 A/B 对比”。

1. **实验设计**：填写实验名称、选择待执行 Agent，并按需选择任意评测数据集（结果、轨迹或可靠性数据集）。Agent 下拉同时包含已有历史 Trace 的 Agent，以及客户端配置中在线主机扫描到的可执行 Agent。
2. **Trace 来源**：
   - **选择 Trace**：保留自动监听和历史 Trace 筛选、分页、多选能力；开始实验后直接评估，不重新运行 Agent。
   - **生成 Trace**：先选择运行主机 IP，再选择该主机上当前 Agent 可用的模型，并勾选数据集 Case。模型名称后会显示 provider，以区分不同 provider 提供的同名模型；系统仍以完整 `provider/model` 标识执行目标。系统把每条 Case 的“输入”作为 Agent 用户输入来生成 Trace；未选择数据集或没有在线可执行主机时不可使用。
3. **预期答案**：所选数据集会自动带入 Case 的预期输出、匹配的数据集输入快照和可用 Tool/Skill 上下文；可靠性数据集还会带入故障元数据。选择已有 Trace 时，只要 Trace 任务输入包含数据集输入，就会匹配对应标注；多条数据集输入同时命中时优先使用更长、更具体的一条。该快照供引用 `dataset_input` 的自建评估器使用。也可继续使用“从数据集导入匹配”、手工标注和“存为数据集”。
4. **评估器与执行**：可靠性数据集提供“Agent RAS 可靠性故障检测恢复评估器”，先确认预期故障真实发生，再评价故障检测、触发处置和故障消解。未确认故障发生时总分及三个维度均显示 `—`，理由会说明未检测到故障发生，且该结果不参与综合分。选择已有 Trace 时也可使用该评估器。点击“开始实验”后系统立即启动：已有 Trace 直接进入评估，生成 Trace 则立即进入运行中并在后台完成 Trace 生成、绑定和评估。

实验详情页只负责展示运行状态、进度和结果，不再提供第二个“开始执行”按钮，也不在全局实验详情内容区重复提供返回按钮。Skill 实验的实验详情和 Case 详情都在 `/skills` 工作台右侧切换，不跳转到全局 `/experiments` 路由；Case 详情返回当前 Skill 实验，实验详情再返回当前 Skill 的实验记录。实验没有可操作的“草稿”阶段：创建与启动之间的临时记录不会出现在实验列表；启动失败时系统会自动回滚仍未启动的临时记录并保留向导内容，用户再次点击时会重新创建并启动。只有服务端确认已进入运行流程后才跳转详情页；如果启动实际已生效但响应丢失，系统会保留该实验并进入详情，不会误删运行中的数据。

生成 Trace 是所有生成模式实验的硬前置条件。普通评测数据集由客户端直接执行 Agent；可靠性数据集继续先执行故障注入。每次生成 Trace 的 Agent 执行上限为 300 秒。普通生成由客户端在取得本次平台会话的 Trace ID 后立即上报，服务端只按该 ID 绑定 Execution，不会用输入文本反查；服务端会等待 Session 完整结束且轨迹非空后再启动评估。可靠性 FI Run 即使先因 Session 尚未入库而显示失败，只要已经返回 Trace ID，实验仍会在扩展等待窗口内继续等待晚到的完整 Session，成功绑定后自动补跑该 Case 的评估。普通生成遇到临时投递、执行或入库等待故障时，会在首次执行后自动重试两次；自动重试只会检查本次生成周期内已返回的 Trace ID，避免延迟入库造成重复执行，也不会误绑定更早的历史 Trace。执行超时时客户端会终止本次 Agent 进程后再领取后续重试，因此页面的 Attempt 次数不会仅仅代表排队但未执行的命令。全部 Case 都未生成有效 Trace 时，实验标记为失败且不产生评估分；部分 Case 成功时，只评估成功 Case，失败 Case 在详情中显示失败原因和尝试次数，不计入综合分。详情状态条会分别展示 Trace 的已生成、失败和生成中数量。

Case 操作列统一使用“重试”按钮，具体行为由创建实验时选择的 Trace 来源决定：选择已有 Trace 的实验会保留当前 Trace，只重新评估失败结果；生成 Trace 的实验即使已经绑定过 Trace，也会强制发起一次新的 Agent 执行，不复用任何历史 Trace，并在新 Trace 绑定后重新运行该 Case 的全部评估器。正在自动重试、生成或评估中的 Case 不会重复启动。

实验列表的“综合分”展示当前实验全部有效结果的综合得分。它与通用评估器使用同一口径：只对实际执行且有分的评估器总分求平均；无分的可靠性检测恢复结果不进入分母。Trace 评测详情中的评估器卡会明确显示总分或 `—`，展开后可查看各维度证据和建议。

生成 Trace 的运行主机来自“客户端配置”，页面不会再提供 Worker 安装 curl 命令。如果没有可用 IP，请先检查客户端是否在线，以及其能力上报是否包含所选 Agent、平台和模型。Linux systemd 与 macOS launchd 服务会固化执行安装命令时的 `PATH`，从而发现安装在用户目录中的 OpenCode 等 Agent；已安装的旧 Linux 客户端若在终端能找到 OpenCode、服务中却找不到，请在“客户端安装”页重新生成并执行安装命令以刷新 unit 和服务。普通生成还要求客户端声明“可返回 Trace ID”；旧客户端即使能执行 Agent，也不会作为普通生成目标，需要升级客户端后再试。

### 先想清楚四个问题

1. **本次要验证什么变化**——是新版本、改了提示词，还是换了工具？
2. **样本是否代表当前问题**——样本应覆盖你真正关心的场景，而非随手抽取。
3. **本次更关注结果还是过程**——决定后续重点看结果评测还是链路评测。
4. **结果将用于什么决策**——例如是否放行发布、是否采纳某次优化。

### 选择运行场景

| 场景 | 目的 | 建议样本 |
| --- | --- | --- |
| 发布前回归 | 确认变更未引入退化 | 一组稳定的核心样本 |
| 优化前基线 | 记录修改前的水平 | 与优化后保持完全一致 |
| 版本对比 | 横向比较不同版本 | 同一数据集、同一评估器 |

## 批次管理

评测执行页以「批次」为单位组织任务。**一个批次代表一次完整实验，而非单条样本**。每个批次包含：

- 当前使用的数据集与评测对象
- 预置评估器集合
- 样本总数
- 运行中、已完成、失败的样本数量
- 当前平均分或阶段性结果

按批次理解结果，可以避免被单条样本的偶然表现误导。

## 运行监控

批次启动后，不必等全部跑完再看。运行过程中重点关注三件事。

### 状态分布

通过各状态的样本数量判断批次健康度：

- `pending`：等待执行
- `running`：正在执行
- `done`：已完成
- `failed`：执行失败

### 完成速度

如果进度长时间停滞，通常指向以下原因：

- 后台执行卡住
- 评测对象不可用
- 评估器或外部依赖异常

### 失败样本

**只要出现明显失败样本，就立即抽样排查**，不要等整批跑完。早期失败往往暴露的是数据集或评估器配置问题，越早发现越省时间。

## 解读结果：先建立整体判断

批次完成后，建议按由粗到细的顺序阅读：

1. 批次整体完成情况(完成 / 失败比例)
2. 平均分与主要失败比例
3. 得分最低的一批样本
4. 是否存在系统性失败模式(同类错误反复出现)

确认整体趋势后，再针对单条样本进入下面两个视角的详细判读。

## 结果评测

**结果评测**判断 Agent 的最终输出与预期结果的匹配程度，回答「结果是否覆盖了关键要求」。适用于发布前回归、版本对比和样本级复核。

  <img src="../../images/agent/evaluation/eval_run_result_info.png" alt="结果评测详情页，展示分数、覆盖依据、缺失原因、执行过程原因和 Skill 改进建议" style="width: 100%; max-width: 1120px; height: auto; border: 1px solid #e5e7eb; border-radius: 12px; background: #ffffff;" />
</p>

### 卡片字段说明

| 字段 | 含义 |
| --- | --- |
| **分数** | 本次输出的总体质量分，满分 `10` 分 |
| **评级标签** | 覆盖状态，如 **完全覆盖 / 部分覆盖 / 未覆盖** |
| **覆盖依据** | 输出中已命中的关键事实，是得分来源 |
| **缺失原因** | 输出中遗漏、写错或未展开的关键点，是扣分来源 |
| **实际输出片段** | Agent 的真实输出摘录，作为评测原始依据 |
| **预期结果片段** | 标准答案摘录，与实际输出并排比对 |
| **执行过程原因** | 缺陷在执行链路中发生的环节 |
| **trace 步骤** | 关联的具体步骤编号与工具调用，用于回查证据 |
| **Skill 归因** | 仅当 trace 关联 Skill 时展示，说明缺陷是否更可能归属对应 Skill 或提示词约束 |
| **改进建议** | 仅当 trace 关联 Skill 时展示，可直接落地的修正动作，如补充 `SKILL.md` 约束 |
| **结果层问题** | 展示关键观点之外的事实错误、编造内容、冗余或格式问题；这类问题不直接参与关键观点等权算分，但可归因项会进入 Skill 优化点 |

### 推荐判读顺序

1. 看 **分数** 与 **评级标签**，建立整体印象。
2. 看 **覆盖依据**，确认哪些关键点已命中。
3. 看 **缺失原因**，定位本次扣分的主要来源。
4. 对照 **实际输出片段** 与 **预期结果片段**，核实差异是否成立。
5. 看 **执行过程原因** 与 **trace 步骤**，判断缺陷出现在检索还是输出环节。
6. 查看 **结果层问题**，确认是否存在额外事实错误、编造内容、冗余或格式偏差。
7. 如果 trace 关联了 Skill，再看 **Skill 归因** 与 **改进建议**，将问题转化为修复动作；未关联 Skill 的 trace 不展示这些字段，也不会生成 Skill 优化点。

### 结果说明什么

- 高分代表最终输出覆盖了更多关键要求。
- 低分代表输出与参考结果存在明显缺口。
- **覆盖依据 + 缺失原因** 决定结果是否**可解释**。
- trace 关联 Skill 时，**Skill 归因 + 改进建议** 决定结果是否**可转化为 Skill 修复动作**；未关联 Skill 时，结果评测只用于判断输出是否达标。

## 链路评测

**链路评测**判断 Agent 的执行轨迹(Trace)是否稳定、合理、可复现，回答「过程是否值得复用」。对于多步 Agent，这一视角通常比单纯的总分更适合定位系统性缺陷。

<p align="center">
  <img src="../../images/agent/evaluation/eval_run_trace_info.png" alt="链路评测详情页，展示轨迹总结、完整性、工具选择、冗余、归因、偏离步骤和改进建议" style="width: 100%; max-width: 920px; height: auto; border: 1px solid #e5e7eb; border-radius: 12px; background: #ffffff;" />
</p>

### 一个核心前提

**结果正确 ≠ 过程健康。** 一条 Trace 即使最终完成了任务，仍可能在工具选择、步骤安排或约束遵循上存在缺陷。链路评测的目标不是给一个总分，而是把问题定位到**具体步骤、具体判断、具体改进点**。

### 三个核心维度

| 维度 | 回答的问题 | 分值含义 |
| --- | --- | --- |
| **完整性** | 任务关键目标是否完成 | 高 = 目标大体达成 |
| **工具选择** | 工具类型、参数、调用时机是否合理 | 低 = 方法或参数选择不稳定 |
| **冗余度** | 执行路径是否避免多余步骤、重复调用或无效消耗 | 高 = 路径更精炼 |

> **Warning**
> **冗余度表示路径精炼程度**：分值越高，重复调用、无效步骤和额外消耗越少。

### 其他卡片字段

- **轨迹路径总结**：概括本次执行链路的整体表现。
- **关键动作覆盖明细**：位于完整性的证据中，逐项说明已覆盖、部分覆盖、缺失及对应 Trace 依据。
- **证据与建议**：右栏只使用一个折叠内容块，灰色折叠预览统一以「证据：」开头；展开后先显示「证据」小节，有建议时再追加「Skill 改进建议」小节。没有建议时也保留「证据」标题，便于快速识别内容层级。
- **Skill 改进建议**：仅在 Trace 关联 Skill 且存在有依据的改进点时，显示在完整性下面；建议不参与评分，可继续进入 Skill 优化流程。实验中的轨迹质量评分限时 5 分钟；建议生成另按每次 7 分钟、最多尝试 2 次（含首次）执行。两次都失败时仍保留轨迹评分，不显示建议。

### 推荐判读顺序

1. 看 **轨迹路径总结**，建立整体印象。
2. 看 **完整性、工具选择、冗余度** 三个维度分值。
3. 展开完整性的 **关键动作覆盖明细**，定位部分覆盖和缺失动作。
4. 如果完整性下出现 **建议**，确认它是否已收敛到明确的 Skill 修改动作；没有建议时页面不会显示空提示。

> **Tip**
> **链路评测** 更适合生成修复动作，**结果评测** 更适合判断输出是否达标。两者结合，既能回答「结果是否正确」，也能回答「过程是否稳定」。

## 典型工作流

### 发布前回归

1. 选定一组核心样本。
2. 跑一次完整批次。
3. 对比失败模式是否与历史一致。
4. 据此决定是否允许发布。

### 优化前后对比

1. 先用当前版本跑一次基线。
2. 修改评测对象(版本 / 提示词 / 工具)。
3. 用**同一数据集和评估器**重跑。
4. 对比两次结果，确认是否真实提升。

### 问题定位辅助

1. 在运行观测中找到高价值问题。
2. 将问题整理为数据集。
3. 发起评测。
4. 用结果确认问题是否能被稳定复现。

## 常见误区

- **批次一次开太大**：首轮就难以读懂，建议从小样本开始。
- **跑前没有明确目标**：导致结果无法支撑任何决策。
- **看到平均分就停**：未下钻样本，错过系统性问题。
- **失败后不回看配置**：很多失败源于数据集或评估器本身，而非被测对象。

## 版本化多轮实验

从“实验 → 新建实验”进入统一四步流程，第一步同时展示版本化评测集与原有评测集，无需切换入口。先接入可执行的 HTTP Agent，或者启动 `node examples/evaluation-harness/server.mjs` 并初始化 Demo 目录。Demo 是独立执行服务，基线和修复版本分别展示审批缺陷及修复效果，不使用预期答案合成执行输出。

第一步分别通过“Agent”和“Agent版本”两个下拉选择执行对象与版本；评测集也拆分为“评测集”和“评测集版本”。选择 Skill 对比时，在对比项 A/B 卡片中分别选择同一 Skill 的两个版本，在下方共享条件中选择一个 Agent 及版本。Skill 不再与 Agent 混在执行对象下拉框中。版本列表只显示所选对象的版本，切换对象默认选其最新版本。从数据集卡片发起或按原条件创建回归时，仍保留指定版本。随后选择规则/LLM 评估器版本。新增 Agent 版本仅记录用户声明和外部版本引用，不负责部署。多轮 Case 共用该 Case 的真实执行历史，不跨 Case 共享。

完成后可查看逐轮规则、实际输出、工具参数及原生 Trace；“分析问题并优化”按失败检查聚类并展示观测路由矩阵。修改 Case 会写入评测集新版本；重新执行此 Case 创建独立实验记录。按原条件创建回归可更换目标版本并保留原测试条件。

模型不可用、执行超时或缺少证据会显示“无法判断”，不会假装通过。只有连接故障、429/5xx 和超时可重试。预约、自动发布和多模态评估不在第一版范围内。

### 第一版使用条件与验收范围

版本化多轮实验当前要求 SQLite 和单服务进程。选择已有 HTTP 目标时，由该服务实际执行指定外部版本；新版本登记不会替你部署 Agent。现有客户端任务下发和历史 Trace 评估在同一个向导中选择原有评测集后使用。未登记版本的观测 Agent、原有评测集会明确显示当前内容未版本化，不会自动生成虚构版本。

首次体验可启动仓库中的 `node examples/evaluation-harness/server.mjs`（默认 4319），将 Agent Insight 服务的 `EVALUATION_DEMO_URL` 设置为可访问的 Demo 地址，然后点击“初始化 Demo 目录”。平台通过 Demo `/targets` 获取目标、版本、Prompt、Skill 和工具定义。Demo 的 v1 故意错误审批高风险和超额申请，v2 改为人工复核；同一评测集的预期结果是 50% → 100%。这是实际 HTTP 执行的确定性 Demo，不代表真实语言模型已经验收。

在实验详情点击“分析问题并优化”，按失败类型查看证据、Case ID 和排查建议；修改外部目标后登记新版本，点击“按原条件创建回归”。修改 Case 后会另存完整评测集版本，可以点击“用修订版创建回归”。单 Case 的“重新执行”也生成独立实验。版本分析先选 Agent、评测集、固定版本和比较条件；模型、评估器、执行参数或 Case 子集不同的记录不会混在同一趋势中。

Agent Insight 会采集目标实际返回的输出、工具、路由和可导出的系统提示词。目标不返回的信息显示为未采集；只填预期输出而未配置规则时，确定性规则不能判断，需要选择 LLM 语义评估器。业务关键失败会阻止验收通过；超时、模型错误或缺失证据不能视为通过。服务中断后超过 2 分钟无心跳的运行会在下次查询时标为失败，可新建实验重新执行。

审批红线和工具规则是在执行后检查，决定实验的验收结果；它们不会拦截被测目标正在发生的工具调用，也不会自动发布或回滚 Agent。

实验详情统一展示原有状态、评估器分解和分页 Case 明细表。点击 Case 的“详情”进入原有评估器结果页，展开卡片查看每轮输入、实际输出、工具证据和规则结论。版本验收统计与快照保留在补充摘要及“更多指标与测试条件”，优化和回归入口仍在实验级提供。

### 使用已有 Trace 检查逐轮规则

选择已登记的 Agent 版本和版本化评测集后，在第二步选“使用已有 Trace”并多选会话 Trace，第三步再为每条 Trace 关联 Case。平台在开始前核对用户归属、Agent、已记录的版本和逐轮输入。缺失轮次、工具、Skill 或版本证据会标为未评完整；只在回复中提及某个 Skill 不算实际调用证据。此路径保存评估快照并引用原 Trace，不重新执行 Agent，不生成新的会话。

第二步选“执行 Agent 生成 Trace”时，每个 Case 独立会话，按所配轮数调用目标；第三步仍可逐轮查看输入、预期、审批红线、Skill 路由及工具参数和顺序规则。原有评测集继续提供参考答案、上下文、轨迹及原生评估器；持续采集、客户端下发、模型对比和 Skill 内嵌实验入口保留。只有观测记录的 Agent 还不能直接执行版本化 Case，需要登记可执行目标；页面会说明该限制。

“按原条件创建回归”和 Case 的“重新执行”会实际调用 Agent；重新评估原 Trace 则在第二步明确选已有 Trace。生成执行与 Trace 回放不混为同一趋势比较条件。

### 在版本分析查看实验演进

侧栏“版本分析”默认展示实验版本分析，自动选择有数据的 Agent 和评测集，无需另找实验版本入口。概览显示版本组合、实验记录及双方版本数量；下方表格每个组合一行，显示最近实验的结果，并可展开重复运行历史或进入详情。

趋势默认固定评测集比较 Agent 版本，也可切换固定 Agent 比较评测集版本。平台自动选取包含最多可比较版本的一组条件，每个版本取该条件下最近一次已完成且有评分的实验。百分比差显示为百分点；运行失败或没有评分时不算成 0%。切换趋势条件不会隐藏下方版本组合。当前范围是最近 100 条版本化实验。

旧的按 Trace 版本标签统计仍在“Trace 标签分析”页签中，标签维护继续使用“版本管理”。没有实验的对象显示明确空状态及新建实验入口，不需要为了看到实验结果去给 Trace 手工打版本标签。

目标定义通过“接入目标”手动填写，或从已接入的目标目录获取；不再提供“从已有 Trace 提取目标定义”功能。第二步“使用已有 Trace”仍用于对历史运行逐轮评估。

### 在同一实验中配置 A/B 对比（第一版）

在第一步的实验名称下选择“无变量 · 单组”或一种对比类型。各类对比统一使用上方“对比项”的 A/B 卡片、下方单个“共享条件”区域。只有选中的模块提供 A/B 两套配置，其余模块在对应步骤配置一次、两组共用。对象与版本仍分别用两个下拉框选择；执行对象始终是 Agent。

| 实验类型 | A/B 分别配置什么 | 两组共用什么 |
| --- | --- | --- |
| Agent 对比 | 两个 Agent 或 Agent 版本 | Skill 配置、模型、评测集与 Case、预期答案、评估器、运行设置 |
| Skill 对比 | 同一 Skill 的两个已登记版本 | 同一个 Agent 及版本、执行接入、模型、评测集与 Case、预期答案、评估器、运行设置 |
| LLM 对比 | 两个模型 | Agent 版本、Skill 配置、评测集与 Case、预期答案、评估器、运行设置 |
| 评估器对比 | 两项评估器或两组版本化评估器组合 | Agent 版本、Skill 配置、模型、评测集与 Case、预期答案及同一份 Trace |
| 评测集对比 | 两个评测集或同一评测集的两个版本，各组选自己的 Case | Agent 版本、Skill 配置、模型、评估器、运行设置 |

后续步骤会显示共享条件。对象及版本只读沿用，需要变更时返回第一步；运行设置和公共评估器分别在第二步、第四步统一配置，不能为 A/B 设置不同值。开始实验后保存本次配置快照，后续目录修改不改写版本化实验的历史条件。

评估器对比的第四步明确分为 **A 组 / B 组** 两个区域，标题旁显示各组已选数量，两组使用相同的评估器卡片、说明及标签样式。版本化实验可在每组分别多选，每组至少一项，且两组组合不能完全相同。普通 Trace 对比沿用第一步每组选择一项评估器的方式；第四步分别只读确认，需修改时点击对应组的“返回第一步修改”，重新确认配对条件。

开始前按组检查评估器是否存在、是否可用，以及当前 Case 是否具备预期答案、数据集输入或工具目录等必要信息。同一组内的互斥规则只约束该组，不会因为 A 组选了一种评估器就禁止 B 组比较另一种。任何一组缺少条件都会显示原因并禁止开始，需要补齐共同 Case 信息或返回修改评估器；第四步不会悄悄改变原生 Trace 的 A/B 选择。

版本化数据集下，Agent、Skill、LLM 对比各执行一组相同 Case；评估器对比只执行一次 Agent，两组评估器读取同一份保存的过程证据，避免把 Agent 两次执行的随机差异算成评估器差异。评估器对比不会因为 A 组红线失败就跳过 B 组。LLM 执行端必须接受 model 并在响应中回传实际模型；未确认模型时记为未评完整。

Skill 对比会把 A/B 两个版本的 Skill 定义分别交给同一个 Agent 执行，Agent、模型及其他运行条件保持不变。Agent 执行服务需支持按本次要求加载 Skill，并通过响应中的 `loadedSkills` 确认实际加载的 Skill 标识、版本和定义内容；只返回选中的标签或在答案中提及 Skill 不算确认。未确认、确认的版本不一致或内容不一致时，该 Case 显示“未评完整”，不作为 Skill 改善结果。旧版直接以 Skill 作为执行目标的历史实验仍可查看；从这类实验创建回归时，需补选并核对执行 Agent。

普通 Trace 路径复用已有配对和评估能力：Agent 按 Agent 名称、Skill 按已确认的 Skill 配置及版本、LLM 按模型寻找同一输入的两组记录；其他受控字段不同会排除。Skill 对比仍先确定一个共享 Agent，再选择该 Agent 已有 Trace 中可确认的 A/B 配置，缺失配置证据不等于“无 Skill”。评估器对比为同一条 Trace 分别运行两项评估器。无配对记录时不能继续。实际执行无 Skill 基线及完整 Skill A/B 测试继续使用 Skill 工作台。

评测集对比第一版只支持**已发布的版本化评测集**，不直接比较普通未登记版本的数据集或浏览器草稿。在第一步分别选择 A/B 评测集和版本，不能选择完全相同的版本；第二步分别勾选两组 Case，并共用并发、超时和重试设置；第三步分别查看两组首次输入、最终预期输出和只读逐轮规则；第四步选择一套公共评估器和通过率门槛。同一个已登记 Agent 分别执行两组 Case、生成 Trace，A/B 的 Case 数量可以不同。需要修改 Case 时，先到评测数据集编辑并发布新版本，再回到实验选择。

实验详情增加 A/B 通过率或分数、有效配对数、差异 Case 以及各组详情入口。版本化 Case 可展开两组最终输出，继续查看评估器评分点、证据与建议。未评完整的 Case 不算成 0 分，也不参与差值。评估器对比显示判定差异，分数更高不代表评估器更准确。A/B 实验不混入单个 Agent 版本的趋势统计。

评测集对比的详情分别显示每组 Case 总数与通过率，并列出“输入或规则已变化”“仅 A 组”“仅 B 组”。只有各轮输入、预期输出、规则、评估说明与 Case 标注相同、且两侧均已评完的 Case 才参与判定差值。新增样本或修改验收要求造成的通过率变化，不标为 Agent 改善或退化。例如 B 集增加了更难的贷款场景后通过率下降，只说明同一个 Agent 在 B 集上的通过情况；应查看新增 Case 的评分证据再判断原因。

本地示例模型 demo-basic / demo-reasoning 是确定性的 HTTP 演示行为，用于验证请求路由、Trace 保存和结果对比，没有调用真实大模型。第一版未实现多变量矩阵及统计显著性检验。

实验列表按实际对比类型标记，综合分列显示“查看 A/B”；进入详情分别查看两组结果，避免将两组合成一个分数。

原有 Trace 评估按 Agent 名称选择已采集记录，Agent 版本以 Trace 实际记录为准；页面不会将登记目录中的版本号套到这些历史 Trace 上。执行失败的 Case 会显示失败原因，不再显示“实验尚未执行”。
