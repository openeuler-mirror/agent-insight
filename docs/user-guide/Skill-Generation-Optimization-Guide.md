# Skill 生成、评估与优化使用指南

> 本指南面向 Agent Insight 使用者，介绍如何在工作台中创建、检查、测试和持续改进 Skill。下文将 Skill 简称为“能力”。

## 1. 你可以完成什么

在 Agent Insight 中，一项能力通常会经历以下过程：

```text
描述需求 → 生成或导入 → 检查内容 → 质量评估 → 发布版本
                                      ↓
                         真实场景测试 → 发现问题 → 优化 → 再次发布
```

平台主要帮助你完成三件事：

| 环节 | 解决的问题 | 你需要关注的结果 |
| --- | --- | --- |
| 生成 | 把需求和参考资料整理成可使用的能力 | 内容是否符合目标，文件是否完整 |
| 评估 | 检查内容质量，并验证真实使用效果 | 是否容易误触发、结果是否正确、过程是否可靠 |
| 优化 | 根据已发现的问题生成改进版本 | 修改是否准确，是否引入回归，新版本是否值得发布 |

推荐从 **Skill 工作台** 开始操作。长期维护已有能力和查看历史版本时，可以进入 **Skill 管理中心**。

## 2. 使用前准备

### 2.1 配置可用模型

生成、智能评估和优化都需要可用的模型。开始前，请先在配置中心确认：

- 已添加并启用一个模型配置。
- 模型可以正常调用。
- 如需补充联网资料，已配置搜索服务。

如果模型不可用，任务可能无法启动、执行失败，或只返回不完整结果。

### 2.2 准备需求信息

描述越具体，生成结果越稳定。建议至少准备：

- **目标**：希望解决什么问题。
- **适用场景**：什么情况下应该使用。
- **排除场景**：什么情况下不应该使用。
- **输入**：用户会提供哪些信息。
- **输出**：希望得到什么结果，以及必须包含哪些内容。
- **约束**：使用环境、权限、可访问范围和禁止事项。
- **完成标准**：怎样才算任务完成。

还可以准备规范文档、操作手册、示例数据、历史案例、日志或代码片段作为参考资料。

## 3. 创建一项新能力

### 3.1 从需求生成

1. 打开 **Skill 工作台**，新建会话。
2. 选择生成能力。
3. 输入目标、适用场景、输入输出和限制条件。
4. 如有参考资料，在对话中添加附件。
5. 根据页面提示补充缺失信息。
6. 等待生成完成，然后逐项检查生成内容。
7. 运行质量评估并处理重要问题。
8. 确认内容可用后发布第一个正式版本。

生成任务提交后，即使暂时离开页面，任务通常也会继续执行。重新进入会话即可查看进度和结果。

### 3.2 导入已有内容

如果你已经有完整目录，可以直接选择 **上传已有 Skill**。导入后，内容会先作为未发布版本进入工作台，方便检查和评估。

注意区分两种上传方式：

| 操作 | 适用情况 |
| --- | --- |
| 上传已有 Skill | 导入准备继续维护的完整内容 |
| 在生成对话中添加附件 | 为 AI 提供参考资料，不会自动成为最终文件 |

参考附件是否会被整理进最终内容，由生成结果决定。因此，生成完成后仍需检查必要资料是否已经正确体现。

### 3.3 附件建议

支持上传常见文档、表格、配置、代码和日志。为了提高读取质量：

- 单次只上传与当前需求直接相关的资料。
- 文件名应能说明内容用途。
- 大型文档尽量标出重点章节。
- 敏感信息应先脱敏。
- 不要把相互冲突的规范混在一起而不作说明。

### 3.4 推荐的需求模板

```text
请创建一个用于 <任务或领域> 的能力。

目标：
- 解决……

适用场景：
- 当用户……时使用

不适用场景：
- 当用户……时不要使用

输入：
- ……

输出：
- 使用……格式
- 必须包含……

环境和限制：
- 运行环境……
- 默认只读；执行写操作前必须确认
- 不允许……

完成标准：
- 正常场景下……
- 遇到边界情况时……
- 失败时应……
```

### 3.5 生成后重点检查

不要只看生成完成提示。发布前至少确认：

- 名称和简介清楚、稳定，没有含糊或夸大的描述。
- 适用和不适用场景写得足够明确。
- 操作步骤完整，顺序和条件分支合理。
- 所有引用的文件都真实存在。
- 涉及写入、删除、发送或其他高风险操作时，会先征得确认。
- 失败、超时、权限不足和空结果都有处理办法。
- 输出格式和完成标准能够被实际验证。

## 4. 评估质量和真实效果

评估分为两类，建议按顺序使用：

1. **质量评估**：检查内容本身是否清晰、完整、安全。
2. **场景实验**：在测试数据或历史记录上验证真实使用效果。

质量评估通过并不代表真实任务一定成功；真实实验表现不错，也不代表内容中没有安全或维护问题。

### 4.1 质量评估

在工作台中选择待检查的版本或未发布内容，然后启动评估。平台会从以下方面给出结果：

- 目标和适用范围是否清晰。
- 内容组织是否合理。
- 操作指令是否准确。
- 前后表述是否一致。
- 异常处理和安全约束是否充分。
- 是否包含明显风险或敏感信息。

评估结果通常包含问题级别、问题依据和修改建议。处理时建议：

1. 先查看高风险问题及其依据。
2. 判断问题是否与实际场景相符。
3. 使用 AI 修复或手工修改。
4. 修改后重新评估。
5. 再次人工检查，不要只依赖总分。

如果内容在评估后发生变化，旧结果可能不再适用，应对最新内容重新评估。

### 4.2 触发分析

触发分析用于回答：**该用时是否会被选中，不该用时是否会误选？**

测试数据应同时包含：

- 应该使用的正例。
- 与目标接近但不应使用的反例。
- 明显无关的反例。

重点查看漏选和误选案例，而不只是总体准确率。出现问题时，通常需要调整适用范围、排除条件或示例。

### 4.3 用例分析

用例分析用于回答：**被选中后，结果和执行过程是否可靠？**

可以使用标准测试数据，也可以复盘已有运行记录。建议覆盖：

- 正常流程。
- 边界输入。
- 信息缺失。
- 权限不足。
- 执行失败与恢复。

查看结果时，应同时关注最终答案、操作过程、失败原因和改进建议。

### 4.4 A/B 测试

当你需要判断新版本是否真的更好时，可以对同一批用例比较两个版本，或将其中一侧设置为不使用该能力。

为了让结果可比较，请保持以下条件一致：

- 使用相同的数据和用例顺序。
- 使用相同的模型和评估方式。
- 使用相同的运行参数。
- 只比较两侧都成功完成的用例。

除平均得分外，还要查看退步用例、运行时间和资源消耗。小样本的一次领先不一定代表稳定提升。

### 4.5 如何选择评估方式

| 你遇到的情况 | 优先选择 |
| --- | --- |
| 经常没有被选中 | 触发分析 |
| 经常在错误场景被选中 | 触发分析 |
| 能被选中，但结果不正确 | 用例分析 |
| 最终结果尚可，但过程绕远或不稳定 | 用例分析 |
| 不确定新版本是否优于旧版本 | A/B 测试 |
| 准备首次发布 | 质量评估 + 人工检查 |
| 准备发布重要更新 | 质量评估 + 用例分析 + A/B 测试 |

## 5. 优化已有能力

### 5.1 从问题开始优化

优化应基于明确证据，而不是只输入“帮我优化一下”。证据可以来自：

- 质量评估发现的问题。
- 触发分析中的误选或漏选。
- 用例分析中的失败和低分案例。
- 用户反馈或实际运行记录。
- 你补充的目标与限制。

如果问题较多，平台会帮助合并相似问题并安排优先级。开始优化前，请确认计划没有把互相冲突的要求同时执行。

### 5.2 推荐的优化诉求模板

```text
当前问题：
- 在……场景容易误触发
- 遇到……输入时结果不完整

优化目标：
- 收紧适用范围
- 补充……情况下的处理步骤

必须保留：
- 现有输出格式
- ……流程

禁止修改：
- 不新增外部依赖
- 不删除已有文件

验收方式：
- 原有正常用例继续通过
- ……反例不再触发
```

### 5.3 审阅优化结果

优化完成后，重点查看修改摘要和逐文件差异：

- 修改是否直接对应已知问题。
- 是否意外改变了无关内容。
- 是否删除了仍在使用的步骤或文件。
- 是否新增了未经允许的依赖或权限。
- 是否解决了高风险问题。
- 是否影响原来已经通过的场景。

如果质量检查仍有阻断问题，可以继续修复；如果修改方向不合适，可以补充要求后再次优化。

### 5.4 发布前复测

优化后的内容通过质量评估，只说明内容层面的检查没有发现阻断问题，并不代表真实场景已经验证通过。

对重要能力，发布前建议：

1. 重跑之前失败的用例。
2. 重跑一组原本成功的用例，检查是否出现回归。
3. 进行触发分析，确认适用范围没有意外扩大或缩小。
4. 使用 A/B 测试比较新旧版本。
5. 确认收益值得增加的耗时或资源成本。

### 5.5 发布新版本

发布前请再次确认：

- 当前修改已经完成评估。
- 高风险问题已经处理。
- 修改内容和差异已人工审阅。
- 关键场景已经复测。
- 这是你希望立即启用的版本。

发布后会形成一个新版本，历史版本仍会保留。若发布期间已有其他人或其他会话先发布了更新版本，应基于最新版本重新检查和优化，避免覆盖新改动。

## 6. 推荐工作流程

### 6.1 创建新能力

1. 新建工作台会话。
2. 写清目标、适用范围、输入输出和限制。
3. 添加必要的参考资料。
4. 等待生成并逐项检查内容。
5. 运行质量评估并解决重要问题。
6. 人工确认后发布首个版本。
7. 使用正反例进行触发分析。
8. 使用正常、边界和失败用例进行用例分析。
9. 根据证据继续优化。

### 6.2 改进已有能力

1. 在工作台选择正确的能力和版本。
2. 运行质量评估，先处理结构和安全问题。
3. 用真实或代表性用例建立当前表现基线。
4. 找出误选、漏选、失败和低效案例。
5. 从当前版本开始优化。
6. 审阅优化计划、修改摘要和文件差异。
7. 复测失败用例和原有成功用例。
8. 使用 A/B 测试确认改进效果。
9. 确认后发布新版本。

## 7. 常见状态怎么处理

| 页面状态 | 含义 | 建议操作 |
| --- | --- | --- |
| 尚未评估 | 当前内容还没有评估结果 | 启动质量评估 |
| 评估中 | 任务仍在执行 | 等待完成，不要重复提交 |
| 评估失败 | 模型、配置或执行出现异常 | 检查模型配置后重试 |
| 文件已变化 | 内容已修改，旧结果不再对应当前版本 | 重新评估 |
| 存在高风险问题 | 当前内容不适合直接发布 | 查看依据并修复后重评 |
| 质量检查通过 | 未发现阻断性问题 | 人工审阅，并按风险决定是否复测 |
| 优化执行失败 | 优化任务未正常完成 | 查看错误信息，修复配置或重新发起 |
| 版本冲突 | 当前基础版本已不是最新版本 | 基于最新版本重新优化 |

## 8. 常见问题

### 8.1 生成结束后为什么没有可查看的内容？

先确认模型可用，并检查任务是否仍在运行。如果只返回了文字说明而没有生成实际文件，可在原会话中明确要求生成完整内容；仍无结果时重新发起任务并保留原需求。

### 8.2 为什么质量评估无法启动或没有完整结果？

通常是评估模型未配置、模型调用失败或任务仍在执行。先检查配置和任务状态，再重新评估。

### 8.3 为什么评估完成后仍不建议发布？

“评估完成”只表示任务执行结束，不代表所有问题都已解决。请继续检查高风险问题、问题依据，以及评估后内容是否又被修改。

### 8.4 为什么未发布内容不能进行场景实验？

场景实验通常以正式版本作为测试对象。请先完成质量评估和人工检查，再发布用于实验的版本。

### 8.5 为什么 A/B 结果没有自动变成优化任务？

A/B 测试主要用于判断两个版本的相对表现。请查看具体退步用例，把希望解决的问题和限制条件写入优化诉求。

### 8.6 为什么优化后仍要人工检查？

自动优化可以处理已知问题，但无法完全理解你的业务优先级，也不能保证没有改变其他行为。发布前必须检查差异，并复测关键场景。

### 8.7 离开页面后任务会停止吗？

生成、评估、实验和优化任务在提交成功后通常会继续运行。重新进入对应会话即可查看最新状态。

## 9. 发布检查清单

### 首次发布前

- [ ] 目标、适用场景和排除场景清楚。
- [ ] 输入、输出和完成标准明确。
- [ ] 所有必要内容和引用文件均存在。
- [ ] 高风险操作会先请求确认。
- [ ] 失败和异常情况有处理方式。
- [ ] 已完成质量评估并核对重要问题。
- [ ] 已人工阅读最终内容。

### 优化版本发布前

- [ ] 修改对应明确的问题或证据。
- [ ] 没有意外删除或大范围改写无关内容。
- [ ] 没有新增未经允许的依赖和权限。
- [ ] 高风险问题已经处理并重新评估。
- [ ] 失败用例已经复测。
- [ ] 原有成功用例没有明显回归。
- [ ] 新旧版本对比结果符合预期。
- [ ] 已确认发布后立即启用新版本。
