# 分层真实验证操作指引

开发 Agent 在设计验收计划和生成接入实现时读取本页。目标项目现行接入规范是权威；默认执行本地检查、固定提交评分对照和跨类型完整用户链路。L1/L2/L3 用于标记覆盖层次，首例 L3 同时提供 L2 执行证据。具体路径、认证、命令和能力仍按 [discovery.md](discovery.md) 查询，不以某个 Benchmark 的现有测试直接代替本次验证。

## 1. 发现入口并制定计划

1. 从本次实际用户入口识别必须经过的准备、确认和进入条件，再追踪环境、创建/启动、执行、Artifact、评测、结果及清理的真实调用链。核对项目身份、协议差异与部署版本，记录对应入口、合同及已有测试；使用 CLI 或服务合同的阶段沿用该入口，不新增测试专用 API。后续服务成功不证明前置用户步骤已经覆盖。
2. 将 [validation-matrix.md.tmpl](../assets/templates/validation-matrix.md.tmpl) 复制到包外 `$RUN_DIR/validation-matrix.md`。只填写本次新增、改变及关键边界的断言，已有公共覆盖直接引用测试命令、版本和范围；记录前置数据、身份、实际入口、关键断言、终态、期限、证据和清理，不为每次接入重写整套平台测试。用户会话、设备身份、服务请求分别处理，凭据只引用已有配置。
3. 核对前期确认的客户端与 Agent，从其当前可用模型中请用户选择本次验收模型，已有明确选择则核对后沿用，记录具体模型身份；模型选择仅用于本次实验和验收，不收窄接入支持范围；需要自定义插件或函数适配时，先确认实现、相关测试及部署已就绪，不能以“可适配”代替可执行证据；变化时先协商，不因验收便利自行切换。固定官方 Case、数据/接入版本、用户显式指定的总限制（如有）、已确认组合及按需选择的执行和评分条件。记录本次测试覆盖层次。
4. 按[协议导航](benchmark-protocol.md#7-验收与维护)读取目标选样与覆盖要求，查询官方任务元信息，在验证矩阵记录 Case ID、分类与选取依据、未覆盖范围及适用例外，完成所需用户确认后冻结。
5. 保存 matrix、接入方案、来源及官方固定提交等计划输入，再 `freeze`。矩阵记录计划，不回写实际结果；结果进入各次 attempt 的独立证据。后续改计划需说明原因并重新冻结。

先按本次新增、修改和原样复用的模块选择覆盖：不变的公共行为引用适用测试的版本与范围，只补新增风险和关键连接处。历史测试不能替代本次数据安装、配置生效和真实执行事实。每项额外活动须说明尚未解决的问题。

### 三组验收的推进条件

| 当前组 | 完成条件 | 下一步 |
|---|---|---|
| 本地检查 | 本次实现、实际入口合同及相关前置测试有结果；复用测试注明来源和覆盖，失败已修复 | 运行固定提交评分对照；无依赖的开发可继续 |
| 固定提交评分 | 官方与真实服务使用相同冻结输入，身份、业务终态、指标和清理可核对，比较通过 | 启动首个正式 Case；该 Case 同时提供 L2 执行证据 |
| 跨类型完整用户链路 | 全部冻结 Case 的必要用户步骤、真实提交、评分和清理都有证据，关联与版本一致 | 每例链路核对完成再启动下一例，首例计入正式结果；仅首例通过不能交付完整验收 |

这些是现有三组验收的完成条件，不增加独立 L2 执行任务。语义上不能独立评分时，先按官方方式记录耦合验证方案与覆盖，缺少环境或权限不能作为“不适用”。必要前置通过后即推进首例；默认回归在交付前完成，可用 `stage: delivery` 安排在 runtime 后。若项目要求先行或公共改动影响执行基础，相应回归仍放前面。同一条测试命令已覆盖专项与默认回归且结果有效时，只保留一次执行，不机械拆成两轮。

### 数据集安装验收（必检）

按[协议导航](benchmark-protocol.md#2-接入包manifest-与配置)读取目标协议的启动自动导入及数据集安装验收章节，定位实际安装、查询和存储入口。将协议适用断言写入验证矩阵，执行真实启动、内容与落库核对，并关联可复用测试的版本和范围。

将有效配置、启动日志、原始查询、逐项比较及清理证据归入现有 `source` 检查，按 [acceptance.md](acceptance.md) 输出结果和缺口。预期清单与检查程序分别登记到对应输入，后续执行和评分使用同一已核对的安装版本；CLI 只运行检查和验证记录，实际查询与断言由宿主或项目已有程序完成。

### 配置接入验收

按[协议导航](benchmark-protocol.md#7-验收与维护)读取目标协议的配置验收章节，定位本次加载与实际消费路径，登记协议要求的适用检查和已有覆盖。运行受影响专项，复用同次安装、评分及执行的脱敏有效配置证据，逐项记录结果与缺口。

把所用非敏感配置、程序和部署指纹列入 `implementationInputs`，把配置前置声明为既有接口或 regression 检查的依赖，依 [acceptance.md](acceptance.md) 核对输入变化和证据有效性。

## 2. 生成并执行 L1 接口契约测试

实现接入包后，复用目标项目测试框架，为本次新增、改变及关键边界补充/参数化专项测试；已有公共入口测试按版本和适用范围直接复用。下列为选择覆盖的风险方向，不要求逐项重建测试：

- 合法请求、Schema 与公开/私有边界；适用的字段缺失、非法 Case、错误身份/归属和上下文不匹配。
- 创建与启动的冻结身份和重复调用；实际幂等合同、不合法的状态转换、迟到回调。
- Artifact 必需集合、MIME、真实字节摘要、大小与内容；结果类型、原生指标、归一化和 Evidence。
- 环境“已接受/运行中/ready/needs_action/failed”及评测业务/基础设施状态的区别。

允许受控夹具、假依赖或构造回调验证合同，使用隔离数据并显式标记。保存测试命令、日志和断言结果；接口返回 2xx 本身不等于业务通过。对需要真实部署的 L1 场景，查询运行中的目标接口，记录该场景实际使用的依赖。

## 3. 固定提交评分对照（L2 评分）

调用真实评分前，按 [部署前提](discovery.md#当前方案的部署前提与完成条件) 核对平台和 Evaluator 的实际运行版本、配置位置及双向连通性：平台能访问 Evaluator，Evaluator 容器内部能访问平台。健康响应或宿主机网络检查不能替代容器回访验证；实际进度、Evidence 和结果回调是否成功，复用下面同次评分任务的记录确认，不额外启动 Agent。环境缺口阻塞真实评分，不阻塞独立本地检查。

1. 使用与官方基线相同的冻结正确、错误、非法和边界提交/状态，按实际 Evaluator 合同交付，不启动 Agent。
2. 等待业务终态，保存原生输出、Evidence、版本与清理事实，按验收合同的“评测产物核对”记录原名、集合、内容、来源与实际平台下载的对应关系；同一次服务响应转换为 scoresFile 与官方基线比较，不重复提交任务采证。由该次服务结果直接完成官方一致性对照。
3. 评分依赖环境、句柄或执行中反馈时，事先说明状态交接和耦合验证方案。缺环境不属于语义不适用，不用函数对照或健康检查代替真实评分。

L2 执行段默认不单独运行。下一节首个完整 Case 的执行、真实提交、隔离和清理证据同时覆盖该分段；只有任务语义或本次改动风险明确需要时才增加独立执行及理由。固定提交的评分成功不能替代真实 Agent 链路。

## 4. 执行 L3 完整端到端

默认按冻结样本逐例执行以下步骤，当前 Case 的链路核对与清理完成后再启动下一例。发现接入、环境或证据问题立即诊断，解决后再继续，不等整批结束才处理；仅将执行并发设为 1 后一次提交全部样本，不等于逐例验收。使用项目现有的单 Case 或分步启动入口，不为此新增验收框架或修改平台批量调度。Agent 答错、低分或零分本身不构成接入失败，执行、提交、评分及证据链路正常即可记录后继续；修复时复用已有有效结果，只重测受影响范围。

1. **检查前置结果**：本地检查和固定提交评分前置已通过且版本/摘要一致；L2 执行证据在本次首例中取得，所有已提交任务状态已知。不等待与本次执行无关的收尾回归或完整报告；项目要求先行的检查仍遵从。无法完成的前置项直接给出缺口，不启动对应后续阶段。
2. **核对部署和数据**：按 [部署前提](discovery.md#当前方案的部署前提与完成条件) 核对源码、安装/构建产物、实际运行入口和生效配置；平台、客户端及 Evaluator 使用本次需要的版本与资源。客户端须在正确账号下在线且能力匹配，不以安装退出码或进程存在代替。复用仍有效的平台↔Evaluator 通信及评分回调证据，客户端从其运行环境能访问平台；部署或配置变化后复查受影响方向。安装/验证数据和 Case，核对实际存储及其一致性，再查询匹配目标。默认通过页面完成环境检查/准备并复查就绪，遵守目标仓库的启动及浏览器验证授权约束；使用等价自动化入口也必须覆盖必要准备链路，说明等价依据。API 证据不能冒充页面交互验证，未验证页面时明确标注；缺少必要准备覆盖不能直接创建后宣称完整通过。
3. **创建并启动**：通过实际用户入口发起实验，提交前按 [usage.md](usage.md) 保存稳定请求 ID；返回后马上记录平台实验/任务 ID。返回 202 只表示接受，后续查询实际任务。
4. **观察真实执行链**：有界轮询目标查询入口，记录执行、上传、评测的状态转换。执行器和 Evaluator 自行发送 progress/complete；验收脚本不能伪造终态、替换 Agent 提交、手工补数据库或绕过平台拼接成功结果。
5. **核对跨阶段身份**：逐 Case 关联数据集版本、external/internal Case ID、experimentId、executionRunId、Artifact ID/摘要、evaluationId/attempt、Evidence ID/摘要。分页覆盖整个声明范围；新执行不能套用旧终态。复查已完成的同一执行时保留原身份与来源，并重新核对版本及清理。
6. **核对真实评分与产物**：读取实际提交和官方 Harness 输出，检查业务结果、主指标和聚合。评分可重放时，用本次 Agent 提交再做独立官方对照；否则保存同状态下的权威证据及限制。不能用 L2 的预制提交替代本次执行结果。同次核对本 Case 的原始输出、实际附件列表和下载字节，保存 artifactChecks；页面验证单独如实记录在 artifactPresentation，API 下载不冒充页面通过。
7. **检查配置复用、重试与边界路径**：按[协议导航](benchmark-protocol.md#4-adapter-与实际执行)读取对应验收章节，执行适用的正式入口操作并核对实际生效配置、终态与提交物摘要；证据纳入现有 runtime，API 业务链路与页面交互覆盖分别记录。其余本次相关的失败/边界至少覆盖一项，优先由本地或固定提交评分组验证；仅任务语义或改动风险需要时另跑真实重评、超时、取消或恢复。标明实际覆盖层次；不要求人为破坏共享部署来制造故障。
8. **清理并报告**：在成功、失败及异常路径收敛本次任务和资源，保存清理查询及需保留项；按层次报告结果和缺口。Agent 业务未通过可以是链路正常，执行/评测基础设施错误不能记作业务零分或验收通过。

### 百分比展示验收（必检）

接入声明了百分比指标时，依据目标项目开发规范、实际取值和格式化代码，确认官方单位、Adapter 映射、汇总单位和页面格式。`percentage` 接收已换算的百分数时，`0～1` 的官方比例在送入展示前只乘一次 `100`，保留官方原值及证据。

复用固定提交或已有测试数据，至少核对满值与一个介于零和满值之间的非零值。例如官方比例 `1` 应显示 `100%`，`1/6` 在保留两位小数时应显示 `16.67%`。覆盖 Case 行、评分点及实际展示该指标的汇总视图，按各入口的精度断言。检查从真实结果映射到最终字符串的链路，避免仅向格式化函数手工传入已换算的正确值。浏览器未验证时，可用实际取值和格式化入口做代码断言，仍单独标明页面未验证。将输入、期望、实际值和证据归入已有接口合同或真实链路检查；缺少证据或断言失败时不得交付通过。

## 5. 将步骤接入现有验收程序

优先复用目标项目已有测试和调用入口；已有测试、CLI 或正常部署 API 可以直接承担各项检查；也允许 Agent 分步操作、保存原始证据后转换为 check。需要适配时只在本次运行目录补必要的调用或结果转换，不默认生成共享驱动，不为验收新增业务接口或框架。本版目标的 Benchmark 专属测试统一位于 `test/<key>/`、以 `.test.ts` 结尾并纳入默认回归；部署 Smoke 保留在接入包 `smoke/`，不将其通过视为专属测试已进入默认流程。实际操作仍须覆盖调用、终态、断言及清理；脚本不是完成这些步骤的必要形式。包内 CLI 执行配置命令及汇总，不内置平台操作；缺少真实证据时报告缺口，不以测试专用配置绕过正常部署。

- `stage: evaluation`：同次服务响应完成官方一致性对照；函数级排错使用已有专项测试。
- `stage: delivery`：仅用于真实链路后、交付前的必需 regression 检查，依赖 runtime；失败或缺失仍不得 accepted。默认模板拆分接口专项与收尾回归；若已有一条测试命令同时覆盖两者，保留原前置命令并移除重复的 delivery 项。
- `checks` 中的 L1/专项回归命令：可以使用 `category: regression`，按需要返回结构化 check 或使用现有测试退出码；合成输入不能冒充真实运行。
- `runtime` 命令：复用已有测试、CLI 或正常部署 API；宿主已分步完成真实链路时，可只运行结果适配命令。实际操作仍须先满足本地检查与固定提交评分前置，并按 Case 和业务步骤停止失败后的后续执行；verify 通过 dependsOn 校验检查依赖。首例执行证据复用规则见第 4 节，不为适配结果重跑任务。
- runtime 返回 [acceptance.md](acceptance.md) 所需的 `facts.mode: live`、冻结 `caseIds` 和六步引用；`evidence` 关联本地检查、固定提交评分和全部选定 Case 完整运行的记录；L2 执行与 L3 可以引用同一份真实证据，不复制运行，保留实际查询、断言与清理证据，按计划说明语义上不适用项。缺条件返回 `blocked`，断言失败返回 `fail`，不写无实际操作的 `pass`。
- 将实际使用的入口、薄适配、专项测试及相关配置加入 `implementationInputs`；平台任务由子进程使用 `record-job.cjs` 记录，不能在持锁检查中递归调用主 CLI。

单次请求、轮询、阶段运行、取消及清理都受外层命令超时约束；仅在用户显式设置任务总时长时，才同时受剩余总时长约束。默认不设置整个接入任务的总次数或总时长限制。为清理预留时间，外层 `timeoutSeconds` 大于内部工作期限与清理期限之和；不能仅增大超时或次数掩盖失败。

## 6. 等待、证据与恢复规则

冻结计划中写明请求超时、各阶段截止、本次真实运行及清理期限、轮询间隔及上限；这些操作期限不等于整个开发接入任务的总时长预算。按实际可重试错误和幂等合同设置重试次数上限并有限退避，同类失败达到上限或持续无进展时停止重试、保存证据并诊断，关键条件不明确时与用户交流；到期先保存最后响应与在途 ID，再使用目标取消/查询入口处理。先查目标项目状态定义并实现映射，每次查询返回后立即映射，再决定是否继续等待；不能把所有未列出的状态当成运行中，未知状态应报适配缺失并保留最后响应；观察到运行终态立即转入结果核对和清理，清理确认后结束，不无条件等满预设时长。开发记录区分实际运行、查询等待、用户确认及空闲时间，不把提交接受时间当作运行完成。恢复时核对已有任务，不因网络结果未知而重新提交。

区分任务存活与有效进展。继续等待须结合实际阶段、阶段期限及进展证据；运行状态或心跳本身不足以证明有效进展。连续观察无有效进展时定位阻塞依赖，不仅凭存活延长等待；无需任务持续输出日志，正常排队可依据队列状态与期限判断。

重试前核对失败原因及各执行层已有的重试，同一未解决故障的重试次数合并考虑，不因更换任务、实验或调用层级重新计数。确定性错误先修复；可恢复错误重复发生达到上限或持续无进展时，停止重试并重新诊断。沿用现有运行记录保存依据，不为此新增计数框架。

脚本需要轮询时复用 usage.md 中的 waitForJob（trackedJob 已使用它），query 只做一次请求，不内置第二层循环；独立评分检查也沿用该方式。每次请求传递 AbortSignal；外层请求期限可结束失控的异步等待，但不能强停忽略取消信号的代码，仍须核对实际任务。手工操作同样逐次识别终态，使用宿主任务句柄等待，不手工 `&` 后依赖 shell 通知，也不固定长时间 sleep。

原始记录包含层次/阶段、时间、脱敏方法/入口与请求/响应、HTTP 和业务状态、预期/实际断言、关联 ID 与摘要。子进程、容器、后台派发与临时工作区的清理必须有查询证据；复用缓存、共享镜像和受控证据可以保留并注明原因，不能删除其他实验资源。

包内程序校验结构、范围和摘要，不提供原始平台证据真实性认证。开发 Agent 仍需审阅驱动程序和实际查询；“live”标签、文件存在或健康检查不能独立证明 L3 已执行。

## 7. 失败诊断与按影响重测

结构化 stage、依赖声明与评分结果字段见 [acceptance.md](acceptance.md)，驱动调用见 [usage.md](usage.md)。前述三组验收是顺序与首例复用的唯一操作指引。

修复前先查询任务与清理状态，保留初始错误，定位实现、数据、配置、部署或驱动断言的影响。确定性失败须先修复并做本地验证，不能原样整轮重试或只增加等待。按以下依据选择最小必要重测：

| 修改影响 | 先做的验证 | 真实调用与复用边界 |
|---|---|---|
| 格式、解析、报告或驱动断言 | 使用本次已保存响应作本地重放并跑专项 | 重放只证明处理逻辑；修复后审查断言是否改变实际结论，不能伪造新运行 |
| 评分逻辑或评分配置 | 对固定提交做官方一致性检查 | 原提交仍有效时使用目标支持的重评，不自动重跑 Agent |
| Agent 输入、执行环境或执行逻辑 | 跑受影响专项并重新检查前提 | 重跑受影响 Case 及后续评分，不沿用旧执行结论 |
| 数据、公共代码、部署或未知影响 | 定位受影响路径与版本 | 证据不足以证明可复用时补查或重验；共享路径变化需覆盖其影响 |

在现有事实索引记录失败原因、修改范围、被保留证据的版本/输入/提交摘要/覆盖、失效项及重测结果。复用以仍然有效的证据为依据，不直接复制旧通过状态。

CLI 仍执行检查命令和当前断言，不直接继承旧 pass。驱动可用 [recordedOperation](usage.md#原始操作记录与复查) 复查已保存的原始响应；该工具只对显式操作输入复用，不替模型判断遗漏的依赖。评分或执行输入变化时拒绝复用该操作，按本节影响范围重测；仅转换代码变化时重新转换、检查，并生成本次证据。旧操作未完成时先恢复查询，不通过新建记录绕过在途任务。专项与收尾回归不重复运行同批有效测试。驱动对既有任务先查询其终态与清理，结果未知不重提；实际调用和清理可复用已有入口或由宿主完成，结果适配只转换证据；不能把旧任务结果冒充修改后实现的真实运行。

必要结论、项目回归及清理均有有效证据且最终报告 accepted 后交付；进一步验证须指出尚未覆盖的风险，不以“再确认一次”为理由扩大范围。

## 评测产物的覆盖与复用

先按对应版本官方文档确定证据范围，再由同版本评分入口核实或补充，记录差异处置与排除项；实际文件名和目录来自所选官方入口，不为沿用示例合并、改名或制造统一报告。缓存、输入副本及中间文件不能因出现在输出目录就全量展示，先按范围交付到受控证据目录；目录扫描不是业务分类器。只有返回值（含布尔值、标量、对象或元组）时只忠实序列化实际返回，并在映射材料中注明来源；不得增补字段制造报告。官方无报告须明确说明，不为凑附件另造报告或仅改名保留无必要的自制报告。必要的接入层元数据、平台日志及哈希不算官方产物，展示名称也不得称“官方报告/判定记录”。复用官方入口分析和已有专项测试，沿“官方调用 → 实际写出/返回 → 上传附件”核对生产者与变换；仅对比接入层生成文件和下载字节不够；集合与字节核对并入上述评分服务和各选定 Case 的真实链路，不增加检查阶段或真实调用。结构字段和门禁只维护在 [验收合同](acceptance.md#评测产物核对)。

失败/早停保留实际已经得到的产物，不编造未执行用例、解释或异常栈。已有固定错误/非法/边界提交覆盖相应产物语义，必要的公共异常采集测试可复用；不为展示另跑模型。只修附件采集或展示时，原始记录完整且输入/版本仍有效可复查已有记录；原件已经丢失时复用提交重评，不能重建一个摘要当原件，也不因此重新执行 Agent。路径、大小或私有内容限制形成明确处理记录与缺口，不静默删改后称完整交付。
