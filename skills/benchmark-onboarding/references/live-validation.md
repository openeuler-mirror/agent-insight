# 分层真实验证操作指引

开发 Agent 在设计验收计划和生成接入实现时读取本页。目标项目现行接入规范是权威；本页把“L1 接口契约 → L2 分段真实集成 → L3 完整端到端”落实为接入任务的操作步骤。具体路径、认证、命令和能力仍按 [discovery.md](discovery.md) 查询，不以某个 Benchmark 的现有测试直接代替本次验证。

## 1. 发现入口并制定计划

1. 核对项目身份、协议差异与部署版本；按任务创建、环境、执行、Artifact、评测、结果、重评/取消、资源回收追踪实际调用链。记录路由/CLI、请求类型、鉴权及状态机代码、对应测试和版本。某阶段使用 CLI 或服务合同就沿用该入口，不新增测试专用 API。
2. 将 [validation-matrix.md.tmpl](../assets/templates/validation-matrix.md.tmpl) 复制到包外 `$RUN_DIR/validation-matrix.md`。逐阶段填写前置数据、调用身份、具体入口、命令、正常/异常输入、HTTP/业务/产物断言、异步终态、期限、依赖、证据和资源清理。用户会话、设备身份、服务请求分别处理，凭据只引用已有配置。
3. 固定官方 Case、数据/接入版本、预算、Agent/模型、执行和评分条件。记录测试覆盖层次；至少选择一条可完成的真实链路及本次相关的边界/失败覆盖，不把“模型必须答对”作为链路正常的前提。
4. 保存 matrix、协议核对、来源及官方固定提交等计划输入，再 `freeze`。矩阵记录计划，不回写实际结果；结果进入各次 attempt 的独立证据。后续改计划需说明原因并重新冻结。

### 数据集安装验收（必检）

生成 `source` 检查程序时，先查询目标 Loader、安装事务、数据模型、查询接口和实际存储配置，确定数据落在数据库、索引/清单、本地文件或对象存储的哪些位置。表名、字段、路径及导入语义不写死在 Skill 中。冻结预期数据清单、映射规则和检查范围，不冻结运行中数据库文件本身；每次检查重新读取实际数据并保存证据。

1. **文件完整性**：在实际存储端读取数据文件/对象并解析，核对固定来源、revision、split、格式/Schema、大小、摘要、记录数、Case ID 集合与唯一性；检查缺失、截断、损坏和解析失败。大型数据可流式核验；远端数据需读取实际内容，不能只用 HEAD、文件存在或 ETag 代替内容检查。记录全量来源、安装范围及执行子集的区别。
2. **落库正确性**：通过能证明持久化结果的项目查询接口、只读 ORM 或只读数据库查询，核对安装状态、数据集/版本标识、所属账号或租户、Case 数量、external/internal ID 映射、关联关系和公开/私有字段存放位置。分页读取覆盖声明安装范围；接口不暴露必要字段时，补只读存储检查或标记 `blocked`，不能把返回 200 当作已落库。没有数据库的项目验证实际索引/清单，并记录替代依据。
3. **记录与文件一致性**：按目标 Loader/Adapter 的确定性转换规则逐项比较声明安装范围内的 Case 集合、字段映射、数据版本、内容指纹和资源引用；检查漏导、重复、串版本、错误路径、悬空引用，以及本次资源清单内无记录引用的残留文件。原始数据与规范化记录不要求字节相同，须重算目标指纹并说明映射；文件只作导入源、内容已内联入库时核对转换后的内容，不强求不存在的逐 Case 文件。读取公开/私有内容的断言在受控端执行，公开证据只留摘要和差异统计。
4. **导入行为与恢复**：在隔离测试数据集上按实际合同再次导入同一版本，验证预期的复用、拒绝或新版本行为，不能无故重复 Case 或覆盖被实验引用的冻结数据。用受控损坏/缺失输入或隔离故障验证失败后状态、回滚或可恢复的部分记录、临时文件与锁释放；修复输入后按合同重试/续传，再执行前三项核对。记录各场景使用真实存储还是 Mock 及所在层次，不在共享数据上制造损坏。

每项保存查询/读取时间、存储与版本标识、预期/实际数量及 Case 集合摘要、缺失/重复/多余 ID、字段或资源差异、脱敏原始查询和清理结果。无可用文件存储时记录实际数据载体及等价内容校验；语义不适用需有实现依据，访问不足属于 `blocked`。任一必需项缺证据或失败，数据安装不得记为通过。

`source` 返回现有 check 结构并引用上述独立证据；四项覆盖可汇总专项测试与真实安装记录，但必须区分模拟验证与部署事实。数据集检查程序及配置列入 `implementationInputs`，预期清单纳入 `baselineInputs`。L2 执行和 L3 的驱动必须核对数据检查通过且对应本次安装版本；L3 新建或重装数据时重新检查实际数据。通用 CLI 不会自动连接数据库或推导这些断言。

## 2. 生成并执行 L1 接口契约测试

实现接入包后，复用目标项目测试框架，为本次使用的入口补充/参数化专项测试，覆盖：

- 合法请求、Schema 与公开/私有边界；适用的字段缺失、非法 Case、错误身份/归属和上下文不匹配。
- 创建与启动的冻结身份和重复调用；实际幂等合同、不合法的状态转换、迟到回调。
- Artifact 必需集合、MIME、真实字节摘要、大小与内容；结果类型、原生指标、归一化和 Evidence。
- 环境“已接受/运行中/ready/needs_action/failed”及评测业务/基础设施状态的区别。

允许受控夹具、假依赖或构造回调验证合同，使用隔离数据并显式标记。保存测试命令、日志和断言结果；接口返回 2xx 本身不等于业务通过。对需要真实部署的 L1 场景，查询运行中的目标接口，记录该场景实际使用的依赖。

## 3. 执行 L2 分段真实集成

### 执行段

1. 确认所依赖 L1 和数据集安装检查通过且输入摘要未变化，完成本次 Case 和 Agent 的实际环境检查。
2. 通过已发现入口运行真实 Agent/模型，保存请求/运行 ID，等待执行终态，记录实际执行与适用 Trace/进程证据。
3. 获取该 Agent 产生的提交，读取真实字节，核对归属、摘要、格式和任务需要的状态；观察实际文件/网络与私有数据边界。
4. 保存原始运行和提交证据，核对执行资源清理。缺少合法提交则明确本段问题；业务是否答对留给权威评分。

### 评分段

1. 准备与官方基线相同的冻结提交/状态，按实际 Evaluator 请求合同交付，使用真实依赖和官方 Harness。
2. 等待评测终态，核对原生结果、Evidence、归一化及聚合；与独立官方结果逐样本比较，保留 Judge/随机过程的预先配置和容差。
3. 检查评测清理。依赖环境、句柄或反馈时验证状态恢复和官方反馈时序；不能独立运行的分段须在计划中说明理由、状态条件和替代的耦合真实测试。缺少能力属于待办，不改成可选项来通过。

L2 两段分别成功仍不是 L3 成功。固定答案的评分成功只证明评分路径，不证明 Agent 执行。

## 4. 执行 L3 完整端到端

1. **检查前置结果**：所需 L1、L2 已通过且版本/摘要一致，所有已提交任务状态已知。无法完成的前置项直接给出缺口，不启动对应后续阶段。
2. **核对部署和数据**：本次接入代码与资源已部署到所需组件；安装/验证数据和 Case，按数据集安装验收核对实际存储及其一致性，再查询匹配目标，完成本次 Agent、模型与配置的环境检查/准备。
3. **创建并启动**：通过实际用户入口发起实验，提交前按 [usage.md](usage.md) 保存稳定请求 ID；返回后马上记录平台实验/任务 ID。返回 202 只表示接受，后续查询实际任务。
4. **观察真实执行链**：有界轮询目标查询入口，记录执行、上传、评测的状态转换。执行器和 Evaluator 自行发送 progress/complete；验收脚本不能伪造终态、替换 Agent 提交、手工补数据库或绕过平台拼接成功结果。
5. **核对跨阶段身份**：逐 Case 关联数据集版本、external/internal Case ID、experimentId、executionRunId、Artifact ID/摘要、evaluationId/attempt、Evidence ID/摘要。分页覆盖整个声明范围；新 attempt 不使用旧终态。
6. **核对真实评分**：读取实际提交和官方 Harness 输出，检查业务结果、主指标和聚合。评分可重放时，用本次 Agent 提交再做独立官方对照；否则保存同状态下的权威证据及限制。不能用 L2 的预制提交替代本次执行结果。
7. **检查边界路径**：按矩阵在隔离试验范围内验证适用的重评、超时、取消、重复或恢复行为。标明每个失败/边界场景实际在 L1/L2/L3 哪层验证；不要求人为破坏共享部署来制造故障。
8. **清理并报告**：在成功、失败及异常路径收敛本次任务和资源，保存清理查询及需保留项；按层次报告结果和缺口。Agent 业务未通过可以是链路正常，执行/评测基础设施错误不能记作业务零分或验收通过。

## 5. 将步骤接入现有验收程序

开发 Agent 按目标入口生成本次专用测试驱动程序，代码放接入包的 tests/smoke 或目标协议规定位置，运行输出放包外。它负责阶段依赖、真实调用、轮询、断言、取消与 `finally` 清理；包内通用 CLI 负责执行配置命令及汇总，未内置所有平台操作。

- `candidate`：实现同一批冻结提交的接入评分调用，用于官方对照。
- `checks` 中的 L1/专项回归命令：可以使用 `category: regression`，按需要返回结构化 check 或使用现有测试退出码；合成输入不能冒充真实运行。
- `runtime` 命令：调用本次驱动程序。先核对或执行它所依赖的 L1/L2，再运行 L3；前置失败即停止后续并保存原因。不要只依赖 `verify` 中命令的排列，它不会根据上一项失败自动推导并停止业务后续。
- runtime 返回 [acceptance.md](acceptance.md) 所需的 `facts.mode: live`、冻结 `caseIds` 和六步引用；`evidence` 至少包含可关联的 L1、L2、L3 原始记录、实际查询、断言与清理证据，按计划说明语义上不适用项。缺条件返回 `blocked`，断言失败返回 `fail`，不写无实际操作的 `pass`。
- 将生成的驱动程序、专项测试及相关配置加入 `implementationInputs`；平台任务由子进程使用 `record-job.cjs` 记录，不能在持锁检查中递归调用主 CLI。

测试驱动内部各阶段没有自动获得额外预算：单次请求、轮询、阶段运行、取消及清理都受外层命令和总预算约束。为清理预留时间，外层 `timeoutSeconds` 大于内部工作期限与清理期限之和；不能仅增大超时或次数掩盖失败。

## 6. 等待、证据与恢复规则

冻结计划中写明请求超时、各阶段截止、总试验/清理期限、轮询间隔及上限。按实际可重试错误和幂等合同有限退避；到期先保存最后响应与在途 ID，再使用目标取消/查询入口处理。恢复时核对已有任务，不因网络结果未知而重新提交。

原始记录包含层次/阶段、时间、脱敏方法/入口与请求/响应、HTTP 和业务状态、预期/实际断言、关联 ID 与摘要。子进程、容器、后台派发与临时工作区的清理必须有查询证据；复用缓存、共享镜像和受控证据可以保留并注明原因，不能删除其他实验资源。

包内程序校验结构、范围和摘要，不提供原始平台证据真实性认证。开发 Agent 仍需审阅驱动程序和实际查询；“live”标签、文件存在或健康检查不能独立证明 L3 已执行。
