# 来源与能力查询

## 从用户入口定位目标

用户给出 Agent Insight 项目地址和 Benchmark 来源。项目地址可以是 Git 仓库 URL 或已存在的本地根目录；平台 Web/API 地址是另一项部署连接信息。先定位匹配的工作副本，核对 remote、分支、commit、未提交改动和仓库协作约束。`init` 只检查已有副本，不自动 clone、fetch、切分支或改 Git 配置。

本地路径必须对应工作副本根目录。远端地址按主机和仓库路径匹配，HTTP(S)/SSH 和末尾 `.git` 可归一；不根据同名目录推定匹配。地址有凭据时改用不含凭据的仓库地址和现有认证机制。无法定位、访问受限或多个副本无从选择时，给出具体缺口。

定位工作副本与平台后，先按下方“执行对象确认与方案选择”查询候选并发起用户选择。等待期间可读 [benchmark-protocol.md](benchmark-protocol.md) 与[代码导航](benchmark-protocol.sources.json)，定位本次所需的当前源码、校验器及测试。清单中的路径是发现起点，不是固定的项目布局要求，也不要求逐项通读。在目标根目录按以下线索发现文档和代码，路径移动时继续按标题或符号检索：

```bash
git -C "$TARGET_REPO" remote -v
git -C "$TARGET_REPO" status --short
git -C "$TARGET_REPO" rev-parse HEAD
rg --files "$TARGET_REPO/docs" "$TARGET_REPO/packages" "$TARGET_REPO/services" "$TARGET_REPO/benchmarks"
rg -n 'Benchmark 接入|AbstractBenchmarkAdapter|validateTaskEnvelope|createBenchmarkExecutor' "$TARGET_REPO/docs" "$TARGET_REPO/src" "$TARGET_REPO/packages" "$TARGET_REPO/services"
```

只读查询结果可以自动用于下一步。需要获取远端代码、调整分支或引入公共能力时，按目标仓库约束和用户已授权范围处理。

## 从当前源码确定接入合同

沿代码导航定位本次涉及的类型、校验器、实现和相关测试，确认字段、方法签名、状态与实际行为；路径移动时按标题或符号检索。不比较目标代码与 Skill 发布时的 commit 或整文件摘要，也不因文件变化单独生成差异核对单。协议版本字符串相同不能替代阅读实际合同。

将实际使用的源码位置、关键合同和必要适配写入已有接入确认单；只有当前接口或行为确实不能满足需求时，才记录具体缺口并讨论适配或公共扩展。普通接入不修改已安装 Skill。影响实现的源码列入 implementationInputs，只有影响独立官方评分的内容列入 baselineInputs；不因阅读过某个文件就将其加入评分基线。当前工作副本版本和本次输入摘要用于验收追溯，不用于匹配 Skill 的历史版本。

## 执行对象确认与方案选择

开始阶段定位项目与平台后，先核实以下两个范围，取交集供用户选择，再形成执行方案；不为筛选候选先实现所有适配：

1. **查询客户端实际可用范围。** 使用目标项目现有能力查询入口，读取当前账号可见客户端实际上报的 Agent、具体模型、在线状态及链路跟踪能力；源码注册表和示例不代表本机可用，模型列表用于核实运行能力，接入阶段只确认 Agent。数据集未安装时先查通用能力；查询失败、无权限或未注册时说明缺口，不能推断为不支持或退回默认 Agent。 候选资格沿用目标项目现有能力解析与匹配逻辑，核对能力合并、替代条件及执行配置；不能因单个字段缺失或局部列表未声明就排除。排除须指出实际失败条件及证据；查询与代码结论矛盾时继续核实，证据不足列为“待核实”。
2. **核实 Benchmark 支持范围。** 定向读取固定版本的官方 CLI、SDK、Harness 执行入口及扩展合同，核实哪些客户端 Agent 可保持官方任务、工具/反馈时序、环境、提交与评分语义。支持包括内置接法，以及通过 Benchmark 可扩展的自定义 Agent 插件、回调或函数完成接入；不能仅因内置列表没有某个 Agent 就排除它。适配可行性须有文档或源码依据，说明调用方式、需开发的最小适配及 Trace/提交/清理如何贯通；尚未实现可列为“需适配”，只有设想或合同不明的列为“待核实”，不当作已支持。
3. **展示交集并与用户确认。** 可选范围 = 客户端实际可用的 Agent ∩ Benchmark 可支持的 Agent，展示交集内全部候选，区分“直接支持”和“需适配”。未就绪、待核实及不支持的组合可附原因说明，但不混入已确认候选。不要仅按客户端列表或 Benchmark 内置列表选择，也不因实现方便只展示一个；当前开发 Agent 不自动成为被测 Agent。可推荐但须说明依据，没有已有明确选择或授权代选时等待用户决定；等待期间继续独立的数据和评分工作。已有选择仍在交集内则沿用，否则说明变化并重新协商；交集为空时说明具体缺口，不默认换 Agent。安装数据后再做平台目标匹配和环境检查，不能以新 Benchmark 尚未注册为由排除已核实可适配的组合。模型范围沿用所选客户端 Agent 的实际能力；真实验收前再选择具体模型，仅记录为本次实验/验收参数，不据此向接入实现或部署 Profile 写入模型白名单。选定后优先复用官方方式与现有组件，仅实现必要薄适配；公共扩展按仓库要求对齐，不能仅导入分数冒充真实执行。
4. **按实际需要选择环境。** 网络、权限、隔离和执行评分关系遵循官方要求，并结合目标项目约束，按需添加沙箱、xGovernor 或 Docker；记录采用依据，优先复用官方方式和已有能力。区分官方要求、目标平台约束与某个后端自身限制；Evaluator 的打包方式不自动成为被测 Agent 的执行要求。官方要求同一环境或持续状态时优先保留该语义，平台阶段分开不等于必须另建容器或自建状态归档恢复。协议确实无法表达时按公共扩展流程处理，不能绕过校验，也不能为了沿用某个后端自行缩小 Benchmark 范围或改变官方语义；涉及此类取舍先与用户确认。

将客户端查询来源与时间、Benchmark 支持依据、交集候选及适配状态、用户选择和最小改动依据写入确认单，事实索引引用该结论。确定方案后只沿实际采用路径继续调查；本节要求不强制穷举所有后端，也不要求为方案比较重复调用模型。

## 当前方案的部署前提与完成条件

先阅读目标项目的 `docs/zh/how-to/evaluation/benchmarks/deploy-services.md`：地址选择（2.4）、平台启动（3.3）、Evaluator（5、6）、客户端安装/更新（7）及通信验证（8）。章节或路径变化时按标题查找；只读本次相关部分，已核对且未变化的内容复用。本机接入验收优先检查平台、客户端与 Evaluator 同机部署，已有用户指定或已核实的部署信息优先，不擅自迁移已有服务。三个运行角色不等于三台机器，同机容器也不共享宿主机的回环地址。

安装、更新或启动前，查阅目标仓库对应脚本的参数解析、路径/配置选择及实际启动部分，不能只看文件存在或帮助头部：

| 操作 | 当前脚本入口 | 操作前要核对的内容 |
|---|---|---|
| 平台启动/更新 | `scripts/start.sh` | 源码与构建目录、实际进程入口、端口及配置来源；dev/UI 验证仍遵守目标仓库授权与启动约束 |
| 客户端安装/更新 | `scripts/install-ras-client.js` | 首次注册还是已有绑定、源码复制到的 runtime 目录、系统服务启动路径及平台/账号归属 |
| Evaluator 启动/更新 | `scripts/evaluator.sh` | 构建来源、配置目录、运行镜像与挂载、端口和容器访问平台的地址 |
| 平台配置 Evaluator | `scripts/configure-evaluator-target.js` | 平台访问 Evaluator 的地址、配置写入位置及生效方式；与 Evaluator 回访地址分别核对 |

在现有事实索引按角色记录“源码目录 → 构建/安装产物及版本 → 实际进程或容器入口 → 生效配置位置”，引用已有安装输出、服务定义、进程/容器查询或脱敏配置证据，不新建部署报告。当前工作目录、源码更新和安装命令退出 0 都不能证明运行副本已更新；复制配置或切换目录后核对副本内容、加载位置及本次生效状态。只记录所需非敏感字段，不复制凭据。

首次客户端安装使用指南中安装页生成的命令；未注册时不能用无参数更新命令替代注册。已有注册时按脚本合同更新运行时并核对实际服务入口；只重启旧服务不会更新安装副本。安装后从平台核对正确账号下的客户端在线状态、Agent/模型与目标 Benchmark 所需能力，不以本地安装成功日志代替能力上报。

同机且平台/客户端运行在宿主机、Evaluator 运行在 Docker 时，默认端口示例如下；实际端口、代理或容器拓扑变化时按调用方所在环境调整。命令沿用部署指南第 5.2、6.2 节，不自行另写启动流程。

| 调用方向 | 默认访问地址 | 配置归属 |
|---|---|---|
| 宿主机客户端 → 平台 | `http://127.0.0.1:3000` | 客户端的平台地址及绑定 |
| 平台 → Evaluator | `http://127.0.0.1:3001` | `configure-evaluator-target.js --evaluator-base-url` |
| Evaluator 容器 → 平台 | `http://host.docker.internal:3000` | `evaluator.sh start --platform-base-url` |

`AGENT_INSIGHT_CONFIG_DIR` 只选择业务配置目录，不能代替上述通信地址；执行端回调覆盖也不能代替 Evaluator 的平台地址。检查连通性必须从实际调用进程/容器所在环境发起，宿主机 curl 成功不证明容器能回访。缺少环境、权限或有效证据时保留待验证，不为分析先部署全部服务或启动模型。

在现有事实索引记录前提、来源、检查结果和未决项。进入依赖该前提的实施前，关键能力须有证据，已知不兼容须解决或与用户对齐；其他模块的问题可以后续处理。没有环境访问条件时保留待验证，继续独立的数据或评分工作，不据此宣布兼容或擅自改方案。

安装或通信失败先保存原始错误与实际路径，按证据定位注册/账号、安装副本、系统服务、权限/挂载或网络方向，再修复对应原因；不原样反复重装、重启或延长等待，不用验收请求专用地址/请求头绕过正常部署配置。

调查围绕下一步的具体问题，静态结论未失效则复用；上下文恢复先读索引、用户决策与任务状态。动态部署、账号和客户端能力在使用前核对，不重复泛查整个项目。

## 分析官方实现

总体分析先确定官方语义、数据范围、公开/私有边界、提交格式、目标扩展点和关键选择。随后选择当前最小可验证产物，例如具有固定样本断言的数据 Loader/Schema，或能调用权威判分的评分包装；仅建空目录或写骨架不算完成。按产物的必要前置事实展开调查，后续模块的未知项留待对应实施，不要求先理解整个项目。

确定所需实际入口与状态合同后，按 [live-validation.md](live-validation.md) 编制验证矩阵；具体调用字段在对应模块实施时查询。

记录权威数据、代码和 Harness 的固定 revision，数据 split/subset、样本数量、Case ID、授权条件及文件摘要。区分官方发布、Hugging Face 镜像、第三方整理和实际导入数据；名称一致不代表版本一致。

追踪 Loader 到安装事务、查询接口、数据模型与存储配置，确定实际数据库/索引、文件/对象、版本和 Case 映射、内容指纹算法、重复导入及失败恢复合同。按 [数据集安装验收](live-validation.md#数据集安装验收必检) 制定内容、持久化、二者一致性和导入恢复的断言；不从本机默认目录推断部署数据位置。

确定评测证据时，先查对应固定版本的官方文档：

1. 文档已定义的正式报告、结果文件和相关日志按其说明收集，再用本次官方入口及参数核实实际产物。
2. 文档未说明或不完整，再追踪同版本评分程序的文件写出、返回值和诊断，补齐范围与含义；不要求穷尽所有资料后才读代码。区分官方实际生成与接入层加工：返回值只能忠实序列化，不能添加 Case、版本、哈希等字段拼出报告；官方不生成报告时明确说明，不自行补造。必要的平台协议映射、来源元数据与诊断单独标识，不称为官方原件。
3. 文档与程序不一致时核对版本/参数并记录差异和处置依据；无法确定且影响判分或范围的关键差异按主体沟通规则处理，不静默取舍或编造文件。

依据写入已有确认单：文档链接/仓内位置、版本/章节，以及程序补充、冲突处置和纳入/排除范围。缓存、输入副本与中间文件不自动成为证据；平台目录扫描只防漏传，接入层负责把选定原始产物与非证据文件分开，不把 evidenceRoot 当作过滤器。交付相关源码入口见代码导航第 6 节；不新增调查阶段或记录文件。

以下是全流程核对范围，在实施对应模块时沿实际调用链补齐，不作为所有模块开写的共同前提。每个结论引用代码位置和版本：

1. 任务创建、公开输入和隐藏材料装载。
2. 被测 Agent 的运行方式、工具/网络可见性、反馈时机与预算。
3. 提交生成：回答、文件、完整环境、进程事件或状态句柄。
4. Verifier 对提交的读取、错误分类、原生指标与聚合。
5. 超时、取消、恢复和资源释放。

固定文本或文件能独立判分时，验证不重新执行 Agent 的重评；依赖环境状态时，优先核对官方同环境验证或状态交接方式，确需快照或恢复时再明确充分条件。反馈参与执行时保持其时序和可见范围，不能把最终判分可独立误解成可以移除中间反馈。隐藏测试、答案和官方参考解不进入被测 Agent 输入或公开目录。

开发 Agent 为分析资料联网，不等于被测 Agent 获得搜索权限。根据官方要求和目标项目约束确定本次网络策略，并验证实际运行方式满足它；官方允许联网时不能因某个后端默认断网就改变任务语义。需要隔离时验证相应边界，目录分离和独立进程本身不是隔离证明。

## 从协议发现平台能力

以所给项目版本的接入规范为权威，从当前产物要求出发查询类型、校验器、注册实现和测试；需要部署条件的模块再查询实际状态。包内参考提供架构与查找线索，本次所需 Provider、Agent、Git 来源、Collector、后端和镜像必须现场发现，不能从示例推定支持。

记录“要求 → 本次选用实现 → 依据 → 实际参与路径”。接口字段/完整性合同和实际执行分支分别确认；保留必须满足的合同，但不因字段名称相同就展开其他后端或 Provider 的全部实现。未选用分支只在兼容性或决策确实需要时补查；能力缺口只阻塞依赖它的模块，关键不确定性按 Skill 沟通规则处理。

查询部署状态前，核对平台地址、当前登录账号/租户及其客户端和数据集可见范围。用户指定账号时使用该身份；页面仍在加载、账号不匹配或权限不足时，不能将空列表判为能力缺失。保存不含凭据的身份与目标证据，再按所选 Benchmark 查询执行目标。在线客户端、可选执行目标和实际环境检查通过是不同结论，分别记录。

新接入包发布还需定位平台与 Evaluator 的部署源码版本、目录和更新方式；已有执行客户端不代表本地新代码已部署。先查询项目已有部署说明和配置，缺少实际部署位置时只补问这一项，不要求用户重复提供已发现的执行机。

| 要求 | 发现线索 | 需要的证据 |
|---|---|---|
| Case 与任务 | Manifest、任务类型、Adapter 基类及协议校验器 | 字段是否可表达且被真实校验路径接受 |
| 工作区和运行 | 执行器装配、Provider、Runtime、Backend | 初始化、运行、取消与清理实现 |
| 执行 Profile | `packages/benchmark-protocol/execution.cjs`、任务 Schema、`src/lib/benchmark/execution-targets.ts` | 公开描述与摘要、环境和策略、绑定唯一性及不匹配处理 |
| 后端配置与探测 | `packages/project-config/execution.cjs`、`services/executor/src/execution-config.cjs`；再沿所选后端追踪 | 配置校验、就绪/Trace、实际执行注册和安装分发是否一致 |
| Submission | Collector 注册、Artifact 契约和摘要校验 | 实际收集的内容足以重现官方评分 |
| Evaluator | Catalog 校验、Evaluator 注册和 Entrypoint | 所需依赖、隔离、实际输出/返回值及平台附件映射 |
| 就绪状态 | 执行目标接口、客户端能力上报、环境准备入口 | 本次目标机器、Agent 和 Case 可运行 |
| 验证入口 | 目标仓库测试、Doctor/Smoke、端到端接口 | 是否真实执行，是否覆盖本次新增接入 |

区分公共 Profile 合同与所选后端能兑现的策略。原生工作区不因使用 Profile 就需要 OCI 镜像；无沙箱、客户端默认网络或未声明资源时，不宣称隔离已生效。核对客户端 `executionBindings`、公开 Profile 与本次执行目标的一致性；字段未上报和显式空数组按目标兼容合同分别处理，必需 Profile 缺失不能当作可回退路径。所读入口变化时按符号继续定位，不维护固定后端或模型名单。

结论使用“可复用 / 部署待准备 / 公共能力缺口 / 待验证”。组件存在不等于部署就绪；准备能力存在不等于本次环境已准备。不能在 Manifest 写一个新能力名来代替实现。

确认单放在包外，参考 `assets/templates/integration-plan.md.tmpl`。把所读协议、官方源码/评分配置、数据锁和冻结提交纳入验收计划的输入摘要；不在 Skill 里维护可用 Agent、Git 来源或 Collector 的固定列表。

## 配置接入

按[协议导航](benchmark-protocol.md#2-接入包manifest-与配置)读取目标配置接入要求和部署指南，沿加载器、类型、默认配置及本次消费者查询实际实现。在确认单记录配置来源、使用范围、消费路径及需要新增或复用的部分，再按[配置验收](live-validation.md#配置接入验收)执行对应检查并关联证据。

## 事实索引与分析完成条件

复制 facts-index.md.tmpl 到包外 `$RUN_DIR/facts-index.md`，作为短工作记录：当前最小产物、完成判据、必要前置事实、本次选用能力和路径、已有用户决策及下一项实施/验证。未决问题标明“当前产物必需 / 后续模块处理 / 需要用户决策”、受阻步骤及可继续工作；证据保留路径/符号、摘要/版本或动态查询时间。只在结论、决策或下一步变化时更新，不为每次读取另写记录。analysisInputs 引用已有接入方案即可；持续更新的索引原件不加入不可变 baselineInputs，不建立第二份支持能力清单或重复整段源码。

总体结论和当前产物必要事实足够、仓库设计/确认要求满足后，可推进不依赖评分基线的准备工作；verify 的基线要求见 [acceptance.md](acceptance.md)。运行专项检查后再推进下一产物。完整验收条件仍按计划执行；未知关键选择先沟通并阻塞相应步骤，不为“结束分析”猜测。一次调查应落到结论并实施、具体缺口的定向查询、最小验证或用户决策之一。持续没有新增证据时，转为最小验证、独立模块或具体决策，不继续扩大全仓搜索，也不以固定次数/时限阻止必要调查。

读取前先明确它要回答的具体问题，并查索引是否已有结论。优先选择与当前产物的输入、提交、评分和环境要求最接近的参考；其他实现只补必要差异。先检索符号，再读相关片段，截断时缩小范围，不反复读取长文件来重新确认已知结论。已回答问题的静态证据未变时复用；新问题可读取同一文件的相关片段，证据变化时只补读受影响部分并更新结论，不仅依赖 HEAD（工作树可能有改动）。动态部署、账号、客户端和任务事实在使用前重新确认；中断后先 resume、查询任务/清理待办，再恢复索引。
