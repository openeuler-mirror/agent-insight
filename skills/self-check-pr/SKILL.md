# Agent Insight PR 提交前自检

在建议提交/推送 Agent Insight 代码 PR 之前，必须执行本自检。所有清单项均来自本仓库近期 PR 中**真实发生并被驳回重改**的问题，不是通用 code review 模板。

## 铁律

```
自检不通过前，不得建议创建 / 推送 PR。
「我这边测试全绿」不是有效结论 —— 基线本来就有既存失败，要比的是失败集差集。
```

## 流程总览

```
Step 1  跑机械自查脚本（包含生产构建）
Step 2  确认改动范围（git diff <base>...HEAD）
Step 3  逐项执行 10 项自审清单
Step 4  专项复核「最容易走过场」的 4 类问题
Step 5  汇总结论：通过 / 阻塞项清单
```

---

## Step 1：跑机械自查脚本

在仓库根目录执行：

```bash
bash .opencode/skills/self-check-pr/scripts/self-check.sh
```

- 默认基线 `upstream/master`；可传参指定 `bash .../self-check.sh <base>`
- 接新框架时带上：`PR_FRAMEWORK=<你的框架名> bash .../self-check.sh`
- 脚本会实际执行 `npm run build`：非零退出码是阻塞项，Turbopack warning 记入待确认清单。
- 脚本还会检查 merge commit 夹带、文件编码/BOM、接入配对点，并提示测试失败集和破坏验证方法。
- **脚本标 ✗ 的必须先修，再进入下一步。** 标 !（warn）的记入待确认清单。

## Step 2：确认改动范围

```bash
git diff --stat <base>...HEAD
git diff <base>...HEAD
```

逐个文件问「它为什么必须变」。这一步是后续所有判断题的前提。

## Step 3：10 项自审清单

以下每项都必须给出「通过 / 不通过 / 需人工确认」的明确结论，不要默认通过。

### 1. 范围
- diff 里有没有跟本次目标无关的改动？逐个文件问「它为什么必须变」。
- 有没有改到：lockfile、package.json 的 version/scripts/依赖、CI、.env*、以及跟本需求无关的其它模块？有就该拆出去。
- 分支里有没有 merge commit？（机械脚本已查，这里人工复核）确认没把别人的 commit 带进来。

### 2. 配对点（改了一处，有没有配对的另一处漏改）
- 新增/修改的「值」（框架名、评估器 id、能力开关…）：在仓库里找**已存在的同类**，grep 出它出现的所有位置，逐个确认新值是否也该出现在那里。
- 特别注意「同一语义有两份清单」：例如 `data-service.ts` 里 `SUBAGENT_TREE_FRAMEWORKS` 和 `computeOwnSkills` 各有一份框架清单，只改一处会导致「子 Agent 树建出来了但本层 skill 算错」。
- 新加的字段/能力位，是否真的有代码去读它？**声明了没人读 = 静默失效陷阱。**

### 3. 静默失败（错误被吞掉的地方）
- 有没有 catch 之后只 console.warn / `2>/dev/null` 然后继续往下走的？失败会不会被用户看到？会不会打印「✅ 成功」？
- 有没有「未知枚举值落到默认档」？未知的 severity/status/rating 应该报错，不能静默降级成最轻的一档。
- 「没判出来」和「判为正常」必须是两种结果，不能都返回同一个中间值。

### 4. 「不适用」不等于满分
- 凡是「本场景不需要这个维度/这个检查」的分支，是给满分还是不计分？
- 给满分会把平均值往上拉，方向是错的。正确做法是**排除出分母并写明原因**。

### 5. 聚合/计分公式（有打分逻辑时必查）
- 单调性：把任意一个维度改判得更差，总分必须不升。用**小规模穷举**验证（维度数 n≤7 时 4^n 完全跑得动），别靠眼看。
- 分母是否包含全部维度？把「合格项」排除出分母会让分数与问题数量无关。
- 实际可达的分值有几个？如果只有 100/80/40/5 几个点，就别声称是 0-100 连续分。

### 6. 提示词（LLM 相关改动必查）
- 提示词里有没有写死验收用例的原句、或直接写死期望分数？
- 自查法：把每个具体例子换成同类的另一句话，规则还成立吗？不成立就是写死了。

### 7. 测试是不是真在测我的改动
- 破坏验证：把本次新增的核心逻辑改成恒定返回常数，测试必须变红。不红=白写。
- 加的测试，测的是改的东西，还是顺手测了别的既有模块？
- 改动有没有改变**存量**行为？如果合并/重构了两条分支，原来走 A 路径的老对象现在是不是被换到 B 路径了？给老对象补一条断言。
- 别用「我这边全绿」下结论：基线上本来就有既存失败，要比的是失败集的差集。

### 8. 跨平台与部署环境
- 路径处理：有没有假设路径不含符号链接？（macOS 的 /tmp、NFS 家目录都会踩）。比较路径时两边的规范化程度是否一致（realpath vs 未 realpath）。
- 有没有在安装/运行时联网装依赖？内网离线环境会卡死，仓库里有过先例。
- 依赖的外部工具（JDK/gradle/python…）在目标部署镜像里存在吗？
- 文件编码：有没有产出 UTF-16/BOM/CRLF 的文件？（PowerShell 重定向默认写 UTF-16）

### 9. 分层
- 有没有把「框架名/类型名」的特判写进共享的通用代码里（`if (framework === 'X')`）？归一化应该在各自的 adapter 里做完，通用层保持无关。
- 放的位置对吗？只有本域用的东西不要放进被多个产品面共用的目录。

### 10. 产物与文档
- 有没有把构建产物（.vsix/.zip/.jar/打包结果）提交进 git？应改为按需构建或走 release。
- 构建脚本能在 Linux 上跑吗？（本项目上游是 openEuler，只有 .ps1 等于没人能维护）
- 用户能感知的变化更新了 `docs/user-guide/` 吗？架构/契约变化更新了 `docs/developer-guide/` 吗？
- 一次性的验收报告不要入库，贴 PR 描述里。

## Step 4：最容易走过场的 5 类问题（专项复核）

以下 5 类必须专项确认，不能一带而过：

### 生产构建不能用单独 `tsc` 代替
`npm run build` 会执行 Next.js 实际的打包和类型检查边界，能发现单独 `tsc -p tsconfig.json` 没有暴露的错误。必须以 `npm run build` 的退出码为准；不得只 grep `✖` 测试行，否则 `Failed to compile` / `Cannot find module` 会被误判为没有新失败。

### 「测试全绿」不是结论
基线（`upstream/master`）上本来就有既存失败（当前 `npm test` 在 master 上约 9 条，多为需要 DB 的用例）。要比的是差集：

```bash
git stash -u && git checkout -q <base> && npm test 2>&1 | grep -E '^✖ ' | sort -u > /tmp/base.txt
git checkout -q - && git stash pop && npm test 2>&1 | grep -E '^✖ ' | sort -u > /tmp/mine.txt
comm -13 /tmp/base.txt /tmp/mine.txt      # 必须为空：不得引入新失败
```

### 改了存量行为要给存量对象补测试
真实案例：有人把两处重复的框架清单合并成一份（方向完全正确），但其中一个框架原本是被**有意排除**在外的，合并后它被换到了另一条代码路径，某个字段直接变成空——全量测试依然全绿，因为没有任何一条测试覆盖那个框架的这个函数。合并/重构时，**先列出受影响的老对象，每个补一条断言**。

### 声明了没接线 = 埋雷
真实案例：给 adapter 加了 `capabilities: { subagentTree: true, skills: true }`，但全仓没有一处读这两个字段，真正的开关还是另一处硬编码清单。当次功能是对的（两处都手工改了），但下一个人会以为声明即生效。**要么接线，要么先别加。**

### 单调性靠穷举，不靠眼看
真实案例：两套不同的打分公式都出现过「把某个维度判得更严重，总分反而更高」，而且两边的单元测试都断言了那个更高的数值——因为没人去比它前一档的值。n 很小时直接全枚举：

```js
for (const combo of allCombos(dims, LEVELS))
  for (const i of dims.keys())
    assert(score(worsen(combo, i)) <= score(combo), `${combo} 第${i}维升档后分数反而变高`)
```

## Step 5：汇总结论

输出三部分：
1. **通过项**（简要列出）
2. **阻塞项**（标 ✗ 的机械检查 + 自审中「不通过」项）——列出证据与修法
3. **待人工确认项**（不确定的判断，不得猜）

只有阻塞项为空时，才建议创建/推送 PR。否则明确告知用户「自检未通过，先修以下阻塞项」。

## 边界

- 本技能是**提交前自检**，不替代评审流程，也不替代领域清单（评估器看 `docs/developer-guide/10-evaluator-development.md` §7，采集器看 `docs/developer-guide/09-trace-collector.md` §五）。
- 机械脚本能抓：生产构建失败、Turbopack warning、merge commit 夹带、UTF-16/BOM/lockfile 损坏、接入配对点漏改。**抓不到**：分层、公式正确性、「不适用给满分」、提示词写死用例、静默兜底、基线框架自己就漏的地方。所以脚本输出的是「先怀疑再排除」的清单，判断题必须逐项人工/AI 复核。
